> **Package**: `blendsdk/codegen`

# codegen Best Practices

`blendsdk/codegen` treats everything it produces — generated clients, the committed OpenAPI contract, migration SQL, and the canonical snapshot — as **derived artifacts that are regenerated, not edited**. Its generators are deterministic and its gates (`blendsdk api check`, `blendsdk migrate validate`) compare bytes, not intent. Almost every rule below follows from that one property: whatever you hand-edit, skip, or hide will be reported as drift or `INVALID_HISTORY` on the next run.

All library examples import from the package root (`blendsdk/codegen`); CLI examples use the `blendsdk` executable.

---

## Do / Don't Pairs

### Regenerate — never hand-edit generated output

Every generated file starts with the marker line ``// Generated by `blendsdk api generate` — do not edit by hand.`` A hand edit survives exactly until the next generation run.

**❌ Wrong**

```bash
# "Just fix" the generated method name in place and commit it
sed -i 's/listProduct/listProducts/' src/api-client/client.ts
git commit -am 'fix client method name'
```

**✅ Correct**

```bash
# Fix the source of truth (the controller's operation metadata), then rebuild both artifacts
blendsdk api generate --config blendsdk.api.ts   # writes api.json and the client
blendsdk api check    --config blendsdk.api.ts   # the same rebuild, read-only: the CI gate
```

**Why:** `generateClient` overwrites its own files and prunes marker-bearing files it no longer generates, so a hand edit is lost on the next run. `checkClient` regenerates in memory and compares byte-for-byte, so the hand edit also fails CI as drift.

---

### Give every operation a unique, explicit `operationId`

The fragments below are `OpenAPIDocument.paths` entries; `generateClient` (and `blendsdk api check`) turn them into code or errors.

**❌ Wrong**

```typescript fragment
// ❌ two operations share one operationId
const paths = {
  '/api/products': {
    delete: { operationId: 'remove', responses: { 200: { description: 'OK' } } },
  },
  '/api/orders': {
    delete: { operationId: 'remove', responses: { 200: { description: 'OK' } } },
  },
};
```

**✅ Correct**

```typescript fragment
// ✅ one descriptive, unique operationId per operation
const paths = {
  '/api/products': {
    delete: { operationId: 'deleteProduct', responses: { 200: { description: 'OK' } } },
  },
  '/api/orders': {
    delete: { operationId: 'removeOrder', responses: { 200: { description: 'OK' } } },
  },
};
```

**Why:** a duplicate `operationId` (or a duplicate resolved group/method pair) aborts generation with a `ClientGenerationError` naming both locations. A *missing* `operationId` gets a deterministic fallback (`GET /api/products/{id}` → `productsGetById`) plus a warning at `generate` — and an error at `check`. Reserved words are escaped (`delete` → `delete_`) and reported as a warning, so pick names that don't need escaping.

---

### Always define a 2xx response schema

**❌ Wrong**

```typescript fragment
// ❌ no content schema: the generated method returns Promise<unknown>
responses: { 200: { description: 'OK' } }
```

**✅ Correct**

```typescript fragment
// ✅ a $ref keeps the shared component type; inline schemas become <Group><Operation>Result
responses: {
  200: {
    description: 'OK',
    content: {
      'application/json': { schema: { $ref: '#/components/schemas/Product' } },
    },
  },
}
```

**Why:** the generator looks for the first 2xx response with an `application/json` schema. Without one, the result type degrades to `unknown`, `generate` emits a warning, and `check` reports an error — you lose typing end to end. For paginated endpoints, opt into the `body` envelope so the result is wrapped in `PaginatedResponse<T>` instead of being unwrapped.

---

### Write the committed contract with `blendsdk api generate`

**❌ Wrong**

```typescript fragment
// ❌ toFile()/toJSON() write plain JSON.stringify output — not the bytes `check` compares
const generator = new OpenAPIGenerator({ title: 'Catalog API', version: '1.0.0' });
generator.addController('/api/products', ProductsController);
generator.toFile('api.json');
```

**✅ Correct**

```bash
# ✅ one command writes the contract and the client in their canonical form
blendsdk api generate --config blendsdk.api.ts
git add api.json src/api-client
```

**Why:** `blendsdk api check` rebuilds the document and compares it against the committed file after Prettier normalization (LF endings, stable key order, trailing newline). `toJSON()`/`toFile()` do not run that formatter — the missing trailing newline alone is enough to report drift — so a contract written that way fails `check` even though it is semantically identical. Hand edits to `api.json` drift for the same reason.

---

### Keep controller `routes()` side-effect free

**❌ Wrong**

```typescript fragment
import type { RouteDefinition } from 'blendsdk/webafx';

// ❌ routes() reads runtime state while the contract is being generated
routes(): RouteDefinition[] {
  if (!this.services.features.isEnabled('catalog')) {
    return [];
  }
  return [
    {
      method: 'get',
      path: '/',
      handler: () => this.services.catalog.list(),
      openapi: { operationId: 'listProducts' },
    },
  ];
}
```

**✅ Correct**

```typescript fragment
import type { RouteDefinition } from 'blendsdk/webafx';

// ✅ routes() only describes routes; the handler runs later, with real services
routes(): RouteDefinition[] {
  return [
    {
      method: 'get',
      path: '/',
      handler: () => this.services.catalog.list(),
      openapi: {
        operationId: 'listProducts',
        tags: ['products'],
        responses: [{ statusCode: 200, description: 'Products' }],
      },
    },
  ];
}
```

**Why:** `addController` instantiates the controller with `new ControllerClass({}, {})`, because `routes()` is only expected to build `RouteDefinition` objects. A feature-flag read, a database call, or configuration access either throws during generation or silently captures an empty object — making the committed contract depend on generation-time state.

---

### Author configuration with `defineApiContract` and `defineMigrationConfig`

**❌ Wrong**

```typescript fragment
// blendsdk.api.ts — no helper: key typos surface only when the loader runs
export default {
  outputDir: 'src/api-client',
  controllers: [{ basePath: '/api/products', controller: ProductsController }],
  openapi: { title: 'Catalog API', version: '1.0.0' },
  generator: { splitByGrup: true },
};
```

**✅ Correct**

```typescript
// blendsdk.api.ts
import { defineApiContract } from 'blendsdk/codegen';
import { ProductsController } from './controllers/products.controller.js';

export default defineApiContract({
  outputDir: 'src/api-client',
  controllers: [{ basePath: '/api/products', controller: ProductsController }],
  openapi: { title: 'Catalog API', version: '1.0.0' },
  generator: { splitByGroup: true },
});
```

```typescript
// blendsdk.migrations.ts
import { defineMigrationConfig } from 'blendsdk/codegen';

export default defineMigrationConfig({
  schema: './src/database/schema.ts',
  migrationsDir: './migrations',
  databaseUrlEnv: 'DATABASE_URL',
});
```

**Why:** the helpers are identity functions with inference only — but they move mistakes to `tsc`. Without them, an unknown top-level key makes the loader fail with a configuration error and exit code `2`; inside `generator`, only `splitByGroup`, `strict`, `clientName`, and `runtimeImport` are accepted at all.

---

### Keep artifact paths inside the configuration directory

**❌ Wrong**

```typescript fragment
export default defineApiContract({
  outputDir: '../generated/api-client', // ❌ escapes the config directory
  contractFile: '../../api.json',       // ❌ escapes too
  // ...
});
```

**✅ Correct**

```typescript fragment
export default defineApiContract({
  outputDir: './src/api-client',
  contractFile: './api.json', // the default
  // ...
});
```

**Why:** relative artifact paths are resolved against the configuration file and must not escape it or point at a filesystem root; the loader rejects both with a configuration error (exit `2`). Absolute paths are accepted because the config file is developer-authored, not untrusted input — but project-relative paths keep a checkout portable across machines and CI runners.

---

### Never edit an applied migration or the canonical snapshot

**❌ Wrong**

```bash
# "Harmless" cleanup of a migration that is already applied
sed -i 's/ADD COLUMN/ADD COLUMN IF NOT EXISTS/' migrations/20260827120000_add-status.up.sql
blendsdk migrate up
```

**✅ Correct**

```bash
# Restore the exact committed bytes, then re-check history
git checkout -- migrations/20260827120000_add-status.up.sql
git checkout -- migrations/schema.snapshot.json   # only if it was touched
blendsdk migrate status
```

**Why:** every migration pair is checksummed from its exact bytes (up and down separately), and the snapshot is validated for canonical JSON form, LF endings, and no BOM. Any edit makes `validate`, `status`, and `up` report `INVALID_HISTORY` *before* SQL executes; the fix is always to restore the committed bytes or generate a new migration.

---

### Use rename hints for renames

**❌ Wrong**

```typescript fragment
// ❌ without a hint, a removed table plus a same-shape added table is `ambiguous`
await generateMigration({ name: 'rename-customer-to-account' });
// generation stops: "Provide one explicit table rename hint."
```

**✅ Correct**

```typescript
import { generateMigration } from 'blendsdk/codegen';

const result = await generateMigration({
  name: 'rename-customer-to-account',
  renameHints: [{ kind: 'table', from: 'public.customer', to: 'public.account' }],
});

if (result.status === 'GENERATED') {
  console.log(`Wrote ${result.migration?.id} (${result.changes.length} change(s))`);
}
```

**Why:** the differ cannot safely infer a rename from a drop plus an add, so it emits `table.rename` classified `ambiguous` and refuses to render it. Force-approving that as destructive would drop the table and its data. Hints are validated to be one-to-one, acyclic, same-schema, and to map a removed identity to an added one. The CLI equivalents are `--rename-table prior.schema=desired.schema` and `--rename-column prior.table.column=desired.table.column`.

---

### Stage changes the differ classifies as `caution` or `unsupported`

**❌ Wrong**

```typescript fragment
// schema.ts — ❌ one-step required column on a populated table: classified `caution`, no SQL rendered
account.text('status');
```

**✅ Correct**

```typescript fragment
// schema.ts — ✅ stage 1: ship the column as nullable so the diff renders safe SQL
account.text('status').nullable();
```

```bash
blendsdk migrate generate add-status-nullable
# (deploy, backfill existing rows, verify)

# ✅ stage 2: SET NOT NULL is never generated automatically — author it by hand
blendsdk migrate create require-account-status
```

**Why:** the renderer only emits SQL it can prove safe. A required column addition is `caution` ("use a staged population strategy"); `SET NOT NULL` on existing data is `caution`; type changes, generated-column changes, and identity changes are `unsupported` and need a reviewed manual migration with an explicit `USING` expression. None of these are bypassed by destructive approval — they must be staged or written by hand.

---

### Approve destructive changes only after review

**❌ Wrong**

```typescript fragment
// ❌ approve first, read later — removal statements are generated without anyone reviewing the change list
await generateMigration({ name: 'cleanup', allowDestructive: true });
```

**✅ Correct**

```bash
# The first run stops at the destructive change and classifies it
blendsdk migrate generate cleanup
# → MigrationError (exit 1): the removal requires explicit approval

# Review the schema diff, then approve in the same commit and read the generated SQL
blendsdk migrate generate cleanup --allow-destructive
```

**Why:** approval relaxes exactly one safety class — targeted removals (table, column, constraint, index, view, schema, extension drops). `ambiguous`, `caution`, and `unsupported` changes still fail. Each emitted destructive statement carries a `-- destructive: reviewed and explicitly allowed` banner so reviewers can find them in the diff.

---

### Run migrations as one dedicated deploy step

**❌ Wrong**

```typescript fragment
// ❌ every application instance migrates itself on boot
await runMigrations({ command: 'up' });
```

**✅ Correct**

```typescript
import { runMigrations } from 'blendsdk/codegen';

// Deploy job, single process, before the new version serves traffic.
const plan = await runMigrations({ command: 'up', dryRun: true });
console.log(plan.status, plan.migrations.map(migration => migration.id).join(', '));

const applied = await runMigrations({ command: 'up' });
console.log(applied.status);
```

**Why:** `runMigrations` serializes on a database-scoped advisory lock. Competing sessions wait for `lockTimeoutMs` (default `5000` ms) and then fail with `LOCKED`, so N booting replicas race and the losers can fail health checks. `dryRun` acquires the lock, proves pending order, and returns without creating the ledger or executing SQL.

---

### Stop on `UNKNOWN_OUTCOME`; never clean the ledger by hand

**❌ Wrong**

```bash
# ❌ "unblock" an uncertain migration by deleting its ledger row
psql "$DATABASE_URL" -c "DELETE FROM public.blendsdk_migrations WHERE state = 'NONTRANSACTIONAL_DIRTY';"
```

**✅ Correct**

```typescript
import { getMigrationStatus } from 'blendsdk/codegen';

const { status } = await getMigrationStatus();
if (status !== 'UP_TO_DATE' && status !== 'PENDING') {
  throw new Error(`Migration history needs attention: ${status}`);
}
```

**Why:** a nontransactional migration writes a `NONTRANSACTIONAL_DIRTY` row before its SQL is dispatched and only promotes it to `APPLIED` after confirmed success. While the final row is dirty, every `up`/`down` refuses with `UNKNOWN_OUTCOME`. Deleting or rewriting the row erases the only durable record of that fact and can make the next run re-execute DDL. The ledger's shape is also verified down to its primary key and three check constraints — a hand-modified table fails closed as `INVALID_HISTORY`.

---

### Map the PostgreSQL types the introspector leaves unmapped

**❌ Wrong**

```typescript fragment
// ❌ json, jsonb, bytea, interval and range/geometry columns are intentionally unmapped:
// each becomes an `any` placeholder with a @deprecated note, and a warning is logged
await introspector.introspect(schema);
```

**✅ Correct**

```typescript fragment
import type { ColumnMapper } from 'blendsdk/codegen';

// ✅ map what your generated types need; return undefined for the built-in mapping.
// JsonDocument is a named root object built earlier in the same SchemaContainer.
const mapper: ColumnMapper = (column, scope) => {
  if (column.pg_type === 'jsonb') {
    return scope.ref(JsonDocument);
  }
  if (column.pg_type === 'bytea' || column.pg_type === 'interval') {
    return scope.string();
  }
  return undefined;
};

await introspector.introspect(schema, mapper);
```

**Why:** the built-in mapper covers the portable PostgreSQL types only. Everything it cannot represent becomes an `any` placeholder marked `@deprecated`, which defeats strict mode in the generated types. Map those columns explicitly, and watch the introspection warnings to find any you missed.

---

### Keep hand-written files out of the generated output directory

**❌ Wrong**

```bash
# ❌ copying a generated file keeps the marker, so the pruner will delete it once it is stale
cp src/api-client/client.ts src/api-client/legacy-client.ts
```

**✅ Correct**

```bash
# ✅ keep hand-written modules outside the generated output directory
mkdir -p src/api-support
mv src/api-client/legacy-client.ts src/api-support/legacy-client.ts
```

**Why:** `generateClient` prunes every marker-bearing file it no longer generates, but a hand-written file that collides with a generated name (`client.ts`, `types.ts`, `index.ts`) is simply overwritten. Files without the marker and without name collisions are left untouched — the reliable rule is to keep hand-written modules in their own directory.

---

### Pass `--config` explicitly in automation

**❌ Wrong**

```bash
# ❌ discovery depends on the working directory and searches parent directories
blendsdk migrate validate
```

**✅ Correct**

```bash
blendsdk migrate validate --offline --config packages/app/blendsdk.migrations.ts
```

**Why:** the migration config loader searches parent directories all the way to the filesystem root for `blendsdk.migrations.ts`, so a job that runs from the wrong directory can validate — or generate against — the wrong project. `--offline` additionally keeps history-only validation free of the `pg` driver and any database URL.

---

### Point `runtimeImport` at the complete runtime surface

**❌ Wrong**

```typescript fragment
await generateClient(document, {
  outputDir: 'src/api-client',
  runtimeImport: './runtime.js', // ❌ missing exports that generated files import
});
```

**✅ Correct**

```typescript fragment
await generateClient(document, {
  outputDir: 'src/api-client',
  runtimeImport: 'blendsdk/api-client', // the default; provides the full surface
});
```

**Why:** generated files import `createApiClient`, `ApiClientOptions`, `OperationDescriptor`, and `RequestOptions` from the configured specifier — plus `PaginatedResponse` when any operation uses the `body` envelope and `RuntimeClient` in `splitByGroup` mode. A module that does not export all of those names makes the generated client fail to compile; only override the default when you own such a module.

## Anti-Patterns

- **Hand-editing anything generated.** The client, `api.json`, `schema.snapshot.json`, and applied migrations are all validated outputs. Edits are overwritten by the next generation (marker-bearing files) and reported as drift or `INVALID_HISTORY` everywhere else. *Instead:* change the model or the config, then regenerate.

- **Treating `PostgreSQLSchemaGenerator` output as your migration path.** `PostgreSQLSchemaGenerator` renders re-runnable bootstrap DDL — `generateGrouped()` even emits `DROP ... IF EXISTS` sections when `dropBeforeCreate` is on — and records no history, checksum, or snapshot. It is for initializing throwaway databases. Deployed databases get `generateBaseline` / `generateMigration` and `runMigrations`.

- **Using `blendsdk migrate create` for modeled changes.** Manual templates carry `none` snapshot lineage and never advance `schema.snapshot.json`, so the next `generate` re-emits the same change on top of the manual SQL — duplicate DDL. *Instead:* `generate` for anything the schema module models; `create` only for backfills and procedural work.

- **Hand-authoring a project's first migration and snapshot.** The five-line header order, LF-only canonical JSON, exact-byte checksums, and lineage hashes are validated strictly; a hand-written pair fails validation immediately. *Instead:* `blendsdk migrate baseline <name>`.

- **Ignoring `result.issues`.** `generateClient` warns instead of failing for recoverable contract problems (missing `operationId`, unknown result types, reserved names). If you never read `issues`, the first signal is a red `check` in CI. *Instead:* fail your build on `checkClient` / `blendsdk api check`, and treat `generate`'s warnings as the same problems one step earlier.

- **Expecting `DatabaseSchema` to be an ORM.** It models desired state — tables, columns, constraints, indexes, views — and nothing more. There is no query surface, and it does not read or write rows. Runtime data access belongs to your database layer.

- **Naming nested object properties.** Call `.named()` on a nested property and generation throws *"Object properties cannot be named explicitly."* *Instead:* declare a separate root type and reference it with `.ref()`.

- **Looking for a `--force`, `--fake`, or `--repair` flag.** The migration CLI deliberately has none. History problems are resolved by restoring artifacts or recovering forward under review — never by marking rows applied.

- **Flipping generator options without regenerating.** Switching `splitByGroup`, `clientName`, or `runtimeImport` changes the expected file set; until you run `generate` (which also prunes stale group files), `check` reports the file-set difference as drift. Make the option change and the regenerated artifacts one commit.

- **Using `blendsdk migrate down` as the production rollback plan.** `down` reverts exactly the newest applied migration, requires `--allow-down`, and exists for development workflows. Production uses forward recovery.

## Performance Tips

- **Gate with `check` / `validate --offline`, not with `generate`.** `checkClient` rebuilds the client fully in memory — no writes, no pruning — so a CI gate costs one generation pass and zero filesystem churn. `validateMigrations({ offline: true })` validates files and lineage without importing `pg` or requiring `DATABASE_URL`, skipping pool creation entirely.

- **Batch authored shapes into one generation call.** `Generator.generate(container)` walks the whole container, resets render state, and formats the complete document in a single Prettier pass. Ten small containers cost ten registry walks and ten formatter invocations; one container with ten named roots costs one.

- **Split large API clients by group.** With `splitByGroup: true`, output is deterministic per tag, so an unchanged group's file stays byte-identical between runs and only the touched group appears in diffs. There are more (and smaller) files to format and write — a worthwhile trade once a contract has more than a handful of tag groups.

- **Watch the migration lock window.** The advisory lock is held for the entire run, and waiting sessions give up after `lockTimeoutMs` (default `5000` ms, max `300000`). Keep each migration short; if a statement legitimately needs longer (large index builds, backfills), split it or raise `statementTimeoutMs` (default `900000` ms, max `86400000`) as a reviewed configuration change.

- **Pre-flight with `dryRun` and `status`.** `runMigrations({ command: 'up', dryRun: true })` reports pending order without creating the ledger or running SQL. `getMigrationStatus()` takes the lock only briefly — it acquires, releases, and reports `LOCKED` if someone else holds it. Both are cheap enough to run before every deploy attempt.

- **Introspect once and commit the generated types.** `PostgreSQLIntrospector.introspect` issues one large multi-part catalog query (tables, composites, enums, and domains in a single `UNION ALL` statement). Running it on every build adds a database dependency and latency to a job that otherwise needs none — generate once, commit the output, and re-run only when the catalog changes.

## Security Considerations

- **Credentials live in the environment, never in the config file.** `MigrationConfig` intentionally exposes `databaseUrlEnv` — the *name* of an environment variable — instead of a connection URL, so `ResolvedMigrationConfig` contains no secret and is safe to log or serialize. `MigrationError` redacts complete `postgresql://` URLs (including query-string credentials and certificate paths) and `password=`/`secret=`/`token=` assignments at construction time; render failures with `formatMigrationError` rather than printing raw provider errors or SQL bodies.

- **Configuration and schema modules are executable code.** Both loaders evaluate `blendsdk.api.ts` / `blendsdk.migrations.ts` (and, for schema-aware commands, the schema module) through `jiti` with caches disabled — exactly as your application would run them. Run generation only on trusted checkouts, and understand that a CI job invoking `blendsdk migrate generate` executes repository code with that job's credentials in scope.

- **Treat artifact paths as trusted developer input.** Relative paths must stay inside the configuration directory; the loaders reject `..` traversal, filesystem roots, and symlinked path segments. Absolute paths bypass the traversal check because the file is developer-authored — never derive configuration values from untrusted input such as request data or user-supplied names.

- **Run migrations with a dedicated deployment role.** The runner creates and strictly validates `public.blendsdk_migrations` and executes your DDL with the connecting role. The application runtime role should not need DDL privileges. An incompatible ledger table fails closed as `INVALID_HISTORY` rather than being silently altered.

- **Treat `adoptBaseline` as a deliberate, one-time, audited operation.** It requires the exact `<database>/<baseline-id>` confirmation token after DDL has been quiesced, repeats the catalog comparison inside the ledger transaction, and refuses on any structural difference, unprovable SQL, or unmanaged object your model depends on. It records line age *without* executing the baseline SQL, so misuse marks unverified state as applied. The preview output (`TARGET user@host:port/database` plus itemized classifications) is sanitized and safe for a change ticket.

- **Never repair history by hand.** Editing an applied migration, rewriting the snapshot, or deleting/altering ledger rows defeats the checksum and lineage guarantees the whole system rests on. The only supported recovery is forward recovery under review.

- **Generated identifiers are sanitized — don't undo it.** The naming layer converts tags and `operationId`s into valid identifiers, escapes reserved words, and neutralizes injection attempts from contract text (hostile names become harmless escaped strings, never statements). Don't post-process generated files to rewrite identifiers. And when generating from a third-party OpenAPI document, treat the output as code shaped by untrusted text: review the generated diff before committing.

# codegen Testing Patterns

This document explains how to test code that uses `blendsdk/codegen`: your schema models, generator wrappers, API contracts, and migration workflows. The patterns mirror the package's own suite, which is the source of truth for behavior.

The suite is organized into four kinds of files. Adopting the same split makes it obvious what a failure means:

| File suffix | What it pins |
| --- | --- |
| `*.spec.test.ts` | Required public behaviour, described from the outside |
| `*.impl.test.ts` | Internal rules that may change with the implementation |
| `*.integration.test.ts` | The packaged executable and public API end to end |
| `*.compile-spec.ts` | Compile-only checks that the public types remain usable |

Testing codegen code falls into three tiers, each with a different cost:

1. **Pure, in-memory tests.** Schema models and every generator except the client generator are synchronous or promise-based and stateless. Assert on the rendered TypeScript/SQL/JSON text.
2. **Filesystem tests.** `generateClient`, `checkClient`, `generateMigration`, and `generateBaseline` read and write real files. Use isolated temporary directories; never mock the filesystem.
3. **Database tests.** `runMigrations`, `getMigrationStatus`, `validateMigrations`, `adoptBaseline`, and `PostgreSQLIntrospector` require a live PostgreSQL server. The package's suite starts one with Docker Compose.

> **Import rule for consumer tests**: import only from the public entry point `blendsdk/codegen`. The package's internal tests import from `src/` paths because they live inside the package; every example here imports public symbols only.

## Test Setup

### Test Framework Configuration

The package scripts define the canonical run:

| Script | Command | Purpose |
| --- | --- | --- |
| `test:fast` | `vitest run --reporter=verbose --no-file-parallelism --testTimeout=30000` | Single-process verbose run |
| `test:watch` | `vitest watch --reporter=verbose` | Watch mode |
| `test:coverage` | `vitest run --coverage` | Coverage via `@vitest/coverage-v8` |
| `db:up` | `docker-compose -p codegen -f ./docker/docker-compose${MODE}.yml up -d && sleep 5` | Starts the `postgres-test` service (the `${MODE}` suffix selects an optional overlay) |
| `db:down` | `docker-compose -p codegen -f ./docker/docker-compose${MODE}.yml down -v --remove-orphans` | Stops the stack and removes its volume |
| `db:logs` | `docker-compose -p codegen -f ./docker/docker-compose${MODE}.yml logs postgres-test` | Follows the database log |
| `test` | `pnpm run db:down && pnpm run db:up && pnpm run test:fast && pnpm run db:down` | Full lifecycle: fresh database, fast suite, teardown |

Mirror the run flags in a Vitest config so editor and CI runs behave the same:

```typescript
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    include: ['tests/**/*.test.ts'],
    testTimeout: 30_000,
    fileParallelism: false,
    coverage: { provider: 'v8' },
  },
});
```

`fileParallelism: false` is required for the database suites: they share one PostgreSQL server, one advisory lock namespace, and per-test environment variables, so files must not run in parallel. Within a file, mark database suites `describe.sequential`.

### Required Imports

Every test file starts from the framework and (when it touches artifacts) the filesystem:

```typescript
import { afterAll, afterEach, beforeAll, describe, expect, test } from 'vitest';
import { appendFile, mkdir, mkdtemp, readFile, readdir, rm, writeFile } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
```

Package symbols come from the public entry point. The most frequently used ones are:

```typescript
import {
  ClientGenerationError,
```

### Fixture Projects for Offline Migration Commands

`generateMigration` and `generateBaseline` load a `blendsdk.migrations.ts` configuration, which loads a schema module. Configuration files are plain objects (`export default { ... }`) so they load from anywhere, but the **schema module imports `blendsdk/codegen`**, so it must live somewhere module resolution finds your `node_modules`. Keep fixture projects inside the test directory:

```typescript
/** Fixture roots live inside the test directory so package imports resolve from the fixture modules. */
const fixtureRoot = join(import.meta.dirname, '.fixtures');

/** Isolated artifact project for the offline migration commands. */
export interface FixtureProject {
  readonly projectDirectory: string;
  readonly schemaPath: string;
  readonly configPath: string;
  readonly migrationsDir: string;
}

/** Writes the schema module a migration configuration loads. */
export async function writeSchema(project: FixtureProject, body: string): Promise<void> {
  await writeFile(
    project.schemaPath,
    `import { DatabaseSchema } from 'blendsdk/codegen';\n${body}\n`,
    'utf8'
  );
}

/** Creates one isolated project with a schema module and a migration configuration. */
export async function createFixtureProject(schemaBody: string): Promise<FixtureProject> {
  await mkdir(fixtureRoot, { recursive: true });
  const projectDirectory = await mkdtemp(join(fixtureRoot, 'project-'));
  temporaryDirectories.push(projectDirectory);
  const migrationsDir = join(projectDirectory, 'migrations');

  const project: FixtureProject = {
    projectDirectory,
    schemaPath: join(projectDirectory, 'schema.ts'),
    configPath: join(projectDirectory, 'blendsdk.migrations.ts'),
    migrationsDir,
```

### PostgreSQL Bootstrap DDL

`PostgreSQLSchemaGenerator` is synchronous. Assert on the grouped output (`schema`, `indexes`, `views`, `all`) and on statement ordering with `indexOf`:

```typescript
import { describe, expect, test } from 'vitest';
import { DatabaseSchema, PostgreSQLSchemaGenerator } from 'blendsdk/codegen';

describe('bootstrap DDL', () => {
  test('separates schema, index, and view groups and skips drops on request', () => {
    const database = new DatabaseSchema('app');
    database.extension('uuid-ossp');
    const customer = database.table('customer');
    customer.bigint('id').primaryKey();
    customer.text('email').nullable();
    customer.index().indexName('customer_email_idx').column('email');
    database.view('customer_view').as('SELECT "id" FROM public.customer');

    const generator = new PostgreSQLSchemaGenerator(database);
    const generated = generator.generateGrouped({ dropBeforeCreate: false });

    expect(generated.schema).toContain('CREATE TABLE public.customer (');
    expect(generated.schema).toContain('ADD CONSTRAINT customer_id_pkey PRIMARY KEY (id)');
    expect(generated.schema).not.toContain('DROP TABLE');
    expect(generated.indexes).toContain(
      'CREATE INDEX customer_email_idx ON public.customer (email);'
    );
    expect(generated.views).toContain('CREATE OR REPLACE VIEW public.customer_view AS');
    expect(generated.all).toBe(
      [generated.schema, generated.indexes, generated.views].filter(part => part.length > 0).join('\n')
    );

    // Extensions are created before tables.
    expect(generated.schema.indexOf('CREATE EXTENSION')).toBeLessThan(
```

### API Client Generation

`generateClient` writes `types.ts`, `client.ts`, and `index.ts` into a temporary directory; `checkClient` regenerates in memory and compares. The stable generated marker is not exported, so declare it locally:

```typescript
import { afterEach, describe, expect, test } from 'vitest';
import { appendFile, readFile, rm, writeFile } from 'node:fs/promises';
import { checkClient, generateClient } from 'blendsdk/codegen';
import type { OpenAPIDocument } from 'blendsdk/codegen';
import { cleanupTestArtifacts, sampleDocument, temporaryDirectory } from './test-support.js';

/** The stable marker every generated file must start with. */
const GENERATED_MARKER = '// Generated by `blendsdk api generate` — do not edit by hand.';

afterEach(cleanupTestArtifacts);

describe('client generation', () => {
  test('writes marker-bearing files and is byte-identical when re-run', async () => {
    const directory = await temporaryDirectory();

    await generateClient(sampleDocument(), { outputDir: directory });
    const first = await readFile(join(directory, 'client.ts'), 'utf8');

    const result = await generateClient(sampleDocument(), { outputDir: directory });

    expect(result.files).toEqual(['client.ts', 'index.ts', 'types.ts']);
    expect(first.startsWith(GENERATED_MARKER)).toBe(true);
    expect(await readFile(join(directory, 'client.ts'), 'utf8')).toBe(first);
  });

  test('is independent of input declaration order', async () => {
    const first = await temporaryDirectory();
    const second = await temporaryDirectory();
    const doc = sampleDocument();
    const reversed: OpenAPIDocument = {
      ...doc,
      paths: Object.fromEntries(Object.entries(doc.paths).reverse()),
    };

    await generateClient(doc, { outputDir: first });
    await generateClient(reversed, { outputDir: second });

    expect(await readFile(join(first, 'client.ts'), 'utf8')).toBe(
      await readFile(join(second, 'client.ts'), 'utf8')
    );
    expect(await readFile(join(first, 'types.ts'), 'utf8')).toBe(
      await readFile(join(second, 'types.ts'), 'utf8')
    );
  });

  test('prunes stale generated files but leaves hand-written files alone', async () => {
    const directory = await temporaryDirectory();
    await writeFile(join(directory, 'hand-written.ts'), 'export const keep = true;\n');

    await generateClient(sampleDocument(), { outputDir: directory, splitByGroup: true });
    expect(await readFile(join(directory, 'client.products.ts'), 'utf8')).toContain('ProductsClient');

    await generateClient(
      {
        openapi: '3.1.0',
        info: { title: 'Test API', version: '1.0.0' },
        paths: sampleDocument().paths,
      },
      { outputDir: directory, splitByGroup: true }
    );
    expect(await readFile(join(directory, 'hand-written.ts'), 'utf8')).toBe(
      'export const keep = true;\n'
    );
  });

  test('reports drift when a committed file is modified', async () => {
    const directory = await temporaryDirectory();
    const doc = sampleDocument();
    await generateClient(doc, { outputDir: directory });
    await appendFile(join(directory, 'client.ts'), '\n// hand edit\n');

    const result = await checkClient(doc, { outputDir: directory });

    expect(result.drifted).toBe(true);
    expect(result.driftedFiles).toContain('client.ts');
  });
});
```

### Serializing Database Tests

Database tests mutate shared resources — the admin server, the fixed advisory lock namespace, and environment variables. Always:

- mark the suite `describe.sequential(...)`,
- run Vitest with `fileParallelism: false` (see the config above),
- create one database per test and drop it in an `afterEach` cleanup,
- set the connection URL through a **per-test environment variable** so configuration files never contain credentials.

### Shared Database Test Support

This support module mirrors the package's `runner.test-support.ts`. It is self-contained: it owns an admin pool, isolated databases, fixture projects, and cleanup ordering.

```typescript
/**
 * Database-backed test support for migration runner and baseline adoption tests.
 *
 * @module tests/runner.test-support
 */
import { createHash, randomUUID } from 'node:crypto';
import { mkdir, mkdtemp, rm, writeFile } from 'node:fs/promises';
import { join } from 'node:path';
import { Pool } from 'pg';

/** Fixed qualified name of the runner-owned migration ledger. */
export const ledgerName = 'public.blendsdk_migrations';

/** Admin connection to the compose PostgreSQL server started by `pnpm run db:up`. */
const adminUrl =
  process.env.CODEGEN_TEST_ADMIN_URL ??
  'postgresql://postgres:postgres@127.0.0.1:5597/postgres';

/** Fixture roots live inside the test directory so fixture modules resolve package imports. */
const fixtureRoot = join(import.meta.dirname, '.fixtures');

const temporaryDirectories: string[] = [];
const databaseNames: string[] = [];
const databaseUrlEnvironments: string[] = [];
const createdPools: Pool[] = [];
let adminPool: Pool | undefined;

/** Isolated database and local artifact paths owned by one test. */
export interface TestProject {
  readonly databaseUrl: string;
  readonly databaseUrlEnvironment: string;
  readonly configPath: string;
  readonly migrationsDir: string;
  readonly pool: Pool;
}

/** Optional fixture configuration for database-backed projects. */
export interface TestProjectOptions {
  readonly lockTimeoutMs?: number;
  readonly statementTimeoutMs?: number;
  /** Schema module body for generation commands; the import is prepended. */
  readonly schema?: string;
}

/** Opens the administrative pool used only to create and drop test databases. */
export function setupRunnerTests(): void {
  adminPool = new Pool({ connectionString: adminUrl, max: 2 });
}

/** Creates one isolated PostgreSQL database and one local migration project. */
export async function createTestProject(options: TestProjectOptions = {}): Promise<TestProject> {
  if (!adminPool) throw new Error('Runner test support has not been initialized.');
  const databaseName = `codegen_test_${randomUUID().replaceAll('-', '')}`;
  const databaseUrlEnvironment = `CODEGEN_TEST_${databaseName.toUpperCase()}_URL`;
  await adminPool.query(`CREATE DATABASE "${databaseName}"`);
  databaseNames.push(databaseName);

  await mkdir(fixtureRoot, { recursive: true });
  const projectDirectory = await mkdtemp(join(fixtureRoot, 'project-'));
  temporaryDirectories.push(projectDirectory);
  const migrationsDir = join(projectDirectory, 'migrations');
  await mkdir(migrationsDir);

  if (options.schema !== undefined) {
    await writeFile(
      join(projectDirectory, 'schema.ts'),
      `import { DatabaseSchema } from 'blendsdk/codegen';\n${options.schema}\n`,
      'utf8'
    );
  }

  const configPath = join(projectDirectory, 'blendsdk.migrations.ts');
  await writeFile(
    configPath,
    `export default ${JSON.stringify({
      ...(options.schema !== undefined ? { schema: './schema.ts' } : {}),
      databaseUrlEnv: databaseUrlEnvironment,
      lockTimeoutMs: options.lockTimeoutMs ?? 500,
      statementTimeoutMs: options.statementTimeoutMs ?? 30_000,
    })};\n`,
    'utf8'
  );

  const databaseUrl = `postgresql://postgres:postgres@127.0.0.1:5597/${databaseName}`;
  process.env[databaseUrlEnvironment] = databaseUrl;
  databaseUrlEnvironments.push(databaseUrlEnvironment);
  const pool = new Pool({ connectionString: databaseUrl, max: 4 });
  createdPools.push(pool);
  return { databaseUrl, databaseUrlEnvironment, configPath, migrationsDir, pool };
}

/** Exact-byte metadata for one written migration fixture. */
export interface MigrationFixture {
  readonly id: string;
  readonly path: string;
  readonly checksum: string;
}

/** Renders and writes one valid immutable migration pair. */
export async function writeMigration(
  project: TestProject,
  id: string,
  body: string,
  options: {
    readonly transactional?: boolean;
    readonly fromSnapshot?: string;
    readonly toSnapshot?: string;
    readonly downBody?: string;
  } = {}
): Promise<MigrationFixture> {
  const upPath = join(project.migrationsDir, `${id}.up.sql`);
  const upBytes = Buffer.from(migrationSql(id, body, options));
  await writeFile(upPath, upBytes);
  if (options.downBody !== undefined) {
    await writeFile(
      join(project.migrationsDir, `${id}.down.sql`),
      migrationSql(id, options.downBody, {
        transactional: options.transactional,
        fromSnapshot: options.toSnapshot,
        toSnapshot: options.fromSnapshot,
      }),
      'utf8'
    );
  }
  return { id, path: upPath, checksum: createHash('sha256').update(upBytes).digest('hex') };
}

/** Reports whether the runner-owned ledger currently exists. */
export async function ledgerExists(project: TestProject): Promise<boolean> {
  const result = await project.pool.query<{ exists: boolean }>(
    `SELECT to_regclass('public.blendsdk_migrations') IS NOT NULL AS exists`
  );
  return result.rows[0]?.exists === true;
}

/** Returns stable ledger state without client-side bigint coercion. */
export async function ledgerRows(project: TestProject): Promise<
  ReadonlyArray<{
    readonly id: string;
    readonly checksum: string;
    readonly from_snapshot: string | null;
    readonly to_snapshot: string | null;
    readonly state: string;
    readonly applied: boolean;
    readonly execution_ms: string | null;
  }>
> {
  const result = await project.pool.query<{
    id: string;
    checksum: string;
    from_snapshot: string | null;
    to_snapshot: string | null;
    state: string;
    applied: boolean;
    execution_ms: string | null;
  }>(`
    SELECT id, checksum, from_snapshot, to_snapshot, state,
           applied_at IS NOT NULL AS applied, execution_ms::text
    FROM ${ledgerName}
    ORDER BY id
  `);
  return result.rows;
}

/** Removes all pools, files, environment values, and databases owned by the current test. */
export async function cleanupRunnerTest(): Promise<void> {
  if (!adminPool) return;
  for (const environmentName of databaseUrlEnvironments.splice(0)) {
    delete process.env[environmentName];
  }
  for (const pool of createdPools.splice(0)) {
    await pool.end().catch(() => undefined);
  }
  await Promise.all(
    temporaryDirectories.splice(0).map(directory => rm(directory, { recursive: true, force: true }))
  );
  for (const databaseName of databaseNames.splice(0).reverse()) {
    await adminPool.query(
      `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = $1`,
      [databaseName]
    );
    await adminPool.query(`DROP DATABASE IF EXISTS "${databaseName}"`);
  }
}

/** Closes the administrative pool after the suite owns no databases. */
export async function teardownRunnerTests(): Promise<void> {
  await adminPool?.end();
  adminPool = undefined;
}

/** Produces exact version-one SQL bytes with nullable snapshot lineage. */
function migrationSql(
  id: string,
  body: string,
  options: {
    readonly transactional?: boolean;
    readonly fromSnapshot?: string;
    readonly toSnapshot?: string;
  }
): string {
  return [
    '-- blendsdk-migration: 1',
    `-- id: ${id}`,
    `-- transaction: ${options.transactional ?? true}`,
    `-- from-snapshot: ${options.fromSnapshot ?? 'none'}`,
    `-- to-snapshot: ${options.toSnapshot ?? 'none'}`,
    body.trimEnd(),
    '',
  ].join('\n');
}
```

Cleanup ordering matters: environment variables are deleted, pools are ended, fixture directories are removed, and only then are databases terminated and dropped — a database cannot be dropped while a pool still holds a connection to it.

## Mocking & Stubbing

### Prefer Real Instances

Codegen is built so real instances are cheaper than mocks: generators are deterministic, fast, and side-effect-free outside their output directory, and database behaviour is observable through public results. Reach for a mock only when a documented seam exists.

| Instead of mocking… | Do this |
| --- | --- |
| `generateClient` / `checkClient` | Generate into a `temporaryDirectory()`; it takes milliseconds and exercises real Prettier output |
| `generateMigration` / `generateBaseline` | Use a `FixtureProject` or `createTestProject`; pass a fixed `now` instead of mocking `Date` |
| `process.env` | Assign the variable named by `databaseUrlEnv` in the test and delete it in cleanup, or use `vi.stubEnv` / `vi.unstubAllEnvs` |
| `pg` | Use the Docker PostgreSQL. The pool is created internally by the database commands; there is no supported injection point |
| `console.log` | Prefer an output boundary in your own wrapper (below); spy on `console` only for the introspector |

### Output Boundaries Instead of Console Spies

The package's own command entry points take an `{ stdout, stderr }` boundary and return an exit code, so tests never intercept `console`. Apply the same shape to your wrappers around codegen services, then test the wrapper without touching global state:

```typescript
import { checkClient } from 'blendsdk/codegen';
import type { OpenAPIDocument } from 'blendsdk/codegen';

/** Output boundary a command wrapper exposes to its callers and tests. */
export interface CommandIo {
  readonly stdout: (message: string) => void;
  readonly stderr: (message: string) => void;
}

/** Rebuilds the client in memory and reports drift, mirroring `blendsdk api check`. */
export async function runCheck(
  document: OpenAPIDocument,
  outputDir: string,
  io: CommandIo
): Promise<number> {
  const result = await checkClient(document, { outputDir });
  for (const issue of result.issues) {
    if (issue.severity === 'error') {
      io.stderr(`ERROR: ${issue.message}`);
    } else {
      io.stdout(`WARNING: ${issue.message}`);
    }
  }
  if (result.drifted) {
    io.stderr(`DRIFT: ${(result.driftedFiles ?? []).join(', ')}`);
    return 1;
  }
  return 0;
}
```

```typescript
import { afterEach, describe, expect, test } from 'vitest';
import { appendFile } from 'node:fs/promises';
import { join } from 'node:path';
import { generateClient } from 'blendsdk/codegen';
import { cleanupTestArtifacts, sampleDocument, temporaryDirectory } from './test-support.js';
import { runCheck } from './check-command.js';

afterEach(cleanupTestArtifacts);

describe('check command', () => {
  test('reports drift through the output boundary and returns 1', async () => {
    const directory = await temporaryDirectory();
    const doc = sampleDocument();
    await generateClient(doc, { outputDir: directory });
    await appendFile(join(directory, 'types.ts'), '// drift\n');

    const stderr: string[] = [];

      stdout: message => stdout.push(message),

```

### Dependency Seams

Three documented seams let tests run deterministically without mocks:

**Deterministic clock.** `generateMigration` and `generateBaseline` accept `now?: Date`; migration identifiers become stable (`20260827120000_initial`):

```typescript fragment
const result = await generateMigration({
  name: 'initial',
  configPath: project.configPath,
  now: new Date('2026-08-27T12:00:00Z'),
});
```

**Adoption preview hook.** `adoptBaseline` accepts an `afterPreview` callback that receives the sanitized `AdoptionPreview` and may return the required confirmation token. Tests use it to assert the preview and to inject races between preview and the authoritative transaction:

```typescript fragment
await adoptBaseline(
  { configPath: project.configPath },
  {
    afterPreview: preview => {
      expect(preview.baselineId).toBe(baseline.migration.id);
      return `${databaseName}/${baseline.migration.id}`;
    },
  }
);
```

**Cancellation signals.** `runMigrations` accepts an `AbortSignal`. A pre-aborted controller proves the boundary stops before touching SQL; a timer-driven abort proves active SQL is cancelled and rolled back. Both patterns are shown under Migration Execution below.

### Console Output From the Introspector

The introspector is the one place the package writes to `console`: an unmapped PostgreSQL type logs a warning and produces a `@deprecated` placeholder. Spy on `console.log` when you want a quiet, assertable run:

```typescript fragment
const log: ReturnType<typeof vi.spyOn> = vi.spyOn(console, 'log').mockImplementation(() => undefined);
try {
  await introspector.introspect(schema);
} finally {
  log.mockRestore();
}
```

Restore the spy in a `finally` block, or use `afterEach(() => vi.restoreAllMocks())`, so a failing assertion never leaves the global console silenced for other tests.

## Test Patterns by Feature

### Data Shapes and Type Generators

- **Scopes.** `schema.scope('api_v1')` namespaces generated types (`ApiV1UserRequest`); assert both scoped names when you generate from multiple agents' shapes.
- **Enums.** A `PrimitiveSchema.enum(...)` becomes a literal union (`export type Directions = "up" | "down";`); assert the exact union text.
- **Duplicate identity.** `SchemaContainer` rejects a second registration of the same scoped name with an error containing `Schema object already exists`.
- **Invalid models.** Naming a property explicitly is a model error; `generate()` rejects rather than emitting ambiguous types:

```typescript
import { describe, expect, test } from 'vitest';
import { SchemaContainer, TypeGenerator } from 'blendsdk/codegen';

describe('model errors', () => {
  test('rejects a property that was named explicitly', async () => {
    const schema = new SchemaContainer();
    const scope = schema.scope();
    scope.object({ id: scope.string().named('Id') }).named('Product');

    await expect(new TypeGenerator().generate(schema)).rejects.toThrow(/cannot be named/);
  });

  test('rejects a duplicate scoped identity', () => {
    const schema = new SchemaContainer();
    const scope = schema.scope('api');
    scope.string().named('Token');

    expect(() => scope.string().named('Token')).toThrow(/already exists/);
  });
});
```

### PostgreSQL Schema and DDL

- Assert **group separation**: tables, constraints, and comments live in `schema`; indexes in `indexes`; views and their comments in `views`.
- Assert **ordering** with `indexOf` (`CREATE EXTENSION` < `CREATE TABLE` < `ADD CONSTRAINT` < `CREATE INDEX` < `COMMENT ON`).
- Assert **safety choices**: generated DDL never emits `CASCADE` on drops and quotes nothing it does not have to; identifiers are emitted as `public.customer` (unquoted) by the bootstrap generator, while migration SQL quotes them (`"public"."customer"`).

### OpenAPI Generation

- **Path conversion.** Express `:id` becomes OpenAPI `{id}`.
- **Opt-in filtering.** Only routes with `openapi` metadata are collected.
- **Security.** `secure: true` (or a service name) receives `defaultSecurity`; unmarked routes have no `security` key.
- **Envelope.** Every operation records `x-blend-envelope` (`data` by default, `body` for paginated responses).
- **Nullable conversion.** Zod nullability becomes a JSON Schema type array, never the OpenAPI 3.0 `nullable` keyword:

```typescript
import { describe, expect, test } from 'vitest';
import { z } from 'zod';
import { OpenAPIGenerator, convertZodToJsonSchema, convertZodToQueryParameters } from 'blendsdk/codegen';
import type { RouteDefinition } from 'blendsdk/webafx';

/** Builds a minimal route definition; the handler is irrelevant to the document. */
function createRoute(overrides: Partial<RouteDefinition>): RouteDefinition {
  return { method: 'get', path: '/', handler: () => {}, ...overrides } as RouteDefinition;
}

describe('OpenAPI contract fidelity', () => {
  test('applies defaultSecurity only to routes marked secure', () => {
    const generator = new OpenAPIGenerator({
      title: 'Test API',
      version: '1.0.0',
      securitySchemes: { bearerAuth: { type: 'http', scheme: 'bearer', bearerFormat: 'JWT' } },
      defaultSecurity: [{ bearerAuth: [] }],
    });
    generator.addRoutes('/api/products', [
      createRoute({ method: 'get', path: '/', openapi: { summary: 'List' } }),
      createRoute({ method: 'post', path: '/', secure: true, openapi: { summary: 'Create' } }),
    ]);

    const doc = generator.generate();

    expect(doc.paths['/api/products'].get?.security).toBeUndefined();
    expect(doc.paths['/api/products'].post?.security).toEqual([{ bearerAuth: [] }]);
  });

  test('converts nullable fields to type arrays instead of the nullable keyword', () => {
    const schema = convertZodToJsonSchema(z.string().nullable(), 'input');

    expect(schema).toEqual({ type: ['string', 'null'] });
    expect(schema).not.toHaveProperty('nullable');
  });

  test('splits a query object into query parameters', () => {
    const parameters = convertZodToQueryParameters(
      z.object({ page: z.coerce.number().default(1), search: z.string().optional() })
    );

    expect(parameters).toHaveLength(2);
    expect(parameters.find(parameter => parameter.name === 'page')).toMatchObject({
      in: 'query',
      schema: { type: 'number', default: 1 },

  });
```

### Client Generation and the Drift Gate

- **Naming.** A reserved `operationId` gains a trailing underscore and a warning; a hyphenated tag becomes a camelCase group (`product-catalog` → `productCatalog`).
- **Hard failures.** Duplicate `operationId`s throw `ClientGenerationError` naming both operations; the same class reports duplicate resolved group/method pairs.
- **Strict mode.** `strict: true` escalates warning-level problems (missing `operationId` or 2xx schema) to errors, so generation fails:

```typescript
import { afterEach, describe, expect, test } from 'vitest';
import { readFile } from 'node:fs/promises';
import { join } from 'node:path';
import { ClientGenerationError, generateClient } from 'blendsdk/codegen';
import { captureClientError, cleanupTestArtifacts, document, success, temporaryDirectory } from './test-support.js';

afterEach(cleanupTestArtifacts);

describe('client generator issues', () => {
  test('escapes a reserved operationId and warns', async () => {
    const directory = await temporaryDirectory();
    const doc = document({
      '/api/products/{id}': {
        delete: {
          operationId: 'delete',
          tags: ['products'],
          responses: success({ type: 'object' }),
        },
      },
    });

    const result = await generateClient(doc, { outputDir: directory });

    expect(await readFile(join(directory, 'client.ts'), 'utf8')).toMatch(/\bdelete_\b/);
    expect(result.issues.some(issue => issue.severity === 'warning')).toBe(true);
  });

  test('fails when two operations share an operationId', async () => {
    const directory = await temporaryDirectory();
    const doc = document({
      '/api/a': {
        get: { operationId: 'duplicate', tags: ['a'], responses: success({ type: 'object' }) },
      },
      '/api/b': {
        post: { operationId: 'duplicate', tags: ['b'], responses: success({ type: 'object' }) },
      },
    });

    const error = await captureClientError(() => generateClient(doc, { outputDir: directory }));

    expect(error).toBeInstanceOf(ClientGenerationError);
    expect(error.message).toContain('/api/a');
    expect(error.message).toContain('/api/b');
  });

  test('fails in strict mode when an operation has no operationId', async () => {
    const directory = await temporaryDirectory();
    const doc = document({
      '/api/things': {
        get: { tags: ['things'], responses: success({ type: 'object' }) },

  test('checkClient upgrades the same problems to errors', async () => {

    const doc = document({

    const result = await import('blendsdk/codegen').then(module =>
```

### Migration Generation

Migration generation is **offline** — it never opens a database connection. Point it at a fixture project, pass a fixed clock, and assert on the published files:

```typescript
import { afterEach, describe, expect, test } from 'vitest';
import { readFile, readdir } from 'node:fs/promises';
import { generateMigration } from 'blendsdk/codegen';
import type { GenerateMigrationResult, MigrationDescriptor } from 'blendsdk/codegen';
import {
  cleanupTestArtifacts,
  createFixtureProject,
  expectMigrationError,
  writeSchema,
} from './test-support.js';

const CUSTOMER_SCHEMA = `
const schema = new DatabaseSchema('app');
const customer = schema.table('customer');
customer.bigint('id').primaryKey();
customer.text('name').nullable();
export default schema;`;

const FIRST_NOW = new Date('2026-08-27T12:00:00Z');
const LATER_NOW = new Date('2026-08-27T13:00:00Z');

/** Narrows one generation result to its required migration descriptor. */
function migrationOf(result: GenerateMigrationResult): MigrationDescriptor {
  if (!result.migration) throw new Error('Expected a generated migration.');
  return result.migration;
}

afterEach(cleanupTestArtifacts);

describe('offline migration generation', () => {
  test('publishes one migration and the replacement snapshot with exact lineage', async () => {
    const project = await createFixtureProject(CUSTOMER_SCHEMA);

    const first = await generateMigration({
      name: 'initial',
      configPath: project.configPath,
      now: FIRST_NOW,
    });

    expect(first.status).toBe('GENERATED');
    expect(migrationOf(first).id).toBe('20260827120000_initial');
    expect((await readdir(project.migrationsDir)).sort()).toEqual([
      '20260827120000_initial.up.sql',
      'schema.snapshot.json',
    ]);
    const sql = await readFile(migrationOf(first).upPath, 'utf8');
    expect(sql).toContain('-- blendsdk-migration: 1');
    expect(sql).toContain('-- from-snapshot: none');
    expect(sql).toContain(`-- to-snapshot: ${first.desiredSnapshot}`);
    expect(sql).toContain('CREATE TABLE "public"."customer"');
    expect(first.changes).toContainEqual(
      expect.objectContaining({ kind: 'table.add', safety: 'safe' })
    );
  });

  test('reports UP_TO_DATE and writes nothing when the model is unchanged', async () => {
    const project = await createFixtureProject(CUSTOMER_SCHEMA);
    await generateMigration({ name: 'initial', configPath: project.configPath, now: FIRST_NOW });
    const before = (await readdir(project.migrationsDir)).sort();

    const again = await generateMigration({
      name: 'no-change',
      configPath: project.configPath,
      now: LATER_NOW,
    });

    expect(again.status).toBe('UP_TO_DATE');
    expect(again.changes).toEqual([]);
    expect((await readdir(project.migrationsDir)).sort()).toEqual(before);
  });

  test('blocks an apparent rename until a one-to-one hint is supplied', async () => {
    const project = await createFixtureProject(CUSTOMER_SCHEMA);
    await generateMigration({ name: 'initial', configPath: project.configPath, now: FIRST_NOW });
    await writeSchema(
      project,
      CUSTOMER_SCHEMA.replaceAll('customer', 'account')
    );

    const blocked = await expectMigrationError(
      () => generateMigration({ name: 'rename', configPath: project.configPath, now: LATER_NOW }),
      { kind: 'INVALID_HISTORY', exitCode: 1 }
    );
    expect(blocked.message).toContain('rename hint');

    const hinted = await generateMigration({
      name: 'rename',
      configPath: project.configPath,
      now: LATER_NOW,
      renameHints: [{ kind: 'table', from: 'public.customer', to: 'public.account' }],
    });

    expect(hinted.changes).toContainEqual(
      expect.objectContaining({ kind: 'table.rename', safety: 'safe' })
    );
    const sql = await readFile(migrationOf(hinted).upPath, 'utf8');
    expect(sql).toContain('ALTER TABLE "public"."customer" RENAME TO "account";');
    expect(sql).not.toMatch(/DROP TABLE|CREATE TABLE/iu);
  });

  test('requires explicit approval for destructive changes', async () => {
    const project = await createFixtureProject(CUSTOMER_SCHEMA);
    await generateMigration({ name: 'initial', configPath: project.configPath, now: FIRST_NOW });
    await writeSchema(project, CUSTOMER_SCHEMA.replace("customer.text('name').nullable();\n", ''));

    const blocked = await expectMigrationError(
      () => generateMigration({ name: 'drop-name', configPath: project.configPath, now: LATER_NOW }),
      { kind: 'INVALID_HISTORY', exitCode: 1 }
    );
    expect(blocked.message).toContain('approval');

    const approved = await generateMigration({
      name: 'drop-name',
      configPath: project.configPath,
      now: LATER_NOW,
      allowDestructive: true,
    });

    const sql = await readFile(migrationOf(approved).upPath, 'utf8');
    expect(sql).toContain('-- destructive: reviewed and explicitly allowed');
    expect(sql).toContain('ALTER TABLE "public"."customer" DROP COLUMN "name";');
  });
});
```

Notes:

- Migration identifiers are `YYYYMMDDHHMMSS_slug`; slugs must be lowercase (`add-customer-status`) or generation fails with a configuration error.
- A blocked generation writes **nothing** — neither a migration nor a snapshot. Assert the directory listing when this matters.
- The five-line header (`-- blendsdk-migration: 1`, `id`, `transaction`, `from-snapshot`, `to-snapshot`) is the strict file contract; a wrong `id`, a reordered header, a BOM, CRLF, or a missing final LF all fail parsing with `INVALID_HISTORY`.

### Migration Execution

`runMigrations` (and `getMigrationStatus` / `validateMigrations`) report one of five statuses:

| Status | Produced when |
| --- | --- |
| `UP_TO_DATE` | Every local migration is the applied ledger prefix |
| `PENDING` | Local history has files after the exact applied prefix |
| `INVALID_HISTORY` | A checksum, prefix, ordering, row, or ledger-shape violation |
| `LOCKED` | Another session holds the database-scoped advisory lock |
| `UNKNOWN_OUTCOME` | The final ledger row is `NONTRANSACTIONAL_DIRTY` |

Key patterns:

- Use `expectMigrationError` with `{ kind, exitCode }` for every failure path.
- Simulate a competing migration session by taking the fixed lock directly: `pg_advisory_lock(hashtext(current_database()), hashtext('blendsdk:migrations:v1'))`.
- Use `AbortController` for cancellation; combine with `statementTimeoutMs` well above the abort delay.

```typescript
import { afterAll, afterEach, beforeAll, describe, expect, test } from 'vitest';
import { appendFile } from 'node:fs/promises';
import { getMigrationStatus, runMigrations, validateMigrations } from 'blendsdk/codegen';
import { expectMigrationError } from './test-support.js';
import {
  cleanupRunnerTest,
  createTestProject,
  ledgerExists,
  ledgerRows,
  setupRunnerTests,
  teardownRunnerTests,
  writeMigration,
} from './runner.test-support.js';

beforeAll(setupRunnerTests);
afterEach(cleanupRunnerTest);
afterAll(teardownRunnerTests);

describe.sequential('migration runner edge cases', () => {
  test('reports PENDING before up and UP_TO_DATE afterwards', async () => {
    const project = await createTestProject();
    await writeMigration(project, '20260827120100_pending', 'SELECT 1;');

    expect((await getMigrationStatus({ configPath: project.configPath })).status).toBe('PENDING');

    await runMigrations({ command: 'up', configPath: project.configPath });

    expect((await getMigrationStatus({ configPath: project.configPath })).status).toBe('UP_TO_DATE');
    expect(await validateMigrations({ offline: true, configPath: project.configPath })).toEqual({
      status: 'UP_TO_DATE',
      migrations: [],
    });
  });

  test('rejects an edited applied file as INVALID_HISTORY', async () => {
    const project = await createTestProject();
    const migration = await writeMigration(
      project,
      '20260827120100_edit-guard',
      'CREATE TABLE edit_guard (id bigint);'
    );
    await runMigrations({ command: 'up', configPath: project.configPath });
    await appendFile(migration.path, '-- edited after application\n');

    const status = await getMigrationStatus({ configPath: project.configPath });
    expect(status.status).toBe('INVALID_HISTORY');

    const error = await expectMigrationError(
      () => runMigrations({ command: 'up', configPath: project.configPath }),
      { kind: 'INVALID_HISTORY', exitCode: 1 }
    );
    expect(error.message).toMatch(/checksum/iu);
  });

  test('reports LOCKED while another session holds the advisory lock', async () => {
    const project = await createTestProject({ lockTimeoutMs: 50 });
    await writeMigration(project, '20260827120100_locked', 'CREATE TABLE lock_guard (id bigint);');
    const lockClient = await project.pool.connect();
    await lockClient.query(
      `SELECT pg_advisory_lock(hashtext(current_database()), hashtext('blendsdk:migrations:v1'))`
    );

    await expectMigrationError(
      () => runMigrations({ command: 'up', configPath: project.configPath }),
      { kind: 'LOCKED', exitCode: 1 }
    );

    expect(await ledgerExists(project)).toBe(false);
    await lockClient.query(
      `SELECT pg_advisory_unlock(hashtext(current_database()), hashtext('blendsdk:migrations:v1'))`
    );
    lockClient.release();
  });

  test('rolls back an active transaction when the caller aborts', async () => {
    const project = await createTestProject({ statementTimeoutMs: 10_000 });
    await writeMigration(
      project,
      '20260827120100_abort',
      'CREATE TABLE abort_active (id integer); SELECT pg_sleep(5);'
    );
    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), 80);

    await expectMigrationError(
      () =>
        runMigrations({
          command: 'up',
          configPath: project.configPath,
          signal: controller.signal,
        }),
      { kind: 'ABORTED', exitCode: 1 }
    );
    clearTimeout(timer);

    const created = await project.pool.query<{ name: string | null }>(
      `SELECT to_regclass('public.abort_active') AS name`
    );
    expect(created.rows[0]?.name).toBeNull();
  });

  test('retains a durable dirty marker when a nontransactional migration loses its session', async () => {
    const project = await createTestProject();
    await writeMigration(
      project,
      '20260827120100_unknown',
      'SELECT pg_terminate_backend(pg_backend_pid());',
      { transactional: false }
    );

    await expectMigrationError(
      () => runMigrations({ command: 'up', configPath: project.configPath }),
      { kind: 'UNKNOWN_OUTCOME', exitCode: 1 }
    );

    expect(await ledgerRows(project)).toEqual([
      expect.objectContaining({ state: 'NONTRANSACTIONAL_DIRTY', applied: false }),
    ]);
    expect((await getMigrationStatus({ configPath: project.configPath })).status).toBe(
      'UNKNOWN_OUTCOME'
    );
  });
});
```

The `DOWN` path is equally simple to assert: run `down` without `allowDown` and expect `UNSUPPORTED`; with `allowDown: true` and no down file on the latest migration, expect `INVALID_HISTORY`; with one, expect the table to disappear and the ledger row to be removed atomically.

### Baseline and Adoption

`generateBaseline` creates the first immutable lineage offline; `adoptBaseline` proves an existing database matches that baseline structurally and records the ledger row **without executing baseline SQL**. Two helpers make adoption tests readable:

```typescript
/** Returns only executable SQL after the strict five-line migration header. */
function migrationBody(sql: string): string {
  return sql.split('\n').slice(5).join('\n');
}

/** Returns the confirmation token tied to one exact database and baseline identifier. */
function confirmationToken(project: TestProject, baselineId: string): string {
  return `${new URL(project.databaseUrl).pathname.slice(1)}/${baselineId}`;
}
```

```typescript
import { afterAll, afterEach, beforeAll, describe, expect, test } from 'vitest';
import { readFile, readdir } from 'node:fs/promises';
import { adoptBaseline, generateBaseline } from 'blendsdk/codegen';
import type { AdoptionPreview } from 'blendsdk/codegen';
import { expectMigrationError } from './test-support.js';
import {
  cleanupRunnerTest,
  createTestProject,
  ledgerExists,
  ledgerRows,
  setupRunnerTests,
  teardownRunnerTests,
  type TestProject,
} from './runner.test-support.js';

const CUSTOMER_SCHEMA = `
const schema = new DatabaseSchema('app');
const customer = schema.table('customer');
customer.bigint('id').primaryKey();
customer.text('name').nullable();
export default schema;`;

const BASELINE_NOW = new Date('2026-08-27T09:00:00Z');

beforeAll(setupRunnerTests);
afterEach(cleanupRunnerTest);
afterAll(teardownRunnerTests);

describe.sequential('baseline adoption', () => {
  test('creates one offline baseline and adopts an exact existing database', async () => {
    const project = await createTestProject({ schema: CUSTOMER_SCHEMA });

    const baseline = await generateBaseline({

  test('reports a qualified MISSING mismatch without inserting history', async () => {
    const project = await createTestProject({ schema: CUSTOMER_SCHEMA });

    const project = await createTestProject({ schema: CUSTOMER_SCHEMA });
    const baseline = await generateBaseline({

```

Further adoption cases follow the same shape:

- **`DIFFERENT`** — apply the baseline DDL, then alter a column type directly (`ALTER TABLE public.customer ALTER COLUMN name TYPE varchar(40)`); adoption reports `UNSUPPORTED` naming the column.
- **`EXTRA_MODELED`** — create an extra table not present in the model; adoption reports the extra table's qualified identity.
- **Unmanaged objects** — functions and triggers are reported as informational `UNMANAGED` entries and do **not** block adoption (unless desired columns depend on an unmanaged type).
- **Race injection** — mutate the target database inside `afterPreview`; the authoritative transaction repeats the comparison and fails without touching the ledger.
- **Local drift** — rewrite the migration file inside `afterPreview`; adoption fails with `INVALID_HISTORY` and inserts nothing.

### Database Introspection

`PostgreSQLIntrospector` needs a live connection (created through `blendsdk/postgresql`) and works best asserted through the generated types. A `ColumnMapper` can override any column before fallback mapping runs; unmapped PostgreSQL types log a warning and render a `@deprecated` placeholder:

```typescript fragment
// `database` is a PostgreSQLDatabase connection created from your test environment;
// run this against the same Docker PostgreSQL instance the migration suite uses.
const introspector = new PostgreSQLIntrospector(database);
const schema = new SchemaContainer();

// Override specific PostgreSQL types; return undefined to keep the fallback mapping.
await introspector.introspect(schema, (column, scope) =>
  column.pg_type === 'jsonb' ? scope.any().description('JSON payload') : undefined
);

const source = await new TypeGenerator().generate(schema);
expect(source).toContain('JSON payload');
```

```typescript
import { afterAll, afterEach, beforeAll, describe, expect, test } from 'vitest';
```

# codegen Troubleshooting

This document covers the two CLI surfaces (`blendsdk api`, `blendsdk migrate`), the generator services behind them, and the authoring models that feed them. Both CLIs share one exit-code contract, which is the fastest way to classify a failure:

| Exit code | Meaning |
| --- | --- |
| `0` | Success |
| `1` | Operational failure or drift: `api` drift, migration `INVALID_HISTORY` / `LOCKED` / `UNKNOWN_OUTCOME`, or a thrown `MigrationError` with `exitCode 1` |
| `2` | Usage or configuration failure — nothing was executed or written |

Library entry points never call `process.exit`: `main(argv, io)` returns the code, and services throw typed errors that carry `kind` and `exitCode`.

---

## Common Errors

### API contract and the `blendsdk api` CLI

#### `USAGE: Run \`blendsdk api --help\` for the supported commands.` (exit 2)

**Cause** — The arguments did not match `api generate|check [--config <path>]`. Typical shapes: `api` with no action, an unknown option such as `api generate --wat`, `--config` with no value, or a stray positional argument.

**Fix** — Use one of the two supported forms, or print help:

```bash
blendsdk api --help
blendsdk api generate --config ./blendsdk.api.ts
blendsdk api check
```

When embedding, `main(argv, io)` returns `2` and writes the usage line through your `stderr` callback instead of touching `process`.

#### `Could not find blendsdk.api.ts in this project.` / `API configuration was not found at /path/blendsdk.api.ts.` (exit 2)

**Cause** — Discovery found no contract. `--config` is honored first (a file, or a directory to search upward from); otherwise the loader searches upward from the current directory for `blendsdk.api.ts` and stops as soon as it sees a `.git` entry. A configuration planted above the repository root is never loaded, and running from a subdirectory still finds the project root config.

**Fix** — Put the contract at the project root, or pass `--config` explicitly. A minimal, valid contract:

```typescript
// blendsdk.api.ts
import { defineApiContract } from 'blendsdk/codegen';

class ProductsController {
  public routes() {
    return [
      {
        method: 'get',
        path: '/',
        handler: () => undefined,
        openapi: {
          operationId: 'listProducts',
          tags: ['products'],
          responses: [{ statusCode: 200, description: 'OK', schema: {} }],
        },
      },
    ];
  }
}

export default defineApiContract({
  outputDir: 'src/api-client',
  contractFile: 'api.json',
  controllers: [{ basePath: '/api/products', controller: ProductsController }],
  openapi: { title: 'My API', version: '1.0.0' },
});
```

#### Configuration validation messages (exit 2)

**Symptom** — One of the following messages, with nothing generated:

| Message | Meaning |
| --- | --- |
| `The API configuration must default-export an object.` | The default export is not a plain object |
| `Unknown API configuration key: X.` | A top-level key outside `outputDir`, `contractFile`, `controllers`, `openapi`, `generator` |
| `Unknown generator option: X.` | A `generator` key outside `splitByGroup`, `strict`, `clientName`, `runtimeImport` |
| `<key> must be a non-empty string.` | Missing or blank `outputDir`, `openapi.title`, `openapi.version`, … |
| `openapi.servers[0] must be an object.` | Malformed `servers` entry |
| `openapi.securitySchemes.bearerAuth.type is not a valid scheme type.` | `type` must be `apiKey`, `http`, `oauth2`, or `openIdConnect` |
| `openapi.defaultSecurity[0].bearerAuth must be a string array.` | Security requirement scopes must be strings |
| `outputDir must not escape the configuration directory.` | A relative path resolves outside the config directory |
| `outputDir must not be a filesystem root.` | A path like `/` or `C:\` |
| `Could not load the API configuration: <detail>` | The file failed to load (syntax error, missing import) |

**Cause** — The loader validates strictly and independently of TypeScript. With `defineApiContract` the compiler catches most of this earlier (`Object literal may only specify known properties, and 'mystery' does not exist in type 'ApiContract'`), but a cast or a plain `.ts` file without the helper bypasses that check.

**Fix** — Declare only supported keys and keep relative artifact paths inside the config directory:

```typescript fragment
export default defineApiContract({
  outputDir: 'src/api-client',        // required, must stay inside the config directory
  contractFile: 'api.json',           // optional, defaults to api.json
  controllers: [{ basePath: '/api/products', controller: ProductsController }],
  openapi: {
    title: 'My API',
    version: '1.0.0',
    servers: [{ url: 'https://api.example.com', description: 'Production' }],
    securitySchemes: {
      bearerAuth: { type: 'http', scheme: 'bearer', bearerFormat: 'JWT' },
    },
    defaultSecurity: [{ bearerAuth: [] }],
  },
  generator: { splitByGroup: false, strict: false, clientName: 'AppClient' },
});
```

#### `Controller 0 must reference a controller class.` / `The controller for /api/products is not a controller class.`

**Cause** — The `controller` value is not a function. In practice this is an instance instead of the class, a circular import resolving to `undefined`, or a non-class export.

**Fix** — Reference the class itself and import it directly (avoid barrel re-exports that create cycles):

```typescript fragment
import { ProductsController } from './controllers/products.controller.js';

export default defineApiContract({
  outputDir: 'src/api-client',
  controllers: [{ basePath: '/api/products', controller: ProductsController }],
  openapi: { title: 'My API', version: '1.0.0' },
});
```

#### `DRIFT: api.json, client.ts` (exit 1)

**Symptom** — `blendsdk api check` writes `DRIFT: <files>` to stderr alongside `ERROR:` lines, and exits `1`.

**Cause** — A fresh in-memory rebuild differs from the committed artifacts. The comparison is byte-for-byte: `api.json` is compared against Prettier-formatted JSON (two-space indent, LF, sorted paths), generated client files are compared against fresh output, and any extra file in the output directory that still carries the generated marker counts as drift.

**Fix** — Regenerate, review the diff, and commit both artifacts:

```bash
blendsdk api generate
git diff --exit-code -- api.json src/api-client
```

Never hand-edit generated client files or `api.json` to silence drift — the next `generate` overwrites them and `check` will keep failing until the contract source is fixed.

### OpenAPI and client generation failures

#### `Duplicate operationId "listProducts" used by GET /api/products and POST /api/products/query. OpenAPI operationIds must be unique.`

**Cause** — Two operations share an `operationId`. The generator refuses to run rather than silently let one method overwrite the other. A related error is thrown after sanitization when two different operationIds collapse to the same group/method pair:

```
Duplicate method "products.delete" produced by DELETE /api/a and POST /api/b. Rename one operationId or tag.
```

**Fix** — Give every operation a unique `operationId`, and avoid names that collide after escaping (for example `delete` and `delete_` in the same tag group). A fixed, complete example:

```typescript
import { generateClient, type OpenAPIDocument } from 'blendsdk/codegen';

const document: OpenAPIDocument = {
  openapi: '3.1.0',
  info: { title: 'My API', version: '1.0.0' },
  paths: {
    '/api/products': {
      get: {
        operationId: 'listProducts',
        tags: ['products'],
        responses: {
          200: {
            description: 'OK',
            content: {
              'application/json': { schema: { type: 'array', items: { type: 'object' } } },
            },
          },
        },
      },
      post: {
        operationId: 'createProduct',
        tags: ['products'],
        responses: {
          200: { description: 'OK', content: { 'application/json': { schema: { type: 'object' } } } },
        },
      },
    },
  },
};

const result = await generateClient(document, { outputDir: 'src/api-client' });
console.log(result.files);
```

#### `ERROR: Operation GET /api/products/{id} has no operationId; a deterministic method name was generated.` in `check` (exit 1)

**Symptom** — `generate` prints the same text as `WARNING:` and exits `0`; `check` escalates it to an error and exits `1`. `generateClient` also throws when `strict: true`:

```
The contract has errors:
- Operation GET /api/products/{id} has no operationId; a deterministic method name was generated.
- Operation GET /api/things has no 2xx response schema; its result type is unknown.
```

**Cause** — Missing `operationId` and missing 2xx response schemas are contract defects. `check` always escalates them; `generate` escalates them only with `strict: true`. Without an `operationId`, the generator derives a fallback name (group + HTTP method + path segments, `{id}` becomes `ById` — for example `productsGetById`), which changes whenever the tag or path changes.

**Fix** — Annotate every route that should reach the client. The response schema also determines the generated method's return type, so declare it:

```typescript fragment
import { z } from 'zod';

class ProductsController {
  public routes() {
    return [
      {
        method: 'get',
        path: '/:id',
        handler: () => undefined,
        openapi: {
          operationId: 'getProduct',
          tags: ['products'],
          responses: [
            {
              statusCode: 200,
              description: 'OK',
              schema: z.object({ id: z.number(), name: z.string() }),
            },
          ],
        },
      },
    ];
  }
}
```

Align strictness between the two commands: set `generator.strict: true` so `generate` fails exactly where `check` fails, instead of discovering the problem in CI.

#### `Operation DELETE /api/products/{id} uses the reserved name "delete"; the method was renamed to "delete_".`

**Cause** — JavaScript reserved words, TypeScript type keywords, and object prototype names are escaped deterministically with a trailing underscore: `delete` → `delete_`, `constructor` → `constructor_`, `__proto__` → `__proto___`, `string` → `string_`.

**Fix** — This is a warning, not a failure: the client gets a working method. If the escaped name is unacceptable, rename the `operationId`. Remember that changing it later is a breaking change for every consumer of the generated client.

#### `Operation PATCH /api/products/{id} has duplicate parameter name(s) id; the path or query parameter wins over the body property.`

**Cause** — Path parameters, query parameters, and the JSON request body are flattened into one params object per operation. When a body property shares a name with a path or query parameter, the duplicate is dropped and the path/query parameter wins — so a body `id: number` may silently disappear:

```typescript fragment
export type ProductsUpdateProductParams = { id: string; name?: string };
```

**Fix** — Rename the body property (for example `productId`), or accept the flattening deliberately. If the dropped property carried validation rules, review the route so the contract matches what the handler expects.

#### Cannot find module 'blendsdk/api-client' (TS2307 in the generated client)

**Cause** — Generated clients import a runtime (`createApiClient`, `ApiClientOptions`, `OperationDescriptor`, `RequestOptions`). The default specifier is `blendsdk/api-client`; a project that does not provide that module cannot compile the generated output.

**Fix** — Install/provide the runtime, or point generation at your runtime module:

```typescript fragment
generator: { runtimeImport: '@acme/api-runtime' },
```

#### TS2307: Cannot find module './types.js' or its corresponding type declarations.

**Cause** — Generated files use explicit ESM `./types.js` specifiers. TypeScript only maps those to the `.ts` sources under `node16`, `nodenext`, or `bundler` module resolution; the legacy `moduleResolution: "node"` cannot.

**Fix** — Compile generated clients with a resolution mode that understands ESM and `exports`:

```json
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "target": "es2022",
    "strict": true
  }
}
```

### Migration configuration and file contract failures

#### `Could not find blendsdk.migrations.ts.` / `Migration configuration was not found at /path.` (exit 2)

**Cause** — No configuration was discovered. `--config` is honored first (file or directory); otherwise the loader searches upward from the current directory — and unlike the API loader, it walks all the way to the filesystem root: it does **not** stop at `.git`. A stray `blendsdk.migrations.ts` in a parent directory (for example your home directory) can be picked up by accident.

**Fix** — Keep the config at the project root and pass `--config` in scripts and CI:

```typescript
// blendsdk.migrations.ts
import { defineMigrationConfig } from 'blendsdk/codegen';

export default defineMigrationConfig({
  schema: './src/database/schema.ts',
  migrationsDir: './migrations',
  snapshotFile: './migrations/schema.snapshot.json',
  databaseUrlEnv: 'DATABASE_URL',
  lockTimeoutMs: 5_000,
  statementTimeoutMs: 900_000,
});
```

#### Migration configuration validation messages (exit 2)

| Message | Meaning |
| --- | --- |
| `Migration configuration must default-export an object.` | The default export is not a plain object |
| `Unknown migration configuration key: X.` | A key outside `schema`, `migrationsDir`, `snapshotFile`, `databaseUrlEnv`, `lockTimeoutMs`, `statementTimeoutMs` |
| `databaseUrlEnv must be an uppercase environment-variable name.` | The value must match `^[A-Z_][A-Z0-9_]*$` |
| `lockTimeoutMs must be an integer from 1 through 300000.` | Bounded lock deadline |
| `statementTimeoutMs must be an integer from 1 through 86400000.` | Bounded statement deadline |
| `migrationsDir must not escape the configuration directory.` | Relative path outside the config directory |
| `Configured path must not contain a symbolic link: /path.` | Symlink segment rejected |
| `snapshotFile must not use a migration SQL filename.` | The snapshot cannot be named like `*.up.sql` / `*.down.sql` |
| `Could not load the migration configuration: <detail>` | The file failed to load |

**Fix** — Correct the offending field. Note the deliberate indirection: the config never contains a connection URL, only the name of the environment variable that holds it, so resolved configuration can be logged safely.

#### `The generate command requires a schema module.` / `Could not load the migration schema: <detail>` / `The schema module must default-export one DatabaseSchema instance.`

**Cause** — `generate`, `baseline`, and `adopt-baseline` need desired schema state (`schema` in the config); `up`, `down`, `status`, and `validate` do not. The module is loaded with a fresh Jiti instance, so syntax errors and missing imports surface here.

**Fix** — Point `schema` at a module whose default export is a `DatabaseSchema`:

```typescript
// src/database/schema.ts
import { DatabaseSchema } from 'blendsdk/codegen';

const schema = new DatabaseSchema('app');

const customer = schema.table('customer');
customer.bigint('id').primaryKey();
customer.text('name').nullable();

export default schema;
```

Because execution-only commands never import the schema module, a broken schema module will not fail `up` — validate it explicitly with `blendsdk migrate validate --offline` after changing it.

#### `Invalid migration filename: notes.sql.` / `Unexpected SQL file in migration directory: notes.sql.`

**Cause** — Every non-dot `.sql` file in the migrations directory must match `^(\d{14})_[a-z][a-z0-9-]{0,62}\.(up|down)\.sql$`. Related messages from the same discovery pass:

- `Down migration has no matching up file: 20260827130000_down-only.`
- `Case-folded duplicate migration filename: 20260827120000_ADD.up.sql.`
- `Migration SQL must be a regular file: <name>.` (directories and symlinks are rejected)
- `Duplicate up migration: 20260827120000_add-status.`

**Fix** — Keep only real migration files in the directory; move notes and helper SQL elsewhere. Discovery ignores dot-prefixed files (the writer's temporary files), so private scratch files must start with a dot.

#### `Migration must use LF endings and end with LF: 20260827120000_add-status.up.sql.`

**Cause** — Migration files are exact byte artifacts: UTF-8 without BOM, LF line endings, a final newline, and an executable body (not comment-only). Related messages:

- `Migration must not contain a UTF-8 BOM: <file>.`
- `Migration is not valid UTF-8: <file>.`
- `Migration SQL body must contain a non-comment token.`
- `Snapshot must use LF endings and end with one LF.` / `Snapshot is not valid UTF-8.`

**Fix** — Configure editors and git to keep LF, and re-save the offending file:

```gitattributes
*.sql text eol=lf
*.json text eol=lf
*.ts text eol=lf
```

#### `Migration header ID must match its filename.` / `Missing or reordered migration header: -- id:.`

**Cause** — The five-line header is strict and positional. Renaming or copying a file without updating `-- id:` produces the first message; inserting, deleting, or reordering header lines produces the second. Related: `Invalid migration version header.`, `Migration transaction metadata must be true or false.`, `Invalid snapshot hash metadata.`

**Fix** — Never rename migration files by hand; regenerate instead. A valid file looks exactly like this:

```sql
-- blendsdk-migration: 1
-- id: 20260827120000_add-customer-status
-- transaction: true
-- from-snapshot: none
-- to-snapshot: none
ALTER TABLE "public"."customer" ADD COLUMN "status" text;
```

#### `Transactional migration SQL must not control transactions.`

**Cause** — The runner owns the transaction for migrations with `-- transaction: true`; `BEGIN`, `COMMIT`, `ROLLBACK`, `ABORT`, `SAVEPOINT`, `RELEASE`, `END`, `START TRANSACTION`, `PREPARE TRANSACTION`, and `SET TRANSACTION` are rejected. The check is lexical and fails closed on malformed quoting or comments, but ignores transaction words inside strings and comments.

**Fix** — Remove the transaction control. When a statement cannot run inside a transaction (for example `CREATE INDEX CONCURRENTLY` or `VACUUM`), create the migration as nontransactional:

```bash
blendsdk migrate create rebuild-product-index --no-transaction
```

The generator also marks a migration nontransactional automatically when its change list contains a concurrent index.

#### `Generated snapshot lineage is disconnected at 20260827120000_add-status.` / `Migration/snapshot lineage is torn. Remove the orphan migration or restore the snapshot from version control.`

**Cause** — A generated migration's `-- from-snapshot` must equal the previous generated migration's `-- to-snapshot`, and the newest `-- to-snapshot` must equal the current snapshot bytes. Generation publishes the migration and snapshot as one pair, so a crash between the two, a manual file move, or a hand-edited header breaks the chain. A related guard fires when history exists without any snapshot: `Migration history exists without its canonical snapshot.`

**Fix** — Recovery is deliberately manual and auditable; there is no automatic repair command. Choose one path and stick to it:

1. `git status` and `git diff` to see what changed.
2. If the snapshot was lost: restore it from version control (`git checkout -- migrations/schema.snapshot.json`).
3. If an orphan migration exists (published without its snapshot): remove the migration file, then rerun `blendsdk migrate generate <name>` so both artifacts are published together.

Dot-prefixed temporary files left by an interrupted publish can be deleted safely.

### Migration generation and review failures

#### `Migration name must be a lowercase slug.` / `This command requires a migration name.` (exit 2)

**Cause** — Names must match `^[a-z][a-z0-9-]{0,62}$`, and `generate`, `create`, and `baseline` take the name as the first positional argument. `blendsdk migrate generate --allow-destructive` without a name fails route parsing.

**Fix** — Pass a lowercase, hyphenated name:

```bash
blendsdk migrate generate add-customer-status
blendsdk migrate create backfill-customer-status
blendsdk migrate baseline initial
```

#### `New migration identifiers must follow existing history.`

**Cause** — Migration IDs are UTC timestamps (`YYYYMMDDHHMMSS`) and must sort after the newest existing migration. This fires on clock skew, on fixtures with future timestamps, or when two migrations are generated within the same second. Nothing is written when it fails.

**Fix** — Correct the system clock and rerun. Embedding callers can pin the clock for deterministic output:

```typescript fragment
const result = await generateMigration({
  name: 'add-status',
  now: new Date('2026-08-27T12:00:00Z'),
});
```

#### `Destructive migration changes require explicit approval.`

**Cause** — Removals (column/table/constraint/index/extension/schema drops) are classified `destructive`, and the renderer refuses to emit them without approval.

**Fix** — Review the change list, then approve. Every destructive statement is marked with `-- destructive: reviewed and explicitly allowed`:

```typescript
import { generateMigration, MigrationError } from 'blendsdk/codegen';

try {
  const result = await generateMigration({
    name: 'drop-customer-status',
    allowDestructive: true,
  });
  console.log(result.status, result.migration?.id ?? 'no migration');
} catch (error) {
  if (error instanceof MigrationError) {
    console.error(`${error.kind}: ${error.message}`);
    process.exitCode = error.exitCode;
  } else {
    throw error;
  }
}
```

#### Blocked changes that need manual SQL

**Symptom** — Generation fails with guidance naming the exact change:

| Guidance | Trigger |
| --- | --- |
| `Use a staged population strategy for a required column.` | Adding a `NOT NULL` column that has no default |
| `Populate and validate existing rows before SET NOT NULL.` | `nullable` → `NOT NULL` transition |
| `Provide reviewed manual SQL with an explicit USING expression.` | Column type/size/scale change |
| `Generated-column transitions require reviewed manual SQL.` / `Identity transitions require reviewed manual SQL.` | Generated or identity changes |
| `Primary-key replacements require reviewed manual SQL.` | Primary key changed |
| `Same-name constraint replacements require reviewed manual SQL.` / `Same-name index replacements require reviewed manual SQL.` | Definition changed under an existing name |
| `View dependency order requires reviewed manual SQL.` / `Multiple view dependencies require reviewed manual SQL.` / `View removal dependencies require reviewed manual SQL.` | View changes that cannot be proven safe |
| `Constraint or index changes combined with a table rename require manual SQL.` | Rename plus collection edits |
| `Cyclic table removals require reviewed constraint-drop SQL.` | Cyclic foreign-key drops |

**Cause** — The differ classifies everything it cannot prove as `caution`, `ambiguous`, or `unsupported`, and the renderer emits SQL only for `safe` changes (plus approved destructive ones). This is intentional: PostgreSQL can rewrite equivalent SQL, so semantic guessing would be unsafe.

**Fix** — Write the reviewed SQL as a manual migration next to the generated ones:

```bash
blendsdk migrate create convert-customer-status
```

Then replace the template's no-op body with the reviewed statement:

```sql
-- blendsdk-migration: 1
-- id: 20260827130000_convert-customer-status
-- transaction: true
-- from-snapshot: none
-- to-snapshot: none
ALTER TABLE "public"."customer"
  ALTER COLUMN "status" TYPE integer USING "status"::integer;
```

Manual migrations carry `none` lineage and coexist with generated history; later generated diffs still start from the canonical snapshot.

#### `Rename hints must be one-to-one and acyclic.` / `Rename hint must reference one prior and one desired identity.`

**Cause** — Rename hints are validated before diffing. Each hint must map exactly one removed identity to one added identity, stay inside one schema, never cycle, and column hints that cross table names need a matching table rename hint. Without a hint, a dropped+added pair with identical shape is classified `ambiguous` and blocks generation (`Provide one explicit table rename hint.`).

**Fix** — Pass explicit hints from the CLI, or the equivalent `renameHints` option:

```bash
blendsdk migrate generate rename-customer \
  --rename-table public.customer=public.account \
  --rename-column public.customer.label=public.account.display_name
```

Cross-schema renames are rejected by design (`Cross-schema renames require reviewed manual SQL.`) — handle them with a manual migration.

### Migration execution, locking, and recovery

#### `LOCKED: The PostgreSQL migration lock is held by another session.` (exit 1)

**Symptom** — `up`/`down` fail after roughly `lockTimeoutMs` (default 5 s); `status`/`validate` report `LOCKED` without waiting and exit `1`.

**Cause** — Runners serialize on a per-database advisory lock (`blendsdk:migrations:v1` on the current database). Another runner — or a long transaction from an application — is holding it. Different databases never contend.

**Fix** — Retry, raise `lockTimeoutMs` (maximum 300 000 ms), or find and wait out the holder:

```sql
SELECT pid, state, application_name
FROM pg_stat_activity
WHERE datname = current_database()
  AND application_name = 'blendsdk-migrations';
```

#### `UNKNOWN_OUTCOME: The latest nontransactional migration has an unknown outcome.`

**Symptom** — A ledger row stays in state `NONTRANSACTIONAL_DIRTY`; `status` reports `UNKNOWN_OUTCOME`; all further `up`/`down` runs refuse to proceed.

**Cause** — Nontransactional migrations commit a durable uncertainty marker before their SQL is dispatched. If the session is lost, the run is cancelled mid-flight, or the ledger cannot be finalized afterwards, the runner cannot know whether the SQL took effect — so it fails closed. There is deliberately no automatic repair command.

**Fix** — Investigate, decide forward or backward recovery, and only then finalize the row as a reviewed operator action:

```sql
SELECT id, state, checksum, applied_at, execution_ms
FROM public.blendsdk_migrations
ORDER BY id;
```

1. Inspect the database to determine whether the migration's effects are present.
2. If the effects are confirmed, finalize the row:

```sql
UPDATE public.blendsdk_migrations
SET state = 'APPLIED', applied_at = now(), execution_ms = 0
WHERE id = '20260827120100_nontransactional'
  AND state = 'NONTRANSACTIONAL_DIRTY';
```

3. If the effects are absent, revert the row (delete it) and rerun the migration after fixing the cause.
4. Re-run `blendsdk migrate status` to confirm the runner is unblocked.

#### `DATABASE: Migration 20260827120100_broken failed and was rolled back.`

**Cause** — The migration SQL failed inside the runner-owned transaction. Effects were rolled back, no ledger row was written, and no later migration was attempted. Session-loss variants: `Migration <id> failed and its session was lost.`, `Migration <id> completed but its ledger could not be finalized.`

**Fix** — The message is intentionally sanitized: it never contains SQL text or credentials, so use the PostgreSQL server log for the raw error. If the migration was never applied, it is still mutable — fix the body directly and rerun:

```bash
blendsdk migrate validate --offline
blendsdk migrate up
```

If the failure was a statement timeout, raise `statementTimeoutMs` or split the migration into smaller files.

#### `ABORTED: Migration operation was cancelled.`

**Cause** — SIGINT/SIGTERM (`up`/`down` only) or an embedded caller's `AbortSignal`. A transactional migration in flight is rolled back; already-completed migrations stay applied; a nontransactional migration cancelled after dispatch becomes `UNKNOWN_OUTCOME`.

**Fix** — Rerun `up`; the runner resumes from the first pending migration. If the interruption happened mid-nontransactional, resolve the dirty marker first.

#### `Migration prefix or checksum mismatch at position 1.` / `Migration 20260827120000_x changed after history validation.`

**Cause** — An applied migration file was edited. Checksums are exact-byte SHA-256 values recorded in the ledger, and the ledger must be the exact ordered prefix of local history. Even whitespace changes trigger this; `Migration <id> changed after history validation.` covers a file edited while a runner was waiting for the lock.

**Fix** — Restore the file and deliver the change as a new migration:

```bash
git checkout -- migrations/20260827120000_x.up.sql
blendsdk migrate validate --offline
blendsdk migrate generate correct-previous-mistake
```

#### `Down requires explicit allowDown confirmation.` / `The latest applied migration has no down file.`

**Cause** — `down` is guarded twice: the CLI requires `--allow-down` (otherwise exit 2 usage), and the runner requires `allowDown: true`. It also needs the newest applied migration to have a matching `.down.sql`; running `down` against an empty ledger reports the same message.

**Fix** — Confirm deliberately, and only for migrations created with a down file:

```bash
blendsdk migrate down --allow-down
```

For a generated migration without a down file, add one whose lineage inverts the up file: `-- from-snapshot` equals the up file's `-- to-snapshot`, and `-- to-snapshot` equals the up file's `-- from-snapshot`. Manual migrations created with `blendsdk migrate create --with-down` already use `none` lineage on both sides.

#### `DATABASE: Database URL environment variable DATABASE_URL is not set.`

**Cause** — Online commands (`up`, `down`, `status`, and `validate` without `--offline`) read the URL from the environment variable named by `databaseUrlEnv`. The value is never read from the config file.

**Fix** — Export it, or validate offline when no database is available:

```bash
export DATABASE_URL='postgresql://user:password@127.0.0.1:5432/app'
blendsdk migrate status
blendsdk migrate validate --offline
```

If the driver itself is missing, the error is `The optional pg package is required for database migration commands.` — install `pg` in the project.

#### `LOCKED` after exactly `lockTimeoutMs`, or a migration cancelled at `statementTimeoutMs`

**Cause** — Defaults are 5 000 ms for the advisory-lock wait and 900 000 ms per statement. CI concurrency frequently exceeds the lock default; long index builds may exceed the statement default.

**Fix** — Raise the bounds in the migration config (maximums: 300 000 ms and 86 400 000 ms), or split the work:

```typescript fragment
export default defineMigrationConfig({
  schema: './src/database/schema.ts',
  lockTimeoutMs: 60_000,
  statementTimeoutMs: 3_600_000,
});
```

### Snapshot and ledger integrity failures

#### `Snapshot bytes are not in canonical version-one form.`

**Symptom** — Any snapshot operation fails: generation, status, or the runner's lineage validation.

**Cause** — `schema.snapshot.json` is byte-canonical: two-space JSON, LF endings, a final newline, no BOM, and the exact serialization the normalizer produces. Hand edits, IDE reformatting, or a JSON formatter produce valid JSON that still fails. Related messages: `Snapshot does not match the strict version-one schema.`, `Snapshot is not valid JSON.`, `Snapshot file does not exist.`, `Snapshot path must be a regular file.`

**Fix** — Never edit or reformat the snapshot by hand. Restore it from version control and regenerate through the schema:

```bash
git checkout -- migrations/schema.snapshot.json
blendsdk migrate generate add-customer-status
```

Editing the schema and regenerating is the only supported way to change desired state.

#### `Snapshot format version is unsupported; upgrade BlendSDK before rewriting it.`

**Cause** — The file declares a `formatVersion` other than `1` — usually written by a newer package version than the one running now.

**Fix** — Run a compatible version of `blendsdk/codegen`; do not rewrite the file to force it through. Downgrading the dependency while a newer snapshot exists is unsafe.

#### `The existing migration ledger is not compatible with version one.` / `Migration ledger row 3 is invalid.`

**Cause** — `public.blendsdk_migrations` exists with a different shape than the runner expects — wrong columns, a different primary key, or missing/weakened check constraints (the runner verifies the table's catalog shape, not just its column names). The row-level variant means a row violates the v1 contract (identifier pattern, SHA-256 checksum format, state, or the `applied_at`/`execution_ms` pairing).

**Fix** — Inspect the table before touching it:

```sql
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'blendsdk_migrations'
ORDER BY ordinal_position;
```

If the table was created by hand or by an unrelated tool and holds no real history, drop it and let the runner recreate it. If it holds applied rows, treat them as production data and migrate them deliberately — never let two tools own the same ledger.

### Baseline adoption failures

#### `Baseline adoption requires exactly one initial generated migration.` / `Baseline adoption requires an absent or empty migration ledger.`

**Cause** — `adoptBaseline` only fits the project state produced by `baseline`: exactly one generated initial migration, a snapshot whose hash matches that migration's `-- to-snapshot`, and a target database whose ledger is absent or empty. `The baseline migration does not match the canonical snapshot.` and `Local baseline history changed during adoption.` fire when the local files change mid-adoption.

**Fix** — Prepare the project state first, then adopt with the exact confirmation token:

```bash
blendsdk migrate baseline initial
blendsdk migrate adopt-baseline --confirm-adoption "production/20260827090000_initial"
```

#### `Adoption requires exact target confirmation after application and admin DDL is quiesced.`

**Cause** — The confirmation must be exactly `<database>/<baseline-id>`. This binds the operation to one resolved target and forces an explicit acknowledgement that application and administrative DDL has stopped.

**Fix** — Read the database name and baseline id from the preview the command prints (`TARGET user@host:port/database` plus the comparison list), then pass the exact token. A wrong token is a `CONFIGURATION` error and the ledger is not touched.

#### `UNSUPPORTED: DIFFERENT: column.public.customer.name. Baseline adoption was not changed.`

**Cause** — Adoption compares desired and live catalogs object by object. Only `MATCH` and informational `UNMANAGED` entries are compatible. Other classifications: `MISSING`, `DIFFERENT`, `EXTRA_MODELED`, `UNSUPPORTED_FOR_ADOPTION`. Some desired properties can never be proven structurally equivalent — views, string defaults, generated columns, check constraints, and index expressions/predicates are always reported `UNSUPPORTED_FOR_ADOPTION`, and unsupported relation shapes (partitioned, foreign, unlogged, or partition tables) block adoption.

**Fix** — Reconcile the database or the schema until the comparison is clean:

1. For a database that should match the baseline exactly, apply the baseline SQL manually (that is the documented adoption path — the tool never executes it for you).
2. For every `UNSUPPORTED_FOR_ADOPTION` entry, decide manually whether the live object is equivalent; if the schema relies on SQL expressions adoption cannot verify, simplify the schema or manage those objects outside BlendSDK.
3. Re-run `adopt-baseline`; unrelated functions and triggers are reported as `UNMANAGED` and do not block adoption.

### Schema authoring, type generation, and introspection failures

#### `Schema object already exists public.user`

**Cause** — `SchemaContainer` registers a name the moment `.named()` or `.scope()` is called and rejects duplicates within the same scope. Building the "same" shape twice — for example two `user_request` objects in the default scope — triggers this.

**Fix** — Give each root type a unique name, or isolate versions with scopes:

```typescript
import { SchemaContainer, TypeGenerator } from 'blendsdk/codegen';

const schema = new SchemaContainer();
const v1 = schema.scope('api_v1');
const v2 = schema.scope('api_v2');

v1.object({ id: v1.number() }).named('user_request');
v2.object({ id: v2.string() }).named('user_request');

const source = await new TypeGenerator().generate(schema);
console.log(source);
```

#### `Object properties cannot be named explicitly. Create a seperate root type (public.email) and use .ref() as the property.`

**Cause** — A property object was given a name (`.named()`). Generators render properties inline; only root types may be named. The companion failure, `Referenced schema is not named!`, is the opposite case: a `ref()` points at a schema that was never named.

**Fix** — Promote the nested shape to its own named root type and reference it:

```typescript
import { SchemaContainer, TypeGenerator } from 'blendsdk/codegen';

const schema = new SchemaContainer();
const scope = schema.scope();

const address = scope.object({ city: scope.string(), zip: scope.string() }).named('address');
scope.object({ id: scope.number(), address: scope.ref(address) }).named('customer');

const source = await new TypeGenerator().generate(schema);
console.log(source);
```

#### `Column emial does not exit in customer`

**Cause** — A constraint references a column that does not exist on the table (the message contains a long-standing typo, "exit" instead of "exist"). Typical causes: a typo, a column renamed later, or a constraint added before the column was declared.

**Fix** — Declare columns before the constraints that reference them, and match names exactly:

```typescript
import { DatabaseSchema, PostgreSQLSchemaGenerator } from 'blendsdk/codegen';

const schema = new DatabaseSchema('app');
const customer = schema.table('customer');

customer.bigint('id');
customer.text('email');
customer.primaryKey().column('id');
customer.uniqueConstraint().column('email');

const ddl = new PostgreSQLSchemaGenerator(schema).generate();
console.log(ddl);
```

#### `IDENTITY columns must be integer or uuid types` / `Column cannot be both IDENTITY and GENERATED` / `PostgreSQL only supports STORED generated columns`

**Cause** — Column-state conflicts in the authoring model. A related foreign-key message is `Use the from() and to()` — thrown when `.column()` is called on a `ForeignKeyConstraint` instead of `from()`/`to()`.

**Fix** — Keep identity and generated/default mutually exclusive, and use supported types:

```typescript
import { DatabaseSchema, PostgreSQLSchemaGenerator } from 'blendsdk/codegen';

const schema = new DatabaseSchema('app');
const item = schema.table('item');

item.bigint('id').identity('ALWAYS', { start: 1, increment: 1 });
item.uuid('token').identity('v4');

const ddl = new PostgreSQLSchemaGenerator(schema).generate();
console.log(ddl);
```

#### `[WARNING]: public -> audit_log -> jsonb could not be mapped!` and `any` / `@deprecated` types in generated output

**Symptom** — `PostgreSQLIntrospector.introspect()` logs warnings and the generated types contain `any` properties described as `@deprecated <warning>`.

**Cause** — JSON, `jsonb`, `bytea`, interval, range, and geometry columns have no default mapping; the introspector falls back to a deprecated placeholder rather than guessing. This is a warning, not a failure.

**Fix** — Map the unhandled types explicitly with a `ColumnMapper`; the mapper's return value replaces the fallback for that column:

```typescript
import type { PostgreSQLDatabase } from 'blendsdk/postgresql';
import {
  PostgreSQLIntrospector,
  SchemaContainer,
  type ColumnMapper,
} from 'blendsdk/codegen';

export async function introspectWithOverrides(db: PostgreSQLDatabase): Promise<number> {
  const schema = new SchemaContainer();
  const mapper: ColumnMapper = (record, scope) => {
    switch (record.pg_type) {
      case 'json':
      case 'jsonb':
        return scope.any().recordSet();
      default:
        return undefined;
    }
  };

  await new PostgreSQLIntrospector(db).introspect(schema, mapper);
  return schema.getAll().length;
}
```

### TypeScript and module resolution failures

#### `TS2307: Cannot find module 'blendsdk/codegen'` or `ERR_PACKAGE_PATH_NOT_EXPORTED: Package subpath './dist/index.js' is not defined by "exports"`

**Cause** — The package exposes only its root via the `exports` map, and only for ESM `import`. Deep imports into `dist/` or `src/` are not part of the public API, and `require()` cannot resolve the package entry.

**Fix** — Import from the package root, use ESM, and compile with a resolution mode that understands `exports`:

```typescript
import { generateMigration, runMigrations, MigrationError } from 'blendsdk/codegen';
```

```json
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext"
  }
}
```

#### `TS2339: Property 'nullable' does not exist on type 'void'`

**Cause** — `TableColumnSchema.size()` and `.scale()` set state and return `void`; only the typed helpers return the column for chaining.

**Fix** — Pass size and scale through the helpers, then chain modifiers:

```typescript
import { DatabaseSchema } from 'blendsdk/codegen';

const schema = new DatabaseSchema('app');
const customer = schema.table('customer');

customer.varchar('email', 255).nullable();
customer.numeric('balance', 12, 2).default(0);

console.log(customer.getColumns().map(column => column.getName()));
```

#### `error instanceof MigrationError` is `false` even though the error looks identical

**Cause** — Two copies of `blendsdk/codegen` in the dependency graph produce two distinct `MigrationError` classes; `instanceof` compares class identity, not shape. The same trap applies to duplicated `DatabaseSchema` and `zod` copies.

**Fix** — Prefer `instanceof`, but where duplication is possible check the stable public contract (`kind` and `exitCode`):

```typescript
import { formatMigrationError, runMigrations, type MigrationError } from 'blendsdk/codegen';

function isMigrationError(error: unknown): error is MigrationError {
  if (typeof error !== 'object' || error === null) {
    return false;
  }
  return (
    typeof Reflect.get(error, 'kind') === 'string' &&
    typeof Reflect.get(error, 'exitCode') === 'number'
  );
}

try {
  await runMigrations({ command: 'up' });
} catch (error) {
  if (isMigrationError(error)) {
    console.error(formatMigrationError(error));
  } else {
    throw error;
  }
}
```

#### Route Zod schemas are ignored (request bodies become `{ "type": "object" }`, no query parameters), or `z.toJSONSchema is not a function`

**Cause** — `OpenAPIGenerator` recognizes Zod schemas with `instanceof z.ZodType` against the `zod` copy it resolves, then converts them with Zod 4's native `z.toJSONSchema`. If your application uses a different copy, recognition fails and schemas silently degrade to a permissive object (and GET/DELETE query splitting yields nothing). If the resolved copy is an older major, conversion fails with `z.toJSONSchema is not a function`.

**Fix** — Keep exactly one Zod copy at `^4` and let the app and the codegen package share it:

```bash
pnpm why zod
pnpm dedupe
```

After fixing the graph, regenerate and confirm the document now contains the real property schemas and query parameters.

## Debugging Strategies

### 1. Classify the failure from the exit code and stream first

| Observation | Meaning and next move |
| --- | --- |
| Exit `2`, message starts with `USAGE:` or `CONFIGURATION:` | Fix arguments or configuration; nothing was executed or written |
| Exit `1` with `DRIFT:` on stderr | Rebuild and commit the artifacts |
| Exit `1` with `ERROR: <issue>` | A contract issue escalated — fix the route metadata listed in the message |
| `WARNING:` on stdout | Non-fatal in `generate`; will fail `check` unless fixed |
| Exit `1` with a `MigrationError` message `<KIND>: <text>` | Handle by `kind`, not by message text |

### 2. Reproduce a drift report without writing anything

`checkClient` performs the same rebuild the CLI does, in memory, and returns the exact files and issues. Run it from a script to see the whole picture:

```typescript
import { readFile } from 'node:fs/promises';
import { checkClient, type OpenAPIDocument } from 'blendsdk/codegen';

const text = await readFile('api.json', 'utf8');
const document = JSON.parse(text) as OpenAPIDocument;

const result = await checkClient(document, { outputDir: 'src/api-client' });

console.log('drifted files:', result.driftedFiles ?? []);
for (const issue of result.issues) {
  console.log(`${issue.severity.toUpperCase()}: ${issue.message}`);
}
```

Then compare the committed output against a fresh generation in a scratch directory (`git diff --no-index src/api-client /tmp/api-client`) to see exactly which bytes changed.

### 3. Validate migration state in escalating order

1. Local files only — no database, no driver:

```bash
blendsdk migrate validate --offline
```

2. Live history and lock without mutation:

```bash
blendsdk migrate status
```

3. Pending order without mutation (also proves the lock is currently available):

```bash
blendsdk migrate up --dry-run
```

Interpret the result: `UP_TO_DATE` and `PENDING` are healthy; `INVALID_HISTORY` means local files and the ledger disagree; `LOCKED` means another session holds the advisory lock; `UNKNOWN_OUTCOME` means a nontransactional row needs operator resolution.

### 4. Audit the artifact chain by hand

The lineage is inspectable from three places — migration headers, the snapshot hash, and the ledger:

```bash
head -5 migrations/20260827120000_add-status.up.sql
sha256sum migrations/schema.snapshot.json
```

The snapshot hash must equal the newest migration's `-- to-snapshot:` value. Then compare the ledger:

```bash
psql "$DATABASE_URL" -c "SELECT id, state, checksum, from_snapshot, to_snapshot FROM public.blendsdk_migrations ORDER BY id"
```

Every applied row must pair one-to-one, in order, with local files — same ids, same checksums, same lineage hashes.

### 5. Surface the real database error behind a sanitized message

Runner errors are intentionally sanitized: they never contain SQL text, credentials, or provider detail (URLs are redacted to `[REDACTED_DATABASE_URL]`). To see why a migration failed:

1. Reproduce the migration body manually against a disposable database inside a transaction, or
2. Read the PostgreSQL server log. For the repository test container, use `pnpm run db:logs`.

### 6. Find the lock holder

```sql
SELECT pid, state, wait_event_type, left(query, 80) AS query
FROM pg_stat_activity
WHERE datname = current_database()
  AND (application_name = 'blendsdk-migrations' OR state <> 'idle');
```

A `blendsdk-migrations` session that is idle in transaction holds the advisory lock and will block every runner until it finishes or is terminated.

### 7. Verify what the controller actually exposes before debugging the client

If an operation is missing from the generated client, confirm it reaches the document first. Only routes annotated with `.openapi()` are collected:

```typescript
import { OpenAPIGenerator } from 'blendsdk/codegen';
import { ProductsController } from './controllers/products.controller.js';

const generator = new OpenAPIGenerator({ title: 'My API', version: '1.0.0' });
generator.addController('/api/products', ProductsController);

const document = generator.generate();
console.log(Object.keys(document.paths));
```

If a path is absent here, the route lacks `.openapi()` metadata. If it is present here but absent from the client, the issue is in generation (missing `operationId`, duplicate detection, or filters).

### 8. Run the package's own tests against the disposable PostgreSQL

The test suite expects PostgreSQL at `127.0.0.1:5597`. Starting `test:fast` without it fails with connection errors (`ECONNREFUSED 127.0.0.1:5597`) from the migration runner tests:

```bash
pnpm run db:up        # docker-compose up + 5s readiness sleep
pnpm run test:fast    # vitest, single process, 30s timeout
pnpm run db:logs      # inspect the postgres-test container
pnpm run db:down      # stop and remove volumes
```

The full wrapper `pnpm run test` chains `db:down`, `db:up`, `test:fast`, and `db:down` automatically. Set `MODE` to select a different compose file (`docker/docker-compose${MODE}.yml`).

## Known Pitfalls

- **`generate` warns where `check` fails.** Missing `operationId` and missing 2xx schemas exit `0` from `generate` but exit `1` from `check`. Set `generator.strict: true` so local generation matches CI.
- **Generated files are disposable.** Never edit or rename them by hand; `generate` overwrites them, and any surviving marker-bearing file in the output directory is reported as drift. Hand-written files without the marker are never pruned and never updated — do not put business logic in the output directory.
- **Only pending migrations are editable.** Once a migration is applied, its checksum is recorded; any edit fails snapshot and ledger validation. Fix mistakes with a new migration.
- **The snapshot is byte-canonical.** Formatting it — even with valid JSON — invalidates it. Change desired state by editing the schema and regenerating.
- **Git EOL settings can break the byte gates.** Autocrlf checkouts introduce CRLF and fail both client drift checks and migration/snapshot validation. Pin LF in `.gitattributes`.
- **Migration IDs are UTC timestamps.** Same-second generations and skewed clocks fail with `New migration identifiers must follow existing history.` — the failed attempt writes nothing, so just fix the clock and rerun.
- **Nontransactional migrations trade atomicity for a durable uncertainty marker.** Interruption can leave `UNKNOWN_OUTCOME`/`NONTRANSACTIONAL_DIRTY`, and there is deliberately no repair command — recovery is a reviewed, manual operation.
- **The migration lock is per database.** Concurrent runs against different databases never contend; concurrent runs against the same database fail closed with `LOCKED` rather than interleave.
- **The two config loaders discover differently.** `blendsdk.api.ts` discovery stops at the first `.git` entry; `blendsdk.migrations.ts` discovery walks to the filesystem root. A stray parent config can be picked up by accident — pass `--config` in scripts.
- **Relative artifact paths cannot escape the config directory, and symlinks are rejected everywhere** — config path segments, migration files, snapshots, and migration directories. Absolute paths are trusted; relative ones are bounded.
- **`instanceof` is not a reliable identity check across duplicated package copies.** Use `kind`/`exitCode` (and `formatMigrationError`) for robust handling; the same duplication breaks Zod `instanceof` recognition and silently degrades schemas.
- **Zod identity matters twice.** `instanceof z.ZodType` decides whether a schema is converted at all, and `z.toJSONSchema` requires Zod 4. Duplicate or mismatched copies produce permissive `{ type: 'object' }` schemas, missing query parameters, or `z.toJSONSchema is not a function`.
- **Unrepresentable Zod types become permissive schemas, then `unknown`.** `z.date()` converts to `{}` and generates `unknown` in the client — use ISO string schemas when dates must be typed.
- **Sanitized names are permanent client API.** `delete` becomes `delete_`, tags become camelCase groups, and a missing `operationId` becomes a path-derived name that changes whenever the path or tag changes. Declare explicit ids.
- **The default response envelope is `data`.** For paginated bodies, set `envelope: 'body'` in the route metadata; otherwise the runtime unwraps the wrong field and generated result types describe the wrong shape.
- **`size()` and `scale()` are not chainable.** They return `void`; use `varchar(name, size)` and `numeric(name, size, scale)`.
- **Introspector `could not be mapped` warnings are not failures.** They emit deprecated `any` placeholders — acceptable as a first pass, but supply a `ColumnMapper` before committing generated types.
- **The migration ledger is validated structurally.** Hand-created `blendsdk_migrations` tables fail closed with `INVALID_HISTORY` even when empty, and a verified-empty foreign ledger should be dropped rather than adopted.
