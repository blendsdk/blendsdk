Code Generation ​

blendsdk/codegen has two distinct database-oriented models:

  • SchemaContainer holds application type shapes produced manually or by live database introspection. TypeGenerator turns that container into TypeScript.
  • DatabaseSchema describes desired PostgreSQL objects. PostgreSQLSchemaGenerator can render bootstrap SQL, while the migration workflow compares desired state with a committed snapshot to render incremental SQL.

Bootstrap SQL does not establish migration history. For an application managed by migrations, change DatabaseSchema once and let the snapshot make that change migratable.

Install ​

bash
npm install blendsdk

Add pg, yesql, and postgres-array when connecting through blendsdk/postgresql.

Generate TypeScript from an existing database ​

The introspector reads the live catalog for type generation only:

ts
import { PostgreSQLIntrospector, SchemaContainer, TypeGenerator } from 'blendsdk/codegen';
import { PostgreSQLDatabase } from 'blendsdk/postgresql';

const database = new PostgreSQLDatabase({
  host: process.env.PGHOST,
  port: process.env.PGPORT,
  database: process.env.PGDATABASE,
  user: process.env.PGUSER,
  pass: process.env.PGPASSWORD,
});

try {
  const container = new SchemaContainer();
  await new PostgreSQLIntrospector(database).introspect(container);
  const source = await new TypeGenerator().generate(container);
  console.log(source);
} finally {
  await database.disconnect();
}

This does not create a DatabaseSchema, snapshot, or migration. See the blendsdk/codegen package reference for the exported introspection types.

Author PostgreSQL desired state ​

ts
import { DatabaseSchema } from 'blendsdk/codegen';

const schema = new DatabaseSchema('app');
const customer = schema.table('customer');
customer.bigint('id').primaryKey();
customer.varchar('email', 255);

export default schema;

The same object can feed bootstrap generation and migration normalization. Keep it as the single modeled desired-state definition; do not hand-copy a modeled column into a second DSL.

Generate an incremental migration ​

Point blendsdk.migrations.ts to the schema, then use the committed snapshot as the prior desired state:

ts
import { defineMigrationConfig } from 'blendsdk/codegen';

export default defineMigrationConfig({
  schema: './src/database/schema.ts',
  migrationsDir: './migrations',
});
bash
blendsdk migrate baseline initial
# Later: edit DatabaseSchema once
blendsdk migrate generate add-customer-display-name
blendsdk migrate validate --offline

Review and commit the generated .up.sql and schema.snapshot.json together. Generation is offline and never diffs against production. Use blendsdk migrate create &lt;name&gt; for a data change or PostgreSQL object that DatabaseSchema cannot faithfully represent.

Continue with the database migration guide and the production runbook.

Generate OpenAPI documents ​

OpenAPIGenerator builds an OpenAPI document from BlendSDK route metadata:

ts
import { OpenAPIGenerator } from 'blendsdk/codegen';

const generator = new OpenAPIGenerator({ title: 'Customer API', version: '1.0.0' });
generator.addRoutes('/api', routes);
const document = generator.generate();

For a typed client, drive the same document from a contract file instead: declare your controllers in blendsdk.api.ts with defineApiContract, then run blendsdk api generate to write the committed OpenAPI document and the generated client, and blendsdk api check in CI to fail when either drifts. The API client guide walks through the full flow.

OpenAPI and TypeScript generation create application artifacts. They do not mutate PostgreSQL or advance the migration ledger.
