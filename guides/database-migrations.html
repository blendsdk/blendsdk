PostgreSQL Database Migrations ​

BlendSDK migrations provide a PostgreSQL-only, schema-first workflow. You describe the desired database once with DatabaseSchema; BlendSDK compares it with a committed snapshot and generates reviewable SQL. Production applies only the committed SQL—it never generates migrations from a live database.

This guide starts with the mental model, then walks through a new database, an ordinary schema change, a manual data migration, an existing-database adoption, CI, and production deployment.

The mental model ​

text
DatabaseSchema                 What the application wants
      │
      │ yarn blendsdk migrate generate <name>
      ▼
Versioned SQL migrations       How PostgreSQL moves between versions
      │
      │ yarn blendsdk migrate up
      ▼
PostgreSQL                     What is deployed

schema.snapshot.json           Last committed DatabaseSchema state used for the next diff
blendsdk_migrations            Live PostgreSQL ledger of applied SQL files and checksums

The normal developer loop is:

text
edit DatabaseSchema → generate → review/test SQL → commit schema + migration + snapshot

The snapshot prevents double entry. It gives BlendSDK the previous desired state, so you do not rewrite the same column or constraint in a second migration definition. The schema generator consumes the same desired state as the migration generator, but they have different jobs:

ComponentResponsibility
DatabaseSchemaThe current desired PostgreSQL structure
Schema/code generatorBootstrap SQL or application code derived from the desired structure
Migration generatorIncremental SQL derived from the committed snapshot and current structure
Migration runnerValidates and applies committed migration files
PostgreSQL ledgerProves which exact migration bytes were applied

Install the CLI ​

Install the assembled SDK and PostgreSQL driver:

bash
yarn add blendsdk pg

The blendsdk package installs a project-local executable. With Yarn 1, invoke it as:

bash
yarn blendsdk migrate --help

With npm, use:

bash
npx blendsdk migrate --help

Installing the package does not install a global command. Package scripts automatically place node_modules/.bin on PATH, so a real project will commonly expose short scripts:

json
{
  "scripts": {
    "db:generate": "blendsdk migrate generate",
    "db:create-migration": "blendsdk migrate create",
    "db:validate": "blendsdk migrate validate",
    "db:migrate": "blendsdk migrate up",
    "db:status": "blendsdk migrate status"
  }
}

Arguments are appended normally:

bash
yarn db:generate add-customer-display-name

Configure migrations ​

Create blendsdk.migrations.ts in the project root:

ts
import { defineMigrationConfig } from 'blendsdk/codegen';

export default defineMigrationConfig({
  schema: './src/database/schema.ts',
  migrationsDir: './migrations',
  snapshotFile: './migrations/schema.snapshot.json',
  databaseUrlEnv: 'DATABASE_URL',
  lockTimeoutMs: 5_000,
  statementTimeoutMs: 900_000,
});

Only schema normally needs to be supplied; the other values above are the defaults. Relative paths stay inside the configuration directory. The connection URL comes from the named environment variable and is never written to a migration or snapshot.

The schema module must default-export one DatabaseSchema:

ts
import { DatabaseSchema } from 'blendsdk/codegen';

const schema = new DatabaseSchema('customer-service');
const customer = schema.table('customer');

customer.bigint('id').primaryKey();
customer.varchar('email', 255);

export default schema;

Tutorial 1: Start a new database ​

Generate the complete initial SQL migration and canonical snapshot:

bash
yarn blendsdk migrate baseline initial
yarn blendsdk migrate validate --offline

Your project now resembles:

text
src/database/schema.ts
blendsdk.migrations.ts
migrations/
├── 20260829090000_initial.up.sql
└── schema.snapshot.json

The migration begins with strict metadata followed by ordinary PostgreSQL SQL:

sql
-- blendsdk-migration: 1
-- id: 20260829090000_initial
-- transaction: true
-- from-snapshot: none
-- to-snapshot: <sha256-of-schema.snapshot.json>

CREATE TABLE "public"."customer" (
  "email" varchar(255) NOT NULL,
  "id" bigint NOT NULL
);

Review and commit both generated artifacts. To apply the baseline to an empty PostgreSQL database:

bash
export DATABASE_URL='postgresql://app:password@localhost:5432/customer_service'

yarn blendsdk migrate up --dry-run
yarn blendsdk migrate up
yarn blendsdk migrate status

Expected status progression:

text
PENDING 20260829090000_initial
UP_TO_DATE 20260829090000_initial
UP_TO_DATE

up creates the fixed public.blendsdk_migrations ledger and records the exact migration ID, checksum, lineage, state, application time, and execution duration.

Tutorial 2: Make an ordinary schema change ​

Suppose customers need an optional display name. Edit only src/database/schema.ts:

ts
customer.bigint('id').primaryKey();
customer.varchar('email', 255);
customer.varchar('display_name', 120).nullable();

Generate the incremental migration:

bash
yarn blendsdk migrate generate add-customer-display-name

BlendSDK compares the committed snapshot with the current DatabaseSchema. It creates a migration similar to:

sql
-- blendsdk-migration: 1
-- id: 20260829100000_add-customer-display-name
-- transaction: true
-- from-snapshot: <previous-snapshot-sha256>
-- to-snapshot: <new-snapshot-sha256>

ALTER TABLE "public"."customer"
  ADD COLUMN "display_name" varchar(120);

It also replaces migrations/schema.snapshot.json with the new desired state. Review them together:

bash
git diff -- src/database/schema.ts migrations/
yarn blendsdk migrate validate --offline

Before committing, test on disposable PostgreSQL:

bash
yarn blendsdk migrate up --dry-run
yarn blendsdk migrate up
yarn blendsdk migrate validate
yarn blendsdk migrate status

Commit these three parts as one logical change:

text
src/database/schema.ts
migrations/20260829100000_add-customer-display-name.up.sql
migrations/schema.snapshot.json

Never edit an applied migration. Its exact bytes are checksummed in the live ledger.

What the snapshot does ​

The snapshot is desired-state history. It is not a database dump and is not the live migration ledger.

text
snapshot before change + DatabaseSchema after change = generated migration

Follow these rules:

  • Commit the generated migration and updated snapshot together.
  • Do not hand-edit the snapshot.
  • Do not generate from a developer database and treat that database as the source of truth.
  • Restore interrupted or conflicting artifacts from version control, then run validation again.
  • An UP_TO_DATE generation result means the normalized schema still matches the snapshot.

Tutorial 3: Add a manual data migration ​

Use a manual migration for a data backfill or PostgreSQL behavior outside the modeled schema diff:

bash
yarn blendsdk migrate create backfill-customer-display-name

The created file contains a valid, harmless placeholder:

sql
-- blendsdk-migration: 1
-- id: 20260829103000_backfill-customer-display-name
-- transaction: true
-- from-snapshot: none
-- to-snapshot: none
-- Replace this up no-op with reviewed migration SQL before committing.

SELECT 1;

Replace the no-op with reviewed SQL:

sql
UPDATE "public"."customer"
SET "display_name" = split_part("email", '@', 1)
WHERE "display_name" IS NULL;

Then validate, preview, and apply:

bash
yarn blendsdk migrate validate --offline
yarn blendsdk migrate up --dry-run
yarn blendsdk migrate up
yarn blendsdk migrate status

A manual migration normally does not change schema.snapshot.json. Use generate for modeled schema changes; otherwise the snapshot would still describe the old modeled state and a later generation could attempt the same structural change again.

Add --with-down only when a local reverse operation is genuinely safe. Add --no-transaction only for PostgreSQL statements that cannot run in a transaction. An uncertain nontransactional outcome creates a durable dirty state and blocks further automatic migration.

Renames, destructive changes, and unsupported changes ​

Explicit renames ​

A removed object plus an added object is not enough evidence of a rename. Supply the intent:

bash
yarn blendsdk migrate generate rename-customer \
  --rename-table public.client=public.customer \
  --rename-column public.customer.mail=public.customer.email

Destructive changes ​

Destructive SQL is not emitted without explicit generation-time approval:

bash
yarn blendsdk migrate generate remove-obsolete-column --allow-destructive

This flag permits generation; it does not make the rollout safe. Review data loss, table locking, application compatibility, backups, and recovery before committing.

Safety classifications ​

ClassificationMeaningRequired action
safeBlendSDK can faithfully render the modeled transitionReview and test
cautionSQL is valid but may require rollout or data sequencingDesign the rollout
destructiveThe transition removes modeled stateRequire --allow-destructive and explicit review
ambiguousIntent cannot be inferred, commonly a renameSupply a rename hint or use manual SQL
unsupportedThe model cannot faithfully render the transitionKeep it unmodeled and write reviewed manual SQL

Tutorial 4: Adopt an existing database ​

Do not execute a generated baseline against a database that already contains the modeled objects. Instead:

  1. Represent the existing supported structure with DatabaseSchema.
  2. Generate and review the baseline locally.
  3. Back up the database and stop application or administrative DDL.
  4. Run the structural adoption check.
bash
yarn blendsdk migrate baseline initial
yarn blendsdk migrate validate --offline

export DATABASE_URL='postgresql://app:password@localhost:5432/customer_service'

yarn blendsdk migrate adopt-baseline \
  --confirm-adoption '<database>/<baseline-id>'

The command displays a credential-free target and comparison, repeats the comparison while holding the advisory lock, and records the baseline only when the supported live catalog matches exactly. It does not execute the baseline SQL. A mismatch, unsupported modeled property, dirty ledger, or lost connection records nothing.

After adoption:

bash
yarn blendsdk migrate validate
yarn blendsdk migrate status

Both should report UP_TO_DATE. Adoption is not a force or fake-history command.

Test a local BlendSDK build in a real project ​

Before publishing a new BlendSDK version, build and pack the assembled package from the monorepo:

bash
yarn clean
yarn build

cd packages/blendsdk
npm pack

Install that tarball in a disposable consumer project:

bash
yarn add /path/to/blendsdk-<version>.tgz
yarn add pg
yarn blendsdk migrate --help

Then follow Tutorials 1–3 against disposable PostgreSQL. This verifies the executable, package exports, TypeScript configuration loading, snapshot generation, SQL runner, and consumer dependency resolution before a release is published.

CI workflow ​

CI should validate the immutable files and replay the complete history against disposable PostgreSQL:

bash
yarn blendsdk migrate validate --offline

# Start disposable PostgreSQL and set DATABASE_URL.
yarn blendsdk migrate up --dry-run
yarn blendsdk migrate up
yarn blendsdk migrate validate
yarn blendsdk migrate status

yarn test

Do not treat offline validation alone as migration integration testing.

Production workflow ​

Production uses the same committed SQL that passed review and CI. It never runs baseline, generate, or create:

bash
yarn blendsdk migrate validate
yarn blendsdk migrate up --dry-run
yarn blendsdk migrate up
yarn blendsdk migrate status

Run this from one dedicated deployment job before releasing application replicas. Do not run up independently in every replica.

For changes spanning application and database behavior, prefer expand–migrate–contract:

text
1. Add compatible nullable structures
2. Deploy code that tolerates old and new forms
3. Backfill and verify data
4. Switch reads and writes
5. Remove old structures in a later release

Zero downtime is not guaranteed for every PostgreSQL change. Follow the production migration runbook for locking, deployment stages, failure handling, and forward recovery.

Command reference ​

CommandPurpose
migrate baseline <name>Create the first SQL migration and snapshot
migrate generate <name>Diff the current schema against the committed snapshot
migrate create <name>Create a manual SQL template
migrate validate --offlineValidate local files and lineage without PostgreSQL
migrate validateValidate local files and the live PostgreSQL prefix
migrate up --dry-runConnect, lock, validate, and report pending migrations without mutation
migrate upApply the immutable pending prefix
migrate statusObserve live state without creating or changing the ledger
migrate down --allow-downRevert exactly one latest migration for guarded local use
migrate adopt-baselineProve and record an existing database baseline without running its DDL

Use --config <path> when upward discovery of blendsdk.migrations.ts is not appropriate. Help and version requests exit 0; operational failures exit 1; usage and configuration failures exit 2.

Status and troubleshooting ​

StateMeaningResponse
UP_TO_DATEThe live ledger contains the exact local migration prefixContinue deployment
PENDINGValid local migrations have not been appliedReview, preview, then run up
INVALID_HISTORYFiles, checksums, lineage, or ledger prefix disagreeRestore the reviewed immutable artifacts and investigate; do not force
LOCKEDAnother migration session owns the advisory lockIdentify that job and wait or stop it safely
UNKNOWN_OUTCOMENontransactional work may have executed without a provable resultStop automation and reconcile with a DBA

Production recovery is forward by default. down is deliberately narrow and is not a general production rollback strategy.
