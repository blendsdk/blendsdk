Production Database Migration Runbook ​

Production runs only committed, reviewed migration files. It never generates a schema diff from a live database. Use one dedicated migration job, separate it from application replicas, and keep the ordinary application role unable to change schema where deployment policy permits.

Zero downtime is not guaranteed for every PostgreSQL change. Use expand–migrate–contract when it fits; schedule a maintenance window when lock duration, table rewrite, backfill, or incompatible application behavior cannot be made safe online.

Before the deployment ​

  • Provide DATABASE_URL (or the configured variable) from the deployment secret store. Require PostgreSQL TLS according to your environment; do not put credentials in arguments or logs.
  • Use a migration role with only the DDL/data privileges required by the reviewed release.
  • Confirm infrastructure backups, point-in-time recovery, capacity, and restore testing. BlendSDK migration history is an audit trail, not a backup system.
  • Ensure only one job can advance this database. BlendSDK's advisory lock is the final database guard, not a replacement for deployment orchestration.
  • Set lock and statement timeouts deliberately. A timeout is a failure, never a reason to mark a migration applied manually.

Stage 1: Build and review ​

Generate locally, review exact SQL and safety classification, test on representative disposable PostgreSQL, and commit the .up.sql file with schema.snapshot.json. For expand–migrate–contract, the first release adds compatible nullable structures; later releases backfill and switch reads; only the final release removes the old structure.

bash
blendsdk migrate validate --offline

The release artifact must contain exactly the reviewed immutable migration prefix.

Stage 2: Preflight the target ​

Run from the same network and role as the migration job. Check current state and prove lock availability without mutation:

bash
blendsdk migrate status
blendsdk migrate validate
blendsdk migrate up --dry-run

Stop if history is invalid, a dirty row exists, the target is locked, backups are unhealthy, or the pending list differs from the reviewed release.

Stage 3: Apply once ​

Pause conflicting administrative DDL and start exactly one short-lived migration job:

bash
blendsdk migrate up

Do not run up independently in every application replica. Transactional migrations commit SQL and ledger state together. Explicit nontransactional migrations run alone and retain a blocking dirty state whenever success cannot be proved.

Stage 4: Verify database state ​

Require a successful exit and then verify again:

bash
blendsdk migrate status
blendsdk migrate validate

Expected state is UP_TO_DATE. Capture the sanitized state and migration IDs in deployment logs; never enable routine SQL, data, connection URL, or credential logging.

Stage 5: Roll the application and observe ​

Deploy the application version compatible with the expanded schema, run health checks, and watch database locks, statement latency, error rate, and application compatibility. Complete backfills with separately reviewed application/data tooling. Contract old columns or tables only in a later release after no deployed code depends on them.

If verification or application rollout fails, stop and use forward recovery. Ship a new reviewed migration or an application compatibility fix; do not edit applied files, fake ledger rows, or use an unreviewed production down.

Failure and recovery matrix ​

FailureProven stateRequired response
Advisory lock unavailableNo migration SQL executedConfirm the other job, then retry only after it exits
Validation/history mismatchNo migration SQL executedRestore the reviewed committed files or investigate the target database; never force the ledger
Transactional SQL failureThe failed SQL and ledger insert rolled backDiagnose the failure, correct only a not-yet-applied file according to repository policy, and rerun
Connection loss during transactionPostgreSQL determines rollback or commit; BlendSDK does not claim successRun validate and status; investigate the database when the ledger cannot prove the outcome
Nontransactional interruptionOutcome unknown; a durable dirty row blocks mutationStop, have a DBA inspect the exact database effect, reconcile manually, then ship reviewed forward recovery
Application incompatible after successful migrationThe database migration remains appliedRoll application code forward or back only while schema compatibility permits; otherwise deploy a reviewed forward database fix

Automatic retries are safe only before SQL dispatch and are not provided as a repair mechanism. Never retry unknown nontransactional work blindly.

Existing production database adoption ​

Adoption is a one-time operation, not a shortcut around history. Generate and review the baseline, quiesce all application and administrative DDL, run the comparison preview, verify the credential-free target, and provide the exact <database>/<baseline-id> confirmation. BlendSDK repeats the comparison under its advisory lock before inserting the first ledger row. Any modeled difference aborts without running baseline SQL.

After adoption, run status and validate, retain the committed baseline/snapshot, and use the normal five-stage flow for every later change.

Planned disruption ​

Choose a maintenance window when the safe lock/rewrite duration is unknown, a required column cannot be expanded compatibly, or a backfill and constraint validation cannot be separated. Drain or pause incompatible traffic, communicate the window, apply once, verify, and restore traffic. The goal is controlled disruption with a tested recovery path—not a claim that disruption is always avoidable.
