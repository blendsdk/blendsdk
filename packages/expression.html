expression Overview ​

What It Is ​

blendsdk/expression is a modern, type-safe SQL WHERE clause builder that provides a fluent API for constructing complex queries. It allows developers to create safe and efficient SQL queries with an emphasis on type safety and maintainability.

Key Features ​

  • Type Safety: Utilizes TypeScript for full type safety with generic schema types.
  • Fluent API: Chainable methods for intuitive and readable query construction.
  • Multi-Dialect Support: Designed primarily for PostgreSQL with future plans for MySQL, MSSQL, and SQLite support.
  • Automatic Parameter Management: Prevents SQL injection by managing parameters safely.
  • Advanced Querying Options: Supports JSON operations, full-text search, and subqueries.
  • Debug Mode: Provides detailed compilation information for troubleshooting.
  • Performance-Oriented: Uses an immutable AST for efficient query compilation.

When To Use ​

This package is ideal for scenarios where:

  • You need to build SQL WHERE clauses programmatically while ensuring type safety.
  • Your application interacts with PostgreSQL and requires complex querying capabilities, including JSON and full-text searches.
  • You prioritize maintainability and readability of your database queries in TypeScript.

Architecture ​

The architecture of blendsdk/expression is centered around an immutable Abstract Syntax Tree (AST) pattern, which allows for efficient management and compilation of SQL queries. Key design patterns include:

  • Builder Pattern: The QueryBuilderImpl class utilizes a fluent interface, enabling intuitive query construction through method chaining.
  • Factory Pattern: The library employs factory functions for creating different types of AST nodes, facilitating the organization and structure of the query representation.
  • Immutable Data Structures: Every operation creates a new AST node, preventing accidental mutations and enhancing performance.

Dependencies ​

  • Peer Dependencies: Requires TypeScript version 5.6.0 or higher for development.
  • Build Dependencies: Utilizes @types/node, vitest, and typescript for testing and compilation.
  • What Depends on It: This package underpins other components of the BlendSDK that require complex SQL query generation.

Minimum Example ​

Here is a simple example demonstrating basic usage:

typescript
import { query } from 'blendsdk/expression';

// Create a basic query to select active users above 18 years
const result = query()
  .where('status').equals('active')
  .and('age').greaterThan(18)
  .compile();

console.log(result.sql);     // Outputs: "status = :p1 AND age > :p2"
console.log(result.params);  // Outputs: { p1: 'active', p2: 18 }

expression Core Concepts ​

QueryBuilderImpl ​

What It Is ​

The QueryBuilderImpl class provides the core functionality for creating SQL WHERE clauses using a fluent API. It enables the construction of complex queries while managing SQL parameters to prevent injection attacks.

How It Works ​

The QueryBuilderImpl utilizes a method chaining mechanism to build a hierarchical structure of conditions. It internally maintains an Abstract Syntax Tree (AST) that represents the query structure, which is compiled into a valid SQL statement when requested. The class also employs a ParameterManager to ensure safe handling of query parameters.

Complete Example ​

typescript
import { query, SqlDialect } from 'blendsdk/expression';

// Create a query using QueryBuilder
const result = query({ dialect: SqlDialect.PostgreSQL })
  .where('status').equals('active')
  .and('age').greaterThan(18)
  .compile();

console.log(result.sql);     // Outputs: "status = :p1 AND age > :p2"
console.log(result.params);  // Outputs: { p1: 'active', p2: 18 }

What It Is ​

The ParameterManager class is responsible for handling SQL parameters within the query context. It generates unique parameter names and manages their corresponding values.

How It Works ​

npm install blendsdk/expression

To create a basic SQL WHERE clause, you can use the following minimal setup:

typescript
import { query } from 'blendsdk/expression';

// Create a simple query
const result = query()
  .where('status').equals('active')
  .and('age').greaterThan(18)

console.log(result.params); // Outputs: { p1: 'active', p2: 18 }

Fundamentals ​

Creating a Query ​

To initiate a query, use the query function:

typescript
import { query } from 'blendsdk/expression';

// Begin new query
const qb = query();

Adding Conditions ​

Use the where method to define conditions:

typescript
const result = qb.where('age').greaterThan(20).compile();
console.log(result.sql); // Outputs: "age > :p1"

Combining Conditions ​

You can combine conditions using and and or:

typescript
const result = qb.where('name').equals('John')
  .and('age').greaterThan(18)
  .or('status').equals('active')
  .compile();

console.log(result.sql); // Outputs: "name = :p1 AND age > :p2 OR status = :p3"

Using Subqueries ​

You can also create subqueries:

typescript
const subquery = query().where('id').in([1, 2, 3]);
const result = qb.where('user_id').inSubquery(subquery).compile();
console.log(result.sql); // Outputs: "user_id IN (SELECT * WHERE id IN (:p1, :p2, :p3))"

expression Advanced Patterns ​

Nested Conditions with Grouping ​

When to Use ​

Use nested conditions to group related expressions together for clarity and structure. This pattern is particularly useful when you need to enforce specific logical combinations of conditions.

Complete Example ​

typescript
import { query } from 'blendsdk/expression';

// Create a query with nested conditions
const result = query()
  .where('status').equals('active')
  .and(q => q
    .where('age').greaterThan(18)
    .or('verified').equals(true)
  )
  .compile();

console.log(result.sql); // Outputs: "status = :p1 AND (age > :p2 OR verified = :p3)"
console.log(result.params); // Outputs: { p1: 'active', p2: 18, p3: true }

Explanation ​

This pattern allows complex conditions to be grouped logically. By using a callback function for and, the query can encapsulate a set of conditions that are evaluated together, enhancing readability and maintainability.

Caveats ​

Excessive nesting can lead to confusion. Always ensure that the nesting structure aligns with the logical requirements of the query.

Combining Multiple Comparison Types ​

When to Use ​

This pattern is valuable when you need to apply different comparison types within the same query context. It allows for a more expressive and comprehensive query construction.

Complete Example ​

typescript
import { query } from 'blendsdk/expression';

// Create a query with multiple types of comparisons
const result = query()
  .where('age').greaterThan(21)
  .and('status').equals('active')
  .or('balance').lessThan(100)
  .and('name').like('John%')
  .compile();

console.log(result.sql); // Outputs: "age > :p1 AND status = :p2 OR balance < :p3 AND name LIKE :p4"
console.log(result.params); // Outputs: { p1: 21, p2: 'active', p3: 100, p4: 'John%' }

Explanation ​

By combining different comparison types such as greaterThan, equals, lessThan, and like, you can construct queries that express a wide range of conditions in a concise manner. This enhances the flexibility of your query design.

Caveats ​

Be mindful of operator precedence in SQL and ensure that the logical flow of conditions is clearly defined.

Full-Text Search with Multiple Columns ​

When to Use ​

When your search needs to be conducted across multiple columns, use this pattern to optimize the capability of searching through textual data efficiently.

Complete Example ​

typescript
import { query } from 'blendsdk/expression';

// Create a full-text search across multiple columns
const result = query()
  .search(['title', 'description'], 'TypeScript tutorial')
  .compile();

console.log(result.sql); // Outputs: "to_tsvector('english', title || ' ' || description) @@ plainto_tsquery('english', :p1)"
console.log(result.params); // Outputs: { p1: 'TypeScript tutorial' }

Explanation ​

This pattern allows for full-text searching over an array of columns, utilizing PostgreSQL's capabilities to concatenate column values for searching purposes. It results in a more powerful and comprehensive search capability.

Caveats ​

Ensure that the language used for full-text search matches the linguistic characteristics of the content being searched to improve match accuracy.

Using Subqueries for Advanced Logic ​

When to Use ​

Subqueries are essential for building more complex queries where the result of one query needs to be used as a filter in another. This pattern should be utilized whenever your filtering criteria depend on the results of another query.

Complete Example ​

typescript
import { query } from 'blendsdk/expression';

// Create a query with a subquery
const subquery = query()
  .where('user_id').in([1, 2, 3]);

const result = query()
  .where('post_id').inSubquery(subquery)
  .compile();

console.log(result.sql); // Outputs: "post_id IN (SELECT * WHERE user_id IN (:p1, :p2, :p3))"
console.log(result.params); // Outputs: { p1: 1, p2: 2, p3: 3 }

Explanation ​

Subqueries allow for separating logic into manageable and reusable parts. This method encapsulates the filtering logic in a distinct query, making the main query cleaner and more readable.

Caveats ​

Performance implications should be considered, as using subqueries might lead to less efficient queries compared to using JOIN operations in certain situations.

Debugging Queries with Detailed Information ​

When to Use ​

When you need to inspect the structure and performance of generated SQL queries, this pattern is essential for troubleshooting and optimizing your queries.

Complete Example ​

typescript
import { query, SqlDialect } from 'blendsdk/expression';

Enabling debug mode during the query compilation provides valuable insights such as the SQL generated, the parameters used, and the time taken to compile the query. This is crucial for optimizing performance and debugging issues.

Caveats ​

Only enable debug mode in development or testing environments, as it may expose sensitive information and degrade performance in production.

expression Best Practices ​

Do / Don't Pairs ​

Do: Use Type-Safe Column Access ​

❌ Don't:

typescript
import { query } from 'blendsdk/expression';

const result = query()
  .where('username').equals('admin')
  .compile();

✅ Do:

typescript
import { query } from 'blendsdk/expression';

interface User {
  id: number;
  username: string;
}

const result = query<User>()
  .where('username').equals('admin')
  .compile();

Why? Using type-safe column access ensures that column names are validated against the schema type, reducing runtime errors.

Do: Chain Conditions for Clarity ​

❌ Don't:

typescript
import { query } from 'blendsdk/expression';

const result = query()
  .where('age').greaterThan(30)
  .and('active').equals(true)
  .and('username').equals('admin')
  .compile();

✅ Do:

typescript
import { query } from 'blendsdk/expression';

const result = query()
  .where('age').greaterThan(30)
  .and(q => q
    .where('active').equals(true)
    .or('username').equals('admin')
  )
  .compile();

Why? Chaining conditions within a nested callback improves readability and establishes clear logical grouping.

Do: Use Debug Mode for Troubleshooting ​

❌ Don't:

typescript
import { query } from 'blendsdk/expression';

const result = query()
  .where('status').equals('active')
  .compile();

console.log(result); // Outputs basic result without debug info

✅ Do:

typescript
import { query } from 'blendsdk/expression';

const result = query({ debug: true })
  .where('status').equals('active')
  .compile();

console.log(result.debug); // Outputs debug info including AST

Why? Enabling debug mode provides insights into the query structure and compilation, making it easier to identify issues.

Do: Handle Asynchronous Queries ​

❌ Don't:

typescript
import { query } from 'blendsdk/expression';

const result = query()
  .where('age').greaterThan(21)
  .compile();

// Directly use result without awaiting
console.log(result.sql);

✅ Do:

typescript
import { query } from 'blendsdk/expression';

async function performQuery() {
  const result = query()
    .where('age').greaterThan(21)
    .compile();

  console.log(result.sql); // Ensures we wait for compilation end
}

performQuery();

Why? Wrapping query execution in an async function ensures that all asynchronous operations are handled properly.

Anti-Patterns ​

Avoid Using any Type ​

Using any defeats the purpose of TypeScript's type safety, leading to potential runtime errors.

Don't Over-Nest Conditions ​

Excessive nesting can make your queries hard to read and maintain. Structure queries logically but avoid deep nesting.

Don't Rely on Implicit Returns ​

Always explicitly return the result of a query to avoid undefined behavior.

Performance Tips ​

  • Parameter Reuse: Use the ParameterManager effectively to avoid creating new parameters for identical values, which can lead to unnecessary processing.

  • Batch Conditions: Group similar conditions together to streamline the compilation process and reduce the complexity of the final SQL statement.

  • Minimize Nesting: While nesting can improve clarity, overly nested conditions can negatively impact performance. Strive for balance.

Security Considerations ​

  • Avoid Dynamic SQL: Keep all SQL statements parameterized to prevent SQL injection attacks. Use the provided query builder methods.

  • Validate User Input: Always validate and sanitize user inputs before constructing queries, even if using parameterized statements.

  • Use Debug Mode Carefully: Avoid leaving debug mode enabled in production environments to prevent potential exposure of sensitive information.

expression Troubleshooting ​

Common Errors ​

Invalid Column Error ​

Error Message / Symptom:

"Property 'column_name' does not exist on type 'TSchema'."

Cause: This error occurs when you try to reference a column that is not defined in the schema type (TSchema) you provided to the query builder.

Fix: Ensure that the column you are trying to query is defined in the provided schema type. Here's how to properly structure your query:

typescript
import { query } from 'blendsdk/expression';

interface User {
  id: number;
  active: boolean;
}

const result = query<User>()
  .where('active').equals(true) // Ensure 'active' exists in User
  .compile();

console.log(result.sql); // Outputs: "active = :p1"

Parameter Mismatch Error ​

Error Message / Symptom:

"Expected 2 parameters, received 1."

Cause: This error occurs when the number of parameters provided does not match the number expected by the SQL query, typically seen with BETWEEN, IN, or complex logical comparisons.

Fix: Check the parameters being passed to your queries to ensure they match what the query is expecting. For example, if you are using a BETWEEN condition:

typescript
import { query } from 'blendsdk/expression';

const result = query()
  .where('age').between(18, 65) // Ensure both parameters are provided
  .compile();

console.log(result.sql); // Outputs: "age BETWEEN :p1 AND :p2"

Missing Parameter Value Error ​

Error Message / Symptom:

"Parameter name is missing. JSON operation requires a parameter."

Cause: This error occurs when a JSON operation, such as .jsonContains, is called without a valid parameter value being passed.

Fix: Ensure to provide a valid parameter for JSON operations:

typescript
import { query } from 'blendsdk/expression';

// When searching with a JSON condition, ensure the value is not undefined
const result = query()
  .where('data').jsonContains({ type: 'premium' }) // Ensure valid object is passed
  .compile();

console.log(result.sql); // Outputs: "data @> :p1"

Subquery Must Have Conditions Error ​

Error Message / Symptom:

"Subquery must have at least one condition."

Cause: This occurs when an attempt is made to create a subquery without any conditions defined.

Fix: Add at least one condition in the subquery:

typescript
import { query } from 'blendsdk/expression';

const subquery = query()
  .where('user_id').equals(1); // Add condition to subquery

const result = query()
  .where('post_id').inSubquery(subquery)
  .compile();

console.log(result.sql); // Outputs: "post_id IN (SELECT * WHERE user_id = :p1)"

Error: Dialect Not Implemented ​

Error Message / Symptom:

"Dialect mysql is not yet implemented."

Cause: This error occurs when attempting to use a database dialect that hasn’t been implemented in the package, such as MySQL or SQLite.

Fix: Stick to supported dialects or check for updates if you need to use an unsupported dialect. Currently, the primary supported dialect is PostgreSQL:

typescript
import { query, SqlDialect } from 'blendsdk/expression';

const result = query({ dialect: SqlDialect.PostgreSQL }) // Use PostgreSQL
  .where('status').equals('active')
  .compile();

Debugging Strategies ​

  1. Use Debug Mode: Enable the debug mode when compiling your query. This provides insights into the generated SQL and any parameters used.

    typescript
    const result = query({ debug: true })
  .where('status').equals('active')
  .compile();

console.log(result.debug); // Outputs debug information including AST

  2. Log SQL and Parameters: Always log the SQL and parameter values to check what is being sent to the database.

    typescript
    console.log(result.sql);    // Outputs the SQL command
console.log(result.params); // Outputs the parameter object

  3. Check Console Errors: Monitor your console for any runtime errors and stack traces to understand where the problem might lie in your logic.

  4. Inspect Generated AST: If you have complex queries, inspect the abstract syntax tree (AST) generated to understand the structure and validity of your conditions.

Known Pitfalls ​

  • Using Type any: Avoid using any type as it circumvents TypeScript's type checking, making the code error-prone.

  • Not Validating Column Existence: Always ensure that the columns you are querying exist in the defined schema to prevent runtime errors.

  • Over-Nesting Conditions: While nesting conditions can increase clarity, excessive nesting can lead to confusion and reduced performance.

  • Handling Undefined Values: Always ensure to handle potential undefined values properly, especially when dealing with JSON operations and comparisons that expect parameters.

  • Ignoring SQL Injection Risks: Even when using parameterized statements, validate user inputs to prevent any form of injection despite parameters being managed.
