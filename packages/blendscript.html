BlendScript overview ​

BlendScript is a deterministic expression language for business rules. Formula authors use familiar comparisons, AND, OR, NOT, IN, parentheses, and a fixed set of text functions. Developers embed the package by defining a schema and supplying records.

Use BlendScript when non-developers need to author portable Boolean or scalar rules without receiving access to JavaScript or the host application.

The public runtime has three functions:

  • validateExpression checks syntax and types.
  • compileExpression creates an opaque reusable expression.
  • evaluateExpression evaluates that expression for one record.

The package has no runtime dependencies and does not use dynamic code, I/O, custom functions, or host object traversal. Storage and user-interface concerns belong to the embedding application.

Both private and umbrella imports expose the same API:

typescript
import { compileExpression } from 'blendsdk/blendscript';
import { compileExpression } from 'blendsdk/blendscript';

Core concepts ​

Schema ​

A schema is the allowlist of fields and their types. Supported field types are string, number, boolean, and scalar. A scalar field accepts a string or finite number without changing its runtime representation. Any field may be nullable.

typescript
const schema = {
  Country: { type: 'string' },
  Amount: { type: 'number' },
  Item: { type: 'scalar' },
  Approved: { type: 'boolean', nullable: true },
} as const;

Field matching is exact and case-sensitive. Every schema field must exist in every evaluated record.

Formula types ​

BlendScript infers one result type and nullability. It does not coerce operator operands: text "10" is not number 10, and TRUE is not number 1. Use tryNumber or text when a scalar field needs an explicit concrete representation.

Compile and reuse ​

Compilation validates the complete formula and returns an opaque handle. Reuse that handle for many records with the same schema and loaded package instance. The handle is not serializable or a persistence/interchange format. Store the source and schema, then compile again after loading or after upgrading BlendSDK.

Compatible minor releases preserve parsing, binding, results, and diagnostics for previously valid source/schema pairs. An incompatible change requires a semantic-version major release and migration guidance.

Diagnostics ​

Formula problems are returned, not thrown. Invalid host API input throws BlendScriptApiError. This separation lets an editor show friendly formula feedback while programming mistakes remain visible.

Evaluation ​

Evaluation is left-to-right. AND and OR short-circuit, so an unselected branch is not evaluated or charged against the work limit.

Host boundary ​

Schemas and records must be caller-materialized ordinary objects with own data properties. JavaScript proxies are outside BlendScript's no-host-code guarantee because inspecting them can run proxy traps; the embedding application must materialize them before calling the API.

The host owns authorization, sensitive-data handling, persistence, transport, encryption, logging, and throughput controls. BlendScript does not store or log source or record values.

BlendScript is unrelated to blendsdk/expression and makes no compatibility or ancestry claim with Filtrex.

Basic usage ​

1. Define the available fields ​

typescript
const options = {
  schema: {
    Country: { type: 'string' },
    Enabled: { type: 'boolean' },
  },
  expectedResult: 'boolean',
} as const;

2. Validate while editing ​

typescript
const validation = validateExpression('Country == "NL" AND Enabled == TRUE', options);

if (!validation.ok) {
  showDiagnostics(validation.diagnostics);
}

3. Compile and evaluate ​

typescript
const compilation = compileExpression('Country == "NL" AND Enabled == TRUE', options);

if (compilation.ok) {
  const result = evaluateExpression(compilation.expression, {
    Country: 'NL',
    Enabled: true,
  });
}

A successful evaluation returns { ok: true, value }. A failed evaluation returns one diagnostic.

Advanced patterns ​

Make precedence visible ​

AND binds more strongly than OR. Parentheses make longer rules easier to review:

text
(Country == "NL" OR Country == "BE") AND Enabled == TRUE

Use membership for fixed choices ​

text
Status IN ("New", "Pending", "Review")

IN members are literals. An empty list, a field in the list, or a trailing comma is invalid.

Use bracketed field names ​

text
[Order Total] >= 1000 AND [Customer Segment] == "Gold"

A closing bracket inside a field name is doubled: [Closing]]Bracket].

Handle null explicitly ​

text
OptionalCode == NULL
isBlank(OptionalComment)

isEmpty, isBlank, and tryNumber accept null. Other operations return a BS_NULL_NOT_ALLOWED diagnostic when runtime null reaches them.

Convert mixed scalar fields explicitly ​

Use a scalar schema field when source data may preserve either a string or a finite number. Convert it before a concrete-type operation:

text
tryNumber(Item) != NULL AND tryNumber(Item) > 1
text(Item) == "001"

tryNumber accepts only complete BlendScript decimal text. Invalid, blank, partial, and non-finite text returns NULL. text preserves strings exactly, including leading zeroes.

Compile once ​

Compile a stable rule once and reuse the returned handle. Do not share a compiled handle between two separately loaded copies of the package; compile the saved source in each process.

Best practices ​

  • Give formula authors a small, documented schema with business-friendly field names.
  • Use expectedResult: 'boolean' when the host requires a yes/no rule.
  • Validate on edit, compile on save or load, and reuse the compiled handle for records.
  • Show diagnostic messages with their source location; do not expose raw internal exceptions.
  • Prefer canonical AND, OR, NOT, TRUE, FALSE, and NULL spellings in user documentation.
  • Add parentheses when a formula mixes AND and OR.
  • Use isBlank when whitespace-only text should count as missing.
  • Remember that normal text comparisons and contains checks are case-sensitive.
  • Test boundary values and nullable records in the embedding application.
  • Treat source and records as untrusted input even though BlendScript exposes no host capabilities.

Avoid translating missing record fields to null. A missing field is a different data error and produces BS_MISSING_FIELD.

Do not attempt to extend the language through host functions. The fixed built-in set is part of the security and determinism contract.

Common scenarios ​

Country eligibility ​

text
Country IN ("NL", "BE", "DE")

Minimum amount with approval ​

text
Amount >= 1000 AND Approved == TRUE

Missing customer name ​

text
isBlank(CustomerName)

Case-insensitive status ​

text
equalsIgnoreCase(Status, "pending")

Search normalized text ​

text
contains(lower(Description), "urgent")

Optional code ​

text
OptionalCode == NULL OR startsWith(OptionalCode, "EU-")

Mixed alternatives ​

text
(CustomerType == "Gold" OR Amount >= 5000) AND Blocked == FALSE

These formulas operate only on fields declared by the embedding application.

Testing patterns ​

Applications should test their schemas and business formulas as data-driven cases.

typescript
const compilation = compileExpression(source, {
  schema,
  expectedResult: 'boolean',
});

expect(compilation.ok).toBe(true);
if (compilation.ok) {
  expect(evaluateExpression(compilation.expression, record)).toEqual({
    ok: true,
    value: expected,
  });
}

Include:

  • one matching and one non-matching record;
  • exact boundary values for numeric comparisons;
  • empty, blank, mixed-case, and Unicode text;
  • null for every nullable field;
  • a missing field and a wrong runtime type;
  • formula diagnostics with stable code and span;
  • repeated evaluation of one compiled handle.

Assert diagnostic codes for application logic. Messages are written for people, while codes are the stable machine-readable contract.

API reference ​

validateExpression ​

typescript
validateExpression(source: string, options: ExpressionOptions): ValidationResult

Checks syntax, schema references, operand types, limits, and an optional expectedResult. Success contains resultType and referencedFields.

compileExpression ​

typescript
compileExpression(source: string, options: ExpressionOptions): CompilationResult

Performs the same checks and returns a fresh opaque CompiledExpression on success.

evaluateExpression ​

typescript
evaluateExpression(
  expression: CompiledExpression,
  data: Readonly<Record<string, ExpressionValue>>,
): EvaluationResult

Preflights the complete record in schema order, then interprets the compiled expression.

Limits ​

Source 16,384 code units; tokens 4,096; text 4,096 code units; field name 256 code units; schema fields 1,024; nesting 64; evaluation work 10,000 steps; source diagnostics 20.

BlendScriptApiError is the only runtime class export. All remaining public exports are TypeScript types.
