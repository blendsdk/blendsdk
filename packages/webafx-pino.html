webafx-pino Overview ​

What It Is ​

blendsdk/webafx-pino is a structured logging plugin for WebAFX, leveraging the Pino logging library. It adapts Pino behind the BlendSDK Logger interface, offering a unified and efficient logging solution for web applications.

Key Features ​

  • Seamless integration with the BlendSDK Logger interface.
  • Support for structured JSON logging with customizable options.
  • Request-scoped logging capabilities for enhanced context during HTTP requests.
  • Log level normalization, ensuring consistent logging levels across different applications.
  • Redaction of sensitive data in logs to maintain privacy and security.
  • Option to pretty-print log output for easier debugging during development.

When To Use ​

  • When building web applications that require robust logging capabilities.
  • If you need to integrate with the BlendSDK ecosystem and want a consistent logging interface.
  • When structured logging and the ability to redact sensitive information are crucial for compliance and debugging.
  • If your application leverages the WebAFX framework and you want to enhance logging without a complex setup.

Architecture ​

The blendsdk/webafx-pino package follows a modular design, consisting of several key components:

  • LoggerProvider: An abstract base class implemented by specific logger providers, managing lifecycle methods and request-scoped logger creation.
  • PinoLoggerProvider: A specific implementation that wraps the Pino logging library, providing seamless integration with the BlendSDK Logger interface.
  • Plugin Factory: Functions (createLoggerPlugin, pinoLoggerPlugin) that facilitate the easy creation of logger plugins for use within WebAFX applications.

The architecture employs design patterns such as the Adapter pattern (for integrating with external logging libraries) and the Factory pattern (for creating logger instances).

Dependencies ​

Direct Dependencies ​

  • Pino (^9.6.0): The underlying logging library.
  • Pino-HTTP (^10.4.0): HTTP-specific logging enhancements for Pino.

Peer Dependencies ​

  • blendsdk/webafx (5.42.0): Required for integration with the BlendSDK.
  • Pino-Pretty (>=11.0.0): Optional dependency for pretty-printing logs.

Minimum Example ​

Below is a succinct example demonstrating how to use blendsdk/webafx-pino to create a logger and log an informational message:

typescript
import { PinoLoggerProvider } from 'blendsdk/webafx-pino';

async function main() {
  const logger = new PinoLoggerProvider({ level: 'info', pretty: true });
  await logger.info('Server started', { port: 3000 });
  await logger.shutdown();
}

main().catch((error) => console.error('Error:', error));

webafx-pino Core Concepts ​

LoggerProvider ​

What It Is ​

LoggerProvider is an abstract base class that defines the core logging behavior for all logger implementations in the BlendSDK ecosystem. It serves as the foundation for creating concrete logger providers, making it easier to adapt different logging libraries to the BlendSDK Logger interface.

How It Works ​

The LoggerProvider class includes methods for logging messages at different levels (info, error, warn, debug) along with lifecycle methods for health checks and graceful shutdowns. Concrete implementations, such as PinoLoggerProvider, extend this class to provide specific logging behavior and integrate with the underlying logging libraries, translating BlendSDK logging calls into their respective formats.

Complete Example ​

typescript
import { PinoLoggerProvider } from 'blendsdk/webafx-pino';

  const logger = new PinoLoggerProvider({ level: 'info' });
  await logger.info('Application started');
  await logger.shutdown();
}

main().catch((error) => console.error('Error:', error));

PinoLoggerProvider ​

What It Is ​

PinoLoggerProvider is a specific implementation of the LoggerProvider class that wraps the Pino logging library, offering a seamless integration with the BlendSDK Logger interface. It utilizes Pino's structured logging capabilities, allowing for enhanced flexibility and performance in logging operations.

How It Works ​

PinoLoggerProvider leverages the Pino library to provide various log levels and structured logging. It takes care of normalizing log levels, applying redaction to sensitive data, and creates child loggers for request-scoped logging. This class translates calls to the BlendSDK logging methods into the appropriate Pino functions.

Complete Example ​

Plugin Creation ​

What It Is ​

The plugin creation functions, specifically createLoggerPlugin and pinoLoggerPlugin, provide a structured way to integrate the PinoLoggerProvider into WebAFX applications. They facilitate the setup of logging within an application, allowing for easy configuration and installation of logging services.

How It Works ​

Using these factory functions, developers can easily instantiate a logger provider and automatically register it for use in WebAFX applications. createLoggerPlugin accepts an existing LoggerProvider, while pinoLoggerPlugin creates a PinoLoggerProvider instance and wraps it in a plugin definition.

Complete Example ​

typescript
import { pinoLoggerPlugin } from 'blendsdk/webafx-pino';
import express from 'express';

const app = express();

app.use(pinoLoggerPlugin({ level: 'debug', pretty: true }));

app.get('/', (req, res) => {
  req.log.info('Home page accessed');
  res.send('Hello World');
});

// Start the server...

Summary ​

The blendsdk/webafx-pino package provides an efficient way to implement structured logging in BlendSDK applications using the Pino library. By defining a clear interface through the LoggerProvider abstract class and extending it via PinoLoggerProvider, along with easy plugin creation, it streamlines the logging process while maintaining flexibility and performance.

webafx-pino Advanced Patterns ​

1. Request-Scoped Logging with Middleware Integration ​

When to Use ​

This pattern is useful when you need to attach a request-specific logger in a web application. It captures relevant request context (like request IDs) for logging while processing HTTP requests, allowing better traceability in logs.

Complete Code Example ​

typescript
import express from 'express';
import { pinoLoggerPlugin } from 'blendsdk/webafx-pino';

const app = express();

app.use(pinoLoggerPlugin({ level: 'info', pretty: true }));

app.use((req, res, next) => {
  req.log.info('Incoming request', { method: req.method, url: req.originalUrl });
  next();
});

app.get('/', async (req, res) => {
  await req.log.info('Home page accessed');
  res.send('Hello World');
});

app.listen(3000, () => {
  console.log('Server is running on port 3000');
});

Value of This Pattern ​

By attaching a request-scoped logger to each incoming request, you can log detailed information about the request's lifecycle. This is crucial for debugging and monitoring application behavior. It improves the visibility of request handling and errors specific to each transaction.

Caveats or Performance Considerations ​

Make sure that the middleware is registered early in the request handling chain to ensure that all subsequent handlers can access the request-specific logger. Additionally, avoid logging sensitive information to maintain security and compliance.

2. Structured Logging and Data Redaction ​

When to Use ​

This pattern is ideal when you need to log sensitive information but also protect user privacy by redacting certain fields (like authentication tokens) from logs while still logging other details.

Complete Code Example ​

typescript
import { PinoLoggerProvider } from 'blendsdk/webafx-pino';

async function main() {
  const logger = new PinoLoggerProvider({
    level: 'info',
    redact: ['req.headers.authorization', 'req.headers.cookie'],
  });
  
  await logger.info('User login attempt', {
    req: {
      headers: {
        authorization: 'Bearer secret-token',
        cookie: 'session=abc123'
      }
    },
    user: { id: 1, name: 'John Doe' }
  });
  
  await logger.shutdown();
}

main().catch((error) => console.error('Error:', error));

Value of This Pattern ​

This pattern allows you to retain structured logging benefits while preventing sensitive data from being logged. This is essential for maintaining compliance with data protection regulations and ensuring user trust.

Caveats or Performance Considerations ​

Ensure that redaction paths are properly defined and tested, as incorrect settings might lead to sensitive data being inadvertently logged. Additionally, structured logs may have performance implications due to nested objects; choose what you log wisely.

3. Dynamic Log Level Control ​

When to Use ​

This pattern is useful for applications where the logging level needs to change dynamically based on certain conditions (e.g., environment variables or user settings).

Complete Code Example ​

typescript
import { PinoLoggerProvider } from 'blendsdk/webafx-pino';

  const logger = new PinoLoggerProvider({ level: currentLogLevel });

  await logger.info('Logging at the current log level');
  
  if (currentLogLevel === 'debug') {
    await logger.debug('This is a debug message with more details.');
  }

  await logger.shutdown();
}

main().catch((error) => console.error('Error:', error));

Value of This Pattern ​

This allows for flexibility in logging based on the environment. For instance, you can set your application to log less information in production for performance and privacy reasons, while allowing detailed logging in the development or staging environments for debugging.

Caveats or Performance Considerations ​

Changing the log level at runtime can impact performance. Ensure that the chosen log level is appropriate for the environment, and consider using caching mechanisms to avoid repeated checks of the log level if it doesn’t change frequently.

4. Combining Logging with Error Handling ​

When to Use ​

This pattern is crucial when you want to manage application errors effectively by logging error details while also providing a fallback mechanism for application operations.

Complete Code Example ​

Caveats or Performance Considerations ​

Excessive logging during errors can lead to performance degradation, particularly if the same error occurs repeatedly. Consider implementing rate limiting or aggregating certain error logs to avoid overwhelming your logging infrastructure.

webafx-pino Best Practices ​

Do / Don't Pairs ​

Do: Use Structured Logging ​

❌ Wrong:

typescript
await logger.info('User logged in');

✅ Correct:

typescript
await logger.info('User logged in', { userId: 123, timestamp: Date.now() });

Reason: Structured logging provides context that aids in debugging and analysis. Always include relevant data along with your log messages.

Do: Enable Redaction for Sensitive Data ​

❌ Wrong:

typescript
await logger.info('Incoming request', { req: { headers: { authorization: 'Bearer token' } } });

✅ Correct:

typescript
const logger = new PinoLoggerProvider({ redact: ['req.headers.authorization'] });
await logger.info('Incoming request', { req: { headers: { authorization: 'Bearer token' } } });

Reason: Redacting sensitive information helps prevent data leaks and ensures compliance with privacy regulations.

Don't: Log Raw Error Messages ​

❌ Wrong:

typescript
try {
  // some operation
} catch (error) {
  await logger.error(error.message);
}

✅ Correct:

typescript
try {
  // some operation
} catch (error) {
  await logger.error('Operation failed', { error: error.message, stack: error.stack });
}

Reason: Always provide context for errors. Logging the error message alone loses the opportunity to capture useful debugging information.

Don't: Use Hardcoded Log Levels ​

❌ Wrong:

typescript
const logger = new PinoLoggerProvider({ level: 'debug' });

✅ Correct:

typescript
const logger = new PinoLoggerProvider({ level: process.env.LOG_LEVEL ?? 'info' });

Reason: Using environment variables for log levels allows dynamic adjustments based on deployment settings (e.g., debug in development, info in production).

Anti-Patterns ​

Anti-Pattern: Ignoring Logger Shutdown ​

This commonly happens where developers forget to call the shutdown() method after logging operations are complete. This leads to loss of logged data as the logger might not flush all messages before the application exits.

Solution: Always call await logger.shutdown() in the application termination routine or in a finally block after logging is completed.

Anti-Pattern: Excessive Logging ​

Logging too much information, especially at debug or info levels, can lead to performance bottlenecks and large log files that complicate monitoring.

Solution: Limit how much data is logged, focusing on essential information to reduce log noise. Use log levels wisely and filter out unnecessary logging in production.

Performance Tips ​

Tip 1: Use Proper Log Levels ​

Set log levels correctly to ensure that only necessary information is logged at appropriate levels. For example, use error for critical issues and info for standard operational messages.

Tip 2: Buffer Log Entries ​

If your application generates a high volume of logs, consider buffering log entries and writing them in batches to avoid performance penalties from frequent I/O operations.

Tip 3: Prefetching Data for Logging ​

Fetch any required data to be logged in advance, rather than fetching it in the logging call, to avoid additional latency from database or service calls.

Security Considerations ​

Secure Logging Configuration ​

  • Always use redaction for any fields that may contain sensitive information (like user tokens or passwords).
  • Ensure log files have restricted access permissions to prevent unauthorized reading.
  • Avoid logging sensitive data directly. Instead, handle sensitive fields with redaction or anonymization techniques to preserve user privacy.

webafx-pino Troubleshooting ​

Common Errors ​

TypeScript Compiler Error: "Cannot find module 'blendsdk/webafx'" ​

Cause: This usually occurs when the blendsdk/webafx package is not installed or not properly linked to your project. Make sure that all peer dependencies are installed.

Fix:

  1. Install the required peer dependency:
    bash
    npm install blendsdk/webafx@5.42.0
  2. Ensure your node_modules directory is accessible and includes the package.

Error: "Invalid log level: 'xyz'" ​

Cause: This error occurs when an unsupported log level is passed to the PinoLoggerProvider. The valid log levels are fatal, error, warn, info, debug, trace, and silent.

Fix:

  1. Ensure you're using a valid log level when initializing the logger:
    typescript
    import { PinoLoggerProvider } from 'blendsdk/webafx-pino';

const logger = new PinoLoggerProvider({ level: 'info' }); // Make sure 'info' or another valid level is used

Error: "Request scoped logger is undefined" ​

Cause: This might happen if the request ID is not set or if the middleware that sets the logger was not correctly applied before accessing req.log.

Fix:

  1. Ensure the middleware is applied in the correct order:
    typescript
    import express from 'express';
import { pinoLoggerPlugin } from 'blendsdk/webafx-pino';

const app = express();
app.use(pinoLoggerPlugin({ level: 'info' })); // Apply logger middleware first

app.use((req, res, next) => {
    req.log.info('Incoming request');
    next();
});

Error: "Logger shutdown was not awaited" ​

Cause: Not awaiting the shutdown method may result in losing some log entries if the application exits before the logger finishes flushing.

Fix:

  1. Always await the shutdown() method before exiting:
    typescript
    async function main() {
    const logger = new PinoLoggerProvider({ level: 'info' });
    await logger.info('Server started');
    await logger.shutdown(); // Ensure to wait for shutdown
}

main().catch(error => console.error('Error:', error));

Debugging Strategies ​

  1. Increase Log Level: Temporarily increase your logger's verbosity to capture more detailed logs. Set it to debug or trace during development to gather more context.

    typescript
    const logger = new PinoLoggerProvider({ level: 'debug' });

  2. Check Environment Variables: Ensure that your runtime environment variables (e.g., LOG_LEVEL) are set correctly and are accessible when your application runs.

  3. Examine Middleware Order: Check the order of your middleware in Express. Logging middleware should generally be the first middleware applied to the request lifecycle.

  4. Use a Log Collector: Implement a writable stream to collect logs in tests, ensuring that you can inspect what is being outputted.

    typescript
    function createLogCollector(): { stream: Writable; entries: any[] } {
    const entries: any[] = [];
    const stream = new Writable({
        write(chunk, _encoding, callback) {
            try {
                entries.push(JSON.parse(chunk.toString()));
            } catch {
                entries.push(chunk.toString());
            }
            callback();
        },
    });
    return { stream, entries };
}

  5. Mock External Dependencies: During unit tests, you may want to mock external dependencies to ensure your tests focus solely on the logger's functionality.

Known Pitfalls ​

  • Neglecting Proper Redaction: Always ensure sensitive data is redacted. Forgetting to set redact fields in your logger provider configuration may lead to sensitive data being logged.

  • Not Using Async/Await: In apps using async/await, failing to await logger methods can lead to missed logging due to the asynchronous nature of logging flushes.

  • Ignoring TypeScript Strict Checks: Ensure that the correct types are used when logging. Avoid using any or unknown as this contradicts the strict mode of TypeScript, leading to runtime errors.

  • Over-Logging in Production: While it is crucial to capture enough data for debugging, excessive logging in production can lead to performance issues. Configure thresholds appropriately and adjust log levels based on the application environment.
