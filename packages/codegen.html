codegen Overview ​

What It Is ​

blendsdk/codegen is a powerful TypeScript library designed for code generation, enabling developers to create schema definitions and automatically generate corresponding TypeScript types, interfaces, and type aliases with a fluent API. This library enhances productivity by providing stringent type-checking capabilities and improving code maintainability.

Key Features ​

  • Fluent API: Intuitive builder pattern for seamless schema creation.
  • Schema Registry: Centralized management for easy reference and resolution of schemas.
  • Type Generation: Automatic, formatted TypeScript code generation aligned with defined schemas.
  • Complex Types Support: Capabilities for nested objects, arrays, unions, and references.
  • Type Modifiers: Handling of optional, nullable, and array types for precise type definitions.
  • JSDoc Integration: Automatically generates documentation comments for better code understanding.

When To Use ​

This package is ideal when you need to:

  • Generate TypeScript types from complex schemas with consistent rules.
  • Improve your codebase's maintainability and clarity through strong typing.
  • Create RESTful or GraphQL APIs that require rigorous type definitions and validation.
  • Maintain coherent documentation alongside the code using JSDoc comments.

Architecture ​

The architecture of blendsdk/codegen revolves around a few key design patterns:

  • Builder Pattern: Facilitates flexible and fluent schema construction.
  • Registry Pattern: Manages schema instances in a central registry for easy retrieval and conflict prevention.
  • Factory Pattern: Used for creating different types of schemas and their corresponding TypeScript representations.

Dependencies ​

blendsdk/codegen depends on several packages for database and schema management:

  • Dependencies:
    • blendsdk/cmdline: ^5.51.1
    • blendsdk/dbcore: ^5.51.1
    • blendsdk/postgresql: ^5.51.1

    • zod: ^4.4.3

Minimum Example ​

Here's a minimal example demonstrating the core functionality of blendsdk/codegen:

typescript
import { Schema, ObjectSchema, StringSchema, NumberSchema, TypeGenerator } from 'blendsdk/codegen';

// Create a schema registry
const schema = new Schema();

// Define a simple user schema
const userSchema = new ObjectSchema(schema)
  .named('User')
  .properties({
    id: new NumberSchema(schema).description('Unique user identifier'),
    name: new StringSchema(schema).description('User display name')
  });

const typeGen = new TypeGenerator(schema);
const code = await typeGen.generate();

console.log(code);

This example demonstrates the setup of a schema and the generation of corresponding TypeScript types through a comprehensive API, providing clarity and type safety.

Introspection ​

What It Is ​

Introspection in blendsdk/codegen allows you to retrieve detailed information about database schemas, including tables, columns, constraints, and relationships. This functionality provides developers the ability to dynamically generate types and enforce business rules based on the underlying database structure.

How It Works ​

The PostgreSQLIntrospector class uses SQL queries to fetch schema information from a PostgreSQL database. By executing a predefined introspection SQL command (like INTROSPECTION_SQL), it retrieves detailed metadata for database objects and maps this information into TypeScript types through a provided mapper function. The introspection process constructs a schema that aligns with the data structure of the database.

Complete Example ​

typescript
import { PostgreSQLDatabase } from 'blendsdk/postgresql';
import { SchemaContainer, PostgreSQLIntrospector } from 'blendsdk/codegen';

async function introspectDatabase() {
  // Configure database connection
  const db = new PostgreSQLDatabase({ connectionString: 'your-connection-string' });
  const schemaContainer = new SchemaContainer();
  
  // Create an instance of the PostgreSQL Introspector
  const introspector = new PostgreSQLIntrospector(db);

  // Introspect and map the database schema
  await introspector.introspect(schemaContainer, (column, scope) => {
    // Custom mapping logic to create schema objects...
    return scope.string(); // Example placeholder mapping
  });

  console.log(JSON.stringify(schemaContainer.getAll(), null, 2));
}

introspectDatabase().catch(console.error);

Type Generation ​

What It Is ​

Type Generation is the process of creating TypeScript type definitions from structured schema definitions. This feature allows developers to automatically generate accurate and type-safe TypeScript interfaces and type aliases that reflect their application data models.

How It Works ​

The TypeGenerator class reads schema definitions from a SchemaContainer and translates them into TypeScript syntax. It supports various TypeScript features such as interfaces, type aliases, optional and array types, as well as JSDoc comments for documentation. The generated code adheres to TypeScript standards ensuring that types are robust and maintainable.

Complete Example ​

typescript
import { SchemaContainer, TypeGenerator, ObjectSchema, StringSchema, NumberSchema } from 'blendsdk/codegen';

async function generateTypes() {
  const schema = new SchemaContainer();

  // Define user schema
  const userSchema = new ObjectSchema(schema)
    .named('User')
    .properties({
      id: new NumberSchema(schema).description('Unique user identifier'),
      name: new StringSchema(schema).description('User display name')
    });

  // Generate TypeScript types
  const typeGen = new TypeGenerator();
  const output = await typeGen.generate(schema);

  console.log(output);
}

generateTypes().catch(console.error);

What It Is ​

codegen Advanced Patterns ​

Composite Schema Generation with Introspection ​

When to Use ​

This pattern is useful when you need to generate TypeScript types based on an introspection of a PostgreSQL database schema, allowing for large and complex schemas to be reflected accurately in your TypeScript models.

Complete Code Example ​

typescript
import { PostgreSQLDatabase } from 'blendsdk/postgresql';
import { SchemaContainer, PostgreSQLIntrospector } from 'blendsdk/codegen';

async function generateTypesFromIntrospection() {
  // Connect to the PostgreSQL database
  const db = new PostgreSQLDatabase({
    connectionString: 'your-connection-string',
  });
  
  // Create a schema container to hold the definitions
  const schemaContainer = new SchemaContainer();
  
  // Create an introspector instance
  const introspector = new PostgreSQLIntrospector(db);
  
  // Run introspection and generate types based on the database schema
  await introspector.introspect(schemaContainer, (column) => {
    return schemaContainer.scope(column.schema_name).object({
      [column.column_name]: schemaContainer.string() // Adjust mapping as required
    });
  });

  // Generate TypeScript code from the schema
  const typeGen = new TypeGenerator();
  const tsCode = await typeGen.generate(schemaContainer);
  
  console.log(tsCode);
}

generateTypesFromIntrospection().catch(console.error);

Explanation ​

This pattern leverages the introspection capabilities of PostgreSQLIntrospector to dynamically read the schema from the database, providing a scalable way to define TypeScript models without hardcoding them. The mapping function allows developers to customize how each column is represented in TypeScript.

Caveats ​

  • Ensure that the database connection string is correct and the database is accessible.
  • The mapping function should properly handle the variety of PostgreSQL types to ensure accurate TypeScript representations.

Generating OpenAPI Specifications from Zod Schemas ​

When to Use ​

This pattern is particularly valuable when developing APIs that utilize Zod for validation, allowing for seamless generation of OpenAPI documentation based on existing schema definitions.

Complete Code Example ​

typescript
import { OpenAPIGenerator } from 'blendsdk/codegen';
import { z } from 'zod';

async function generateOpenAPISpec() {
  const apiGen = new OpenAPIGenerator({
    title: 'Test API',
    version: '1.0.0',
  });

  apiGen.addRoutes('/api', [
    {
      method: 'post',
      path: '/create-user',
      validation: z.object({
        username: z.string().min(3),
        email: z.string().email(),
      }),
      openapi: {
        summary: 'Create a new user',
      },
    },
  ]);

  const openAPISpec = apiGen.generate();

  console.log(JSON.stringify(openAPISpec, null, 2));
}

generateOpenAPISpec().catch(console.error);

Explanation ​

This pattern integrates Zod validation directly into your routes, leveraging the OpenAPIGenerator to create a valid OpenAPI specification that reflects the requirements defined in your Zod schema. Each route can thus automatically document its expected input, refining your API's usability.

Caveats ​

  • Ensure that Zod schemas accurately represent your data models to prevent discrepancies in the generated OpenAPI documentation.
  • Validate that the OpenAPI documentation functions as intended with tools like Swagger UI.

Dynamic Route Definitions with Multiple Controllers ​

When to Use ​

This pattern is beneficial in scenarios where different controllers handle various aspects of your application, allowing for cleaner separation of concerns while still enabling centralized OpenAPI documentation generation.

Complete Code Example ​

typescript
import { OpenAPIGenerator } from 'blendsdk/codegen';
import { z } from 'zod';

class UsersController {
  routes() {
    return [
      {
        method: 'get',
        path: '/users',
        openapi: { summary: 'List users' },
      },
      {
        method: 'post',
        path: '/users',
        validation: z.object({
          name: z.string(),
          email: z.string().email(),
        }),
        openapi: { summary: 'Create user' },
      }
    ];
  }
}

class ProductsController {
  routes() {
    return [
      {
        method: 'get',
        path: '/products',
        openapi: { summary: 'List products' },
      }
    ];
  }
}

async function generateCompleteApiSpec() {
  const apiGen = new OpenAPIGenerator({
    title: 'My API',
    version: '1.0.0',
  });

  apiGen.addController('/api/users', UsersController);
  apiGen.addController('/api/products', ProductsController);

  const spec = apiGen.generate();

  console.log(JSON.stringify(spec, null, 2));
}

generateCompleteApiSpec().catch(console.error);

Explanation ​

By using multiple controllers, this pattern allows for organized, modular route definitions that can be modified independently. Each controller can encapsulate its own logic while contributing to a unified API specification.

Caveats ​

  • Ensure that all controllers follow the logical structure expected by the OpenAPIGenerator, including proper openapi metadata to generate the documentation correctly.
  • Evaluate that the routes don't conflict in terms of URL paths or methods to maintain API integrity.

Nested Object Generation with Fluent API ​

When to Use ​

Use this pattern when you need to create complex data structures with nested objects and relationships, especially when building APIs where such models are prevalent.

typescript

function defineNestedSchema() {

    .named('User')

This pattern emphasizes the use of the fluent API to construct complex nested schemas easily. By defining the Address schema first, it can be reused within the User schema, allowing modular and clear definitions.

Caveats ​

  • Circular references in nested schemas can lead to issues in both validation and type generation.
  • Ensure that each property is defined in a manner that accurately reflects desired data structure, especially with nested properties.

codegen Best Practices ​

Do / Don't Pairs ​

1. Use Full Imports for All Dependencies ​

❌ Don't:

typescript
import { ObjectSchema } from 'blendsdk/codegen';

const mySchema = new ObjectSchema();

✅ Do:

typescript
import { ObjectSchema, StringSchema, NumberSchema } from 'blendsdk/codegen';

const mySchema = new ObjectSchema()
  .named('Example')
  .properties({
    id: new NumberSchema().description('Unique identifier'),
    name: new StringSchema().description('Name of the example'),
  });

Why: Using complete imports helps maintain clarity regarding the origin of imported types, improving the maintainability of the code.

2. Avoid Using any Type ​

❌ Don't:

typescript
import { ObjectSchema } from 'blendsdk/codegen';

let user: any;

const mySchema = new ObjectSchema()
  .named('User')
  .properties({
    id: user.id,
  });

✅ Do:

typescript
import { ObjectSchema, StringSchema, NumberSchema } from 'blendsdk/codegen';

interface User {
  id: number;
  name: string;
}

const mySchema = new ObjectSchema<User>()
  .named('User')
  .properties({
    id: new NumberSchema().description('User ID'),
    name: new StringSchema().description('User Name'),
  });

Why: Using specific types instead of any ensures type safety and prevents errors that can arise from using untyped variables.

3. Include Descriptions for Properties ​

❌ Don't:

typescript
import { ObjectSchema, StringSchema } from 'blendsdk/codegen';

const productSchema = new ObjectSchema()
  .named('Product')
  .properties({
    name: new StringSchema(),
  });

✅ Do:

typescript
import { ObjectSchema, StringSchema } from 'blendsdk/codegen';

const productSchema = new ObjectSchema()
  .named('Product')
  .properties({
    name: new StringSchema().description('Name of the product'),
  });

Why: Descriptions help document your schemas, making them self-explanatory and improving developer experience.

4. Use Fluent API for Schema Definitions ​

❌ Don't:

typescript
import { ObjectSchema } from 'blendsdk/codegen';

const userSchema = new ObjectSchema();
userSchema.named('User');
// Individual property definitions are separate...

✅ Do:

typescript
import { ObjectSchema, StringSchema, NumberSchema } from 'blendsdk/codegen';

const userSchema = new ObjectSchema()
  .named('User')
  .properties({
    id: new NumberSchema().description('User ID'),
    username: new StringSchema().description('Username of the user'),
  });

Why: Using a fluently defined schema improves readability and reduces the likelihood of errors by keeping schema definitions contained.

Anti-Patterns ​

1. Not Using Mappers for Database Introspection ​

In cases where database introspection is necessary, failing to provide a mapper function during introspection can lead to poorly defined or generic types.

Anti-Pattern Example:

typescript
const introspector = new PostgreSQLIntrospector(db);
await introspector.introspect(schemaContainer);
// Generic types without a mapper lead to ambiguity.

2. Ignoring Nullable Types ​

When defining schemas, failing to specify nullable types can lead to unexpected runtime errors when handling null values.

Anti-Pattern Example:

typescript
const userSchema = new ObjectSchema()
  .named('User')
  .properties({
    name: new StringSchema(), // This forgets nullable cases
  });

Correct Approach:

typescript
const userSchema = new ObjectSchema()
  .named('User')
  .properties({
    name: new StringSchema().nullable().description('User\'s name, can be null.'),
  });

Performance Tips ​

1. Batch Schema Definitions ​

When defining multiple schemas, batch them within a single SchemaContainer instance to reduce overhead and improve performance.

Example:

typescript
const schemaContainer = new SchemaContainer();

// Define schemas in batches
const userSchema = new ObjectSchema(schemaContainer).named('User').properties({...});
const productSchema = new ObjectSchema(schemaContainer).named('Product').properties({...});

2. Optimize Mappers for Large Datasets ​

When introspecting large databases, optimize mapper functions by ensuring they handle specific edge cases and avoid unnecessary calls.

Example:

typescript
const mapper: ColumnMapper = (column, scope) => {
  if (column.is_foreign_key) {
      return scope.ref(getReferenceSchema(column)); // Optimize using specific reference schema
  }
  // Handle other column types accordingly...
};

// Apply mapper in introspection
await introspector.introspect(schemaContainer, mapper);

Security Considerations ​

1. Sanitize Input ​

When dealing with database introspection and external inputs, always sanitize and validate data to prevent SQL injections and ensure type integrity.

Example:

typescript
const safeName = sanitizeInput(userInput.name); // Sanitize function to clean inputs
const userSchema = new ObjectSchema()
  .named('User')
  .properties({
    name: new StringSchema().description(safeName),
  });

2. Avoid Exposing Sensitive Data ​

When generating TypeScript types from schemas, avoid including properties that may hold sensitive information, ensuring privacy and compliance.

Example:

typescript
const userSchema = new ObjectSchema()
  .named('User')
  .properties({
    username: new StringSchema(),
    password: new StringSchema().description('DO NOT EXPOSE THIS BACKEND'),
    /* Avoid including sensitive fields in public schemas */
  });

By following these best practices, avoiding common pitfalls, and adhering to performance and security guidelines, developers can harness the full capabilities of blendsdk/codegen to generate robust and maintainable TypeScript schemas.

TypeScript Errors ​

  1. "Cannot find module 'blendsdk/codegen'"
    • Cause: The package may not be installed in your Node.js project.
    • Fix:
      1. Ensure you are in the correct project directory and run:
      bash
      npm install blendsdk/codegen
      1. Check node_modules to ensure the package is present.
  1. "Argument of type 'X' is not assignable to parameter of type 'Y'"
    • Cause: You are passing an incompatible type to a function or method.
    • Fix:
      • Verify the types used and check your function signature. Ensure all properties match the required types.
      typescript
      import { ObjectSchema, StringSchema, NumberSchema } from 'blendsdk/codegen';

const userSchema = new ObjectSchema()
  .named('User')
  .properties({
    id: new NumberSchema(), // Ensure id is a number schema

  1. "Property 'X' does not exist on type 'Y'"
    • Cause: Your TypeScript definitions may not line up with what is expected.
    • Fix:
      • Check if you are trying to access a property that is not defined on the object’s interface or type. Make sure that you are importing the correct classes and have defined properties in your schemas.
      typescript
      const user = {
  id: 1,
  name: "John",
};

console.log(user.name); // Ensure 'name' is part of the declared interface/ type.

Runtime Errors ​

  1. "Unhandled Promise Rejection"
    • Cause: An async operation failed without appropriate error handling.
    • Fix:
      • Always use try/catch blocks when awaiting promises.
      typescript
      async function fetchData() {

  } catch (error) {

  }
}
  1. "Cannot read property 'X' of undefined"
    • Cause: Attempting to access a property of an object that is not defined or is null.
    • Fix:
      • Ensure the object is correctly instantiated before accessing its properties.
      typescript
      const user = getUser(); // Assume this function returns user or null

Debugging Strategies ​

To efficiently diagnose issues within the blendsdk/codegen package, you can follow these structured strategies:

  1. Verify Package Installation: Ensure the package is correctly installed and up to date.

    bash
    npm list blendsdk/codegen

  2. Validate Schema Definitions: When working with schemas, confirm that all properties adhere to your defined types.

    • Use TypeScript's tsc command to compile and check for type errors in your project.

  3. Use TypeScript Compiler Options: Enable strict mode in your TypeScript configuration to catch potential issues early.

    json
    {
  "compilerOptions": {
    "strict": true
  }
}

  4. Console Logging: Utilize console.log generously to output intermediate state or values during development or debugging sessions.

    typescript
    console.log('Schema State:', schemaContainer.getAll());

  5. Try/Catch Blocks: Surround your asynchronous code with try/catch blocks to manage errors effectively.

    typescript
    async function run() {
  try {
    await someAsyncFunction();
  } catch (err) {
    console.error('Async error:', err);
  }
}

Known Pitfalls ​

  1. Ignoring Type Safety: Overusing any or omitting types can lead to runtime errors that are hard to debug.

    • Solution: Always define types for variables, function return values, and parameters.

  2. Improper Schema Definitions: Skipping property definitions or making properties optional when they shouldn’t be can lead to unexpected behavior.

    • Solution: Review schema definitions thoroughly to ensure they accurately represent the intended data structure.

  3. Not Using Descriptions: Failing to add descriptions can result in poor documentation for generated schemas or APIs.

    • Solution: Always document your schemas using the .description() method.

  4. Database Misconfigurations: When using introspection, incorrect database connection strings can lead to missed introspections or errors.

    • Solution: Double-check connection strings and database configurations before running introspections.

  5. Performance Concerns in Large Schemas: Insufficient control over batch schema operations or introspections can lead to performance bottlenecks.

    • Solution: Optimize your queries and introspection mappings to ensure efficiency when dealing with large datasets.

By adopting these troubleshooting techniques, debugging strategies, and awareness of common pitfalls, you can effectively resolve issues arising while using the blendsdk/codegen package, leading to a more stable and maintainable codebase.

PostgreSQL migrations ​

blendsdk/codegen includes PostgreSQL-only schema-first migration generation and a checksummed SQL runner. Define the desired DatabaseSchema once, generate a migration from the committed canonical snapshot, review the SQL, and commit both artifacts.

ts
import { defineMigrationConfig } from 'blendsdk/codegen';

export default defineMigrationConfig({
  schema: './src/database/schema.ts',
});

The assembled package exposes the fixed blendsdk migrate commands: baseline, generate, create, validate, status, up, down, and adopt-baseline. Production jobs run only committed SQL with validate, up --dry-run, and up; they never generate from a live database. Installing blendsdk creates a project-local executable; invoke it with yarn blendsdk migrate or npx blendsdk migrate, or place blendsdk migrate in a package script.

Public migration API ​

ExportPurpose
defineMigrationConfigType and validate the small migration configuration object.
generateMigrationCompare the desired schema with the committed snapshot and emit reviewable SQL.
generateBaselineCreate the initial migration and canonical snapshot for a new project.
runMigrationsValidate, preview, apply, or revert reviewed SQL migrations.
getMigrationStatusRead the applied and pending migration state without mutation.
validateMigrationsValidate local lineage and, when connected, the PostgreSQL ledger prefix.

The APIs return MigrationCommandResult with a MigrationStatus of UP_TO_DATE, PENDING, INVALID_HISTORY, LOCKED, or UNKNOWN_OUTCOME. Operational exceptions are MigrationError instances with a stable MigrationErrorKind and MigrationExitCode.
