webafx Overview ​

What It Is ​

blendsdk/webafx is a TypeScript framework for building web applications on top of Express. It offers a robust structure for dependency injection, plugin architecture, controller-based routing, and built-in security features, enabling developers to create scalable and maintainable web applications quickly.

Key Features ​

  • Type-Safe: Fully supports TypeScript with generics and Zod validation.
  • Service Container: Manages dependency injection with singleton and per-request services.
  • Controller-Based Routing: Organizes routes using a clean and testable approach with a fluent API.
  • Plugin System: Extends functionality with a priority-based architecture, health checks, and shutdown handling.
  • Security: Built-in CORS, Helmet security headers, request ID tracking, and rate limiting.
  • Error Handling: Provides typed HTTP errors and standardized responses with validation details.
  • Request Context: Utilizes AsyncLocalStorage for tracking request-specific data throughout the request lifecycle.
  • Static File Serving: Simplifies serving static assets and supports Single Page Applications (SPA) with fallback handling.

When To Use ​

Use the blendsdk/webafx package when you need to:

  • Develop scalable web applications leveraging TypeScript.
  • Implement a robust architecture with features for dependency management and modularity via plugins.
  • Ensure security best practices are baked into your application with built-in features like CORS and security headers.
  • Handle complex route management in a clear and maintainable way using controllers.

Architecture ​

The framework is built on a layered structure, where core components interact in a cohesive way. Key design patterns include:

  • Service Container Pattern: For managing dependencies and lifecycles of services.
  • Plugin Architecture: Allows extensibility and modular design through plugins.
  • Controller Pattern: Organizes routing logic into manageable chunks.

Dependencies ​

The blendsdk/webafx package relies on:

  • Express: Version 5.x — for web server functionality.
  • Zod: Version 4.x — for input validation.
  • Peer Dependencies: Should match the required versions of Express and Zod.

Services or APIs that require this package must be capable of handling Express middleware and comply with the expectations set by the container architecture.

What Depends on It ​

The package is essential for building robust web applications within the Blend SDK ecosystem. Applications utilizing blendsdk/webafx can rely on its extensible architecture for their backend needs.

Minimum Example ​

Here is the simplest example demonstrating the core functionality of blendsdk/webafx:

typescript
import { WebApplication, BaseController } from 'blendsdk/webafx';
import { Request, Response } from 'express';

class HelloController extends BaseController {
  routes() {
    return [
      this.route().get('/').handle(this.hello),

    this.ok(res, { message: 'Hello, World!' });
  }
}

const shutdown = await app.start();

## ApplicationSettings

**What It Is**  
`ApplicationSettings` is a class designed to manage application configuration settings in a type-safe manner. It allows for loading configuration from various sources, applying validation using Zod schemas, and accessing configuration values reliably.

**How It Works**  
The `ApplicationSettings` class initializes with an optional configuration object. It automatically sets the environment mode to `production` by default unless specified otherwise. Configuration is validated against a predefined Zod schema, and any custom properties are permitted via the `.passthrough()` method of Zod. The class provides methods to get settings, validate configuration, and load settings from external files.

**Complete Example**

```typescript
import { ApplicationSettings } from 'blendsdk/webafx';

async function loadSettings() {
  const settings = new ApplicationSettings({
    PORT: 3000,
    ENV_MODE: 'development',
  });
  
  await settings.loadFromFile('.env.js');
  
  const port = settings.get<number>('PORT', 4000);
  console.log(`Server will start on port: ${port}`);
}

loadSettings().catch(console.error);

BaseController ​

What It Is
BaseController is an abstract class that serves as a foundation for defining application controllers. It provides utilities for route definition, response handling, and access to application settings and services.

How It Works
Controllers extend the BaseController and implement the routes() method to define their specific HTTP endpoints. The class includes helper methods for sending standard responses, such as ok, created, and noContent, ensuring consistent response formatting across the application.

Complete Example

typescript
import { BaseController } from 'blendsdk/webafx';
import { Request, Response } from 'express';

class UserController extends BaseController {
  routes() {
    return [
      this.route()
        .get('/users')
        .handle(this.getUsers),
    ];
  }

  async getUsers(req: Request, res: Response) {
    const users = [{ id: 1, name: 'John Doe' }];
    this.ok(res, users);  // Sends back a 200 response with user data
  }
}

How It Works

Plugin ​

What It Is
Plugin is an interface that represents an extensible part of the application, allowing the integration of additional functionalities such as health checks or middleware. Plugins can facilitate modular design in web applications.

How It Works
A plugin can be registered with the WebApplication, providing it a factory function for initialization. During application startup, the factory is executed, allowing the plugin to install any necessary middleware or register health checks.

A plugin may also expose a terminal hook. While the factory runs in the pre-controller phase, the terminal hook runs AFTER controllers and the /health route but BEFORE the 404 handler. This is the correct place for catch-all / fallback middleware (e.g. an SPA index.html fallback) that must not shadow controller routes. Multiple terminal hooks run in plugin priority order (lower first).

Complete Example

typescript
import { WebApplication, Plugin } from 'blendsdk/webafx';

const myPlugin: Plugin = {
  health: async () => true,
  shutdown: async () => {
    // Cleanup logic here
  },
  // Catch-all middleware mounted after controllers, before the 404 handler:
  terminal: async ({ express, logger }) => {
    express.use((req, res, next) => {
      // last-resort handling for unmatched routes
      next();
    });
    await logger.info('terminal middleware mounted');
  },
};

const app = new WebApplication();
app.use(myPlugin);
await app.start();

Request Context ​

The RequestContext provides request-scoped data that can be accessed throughout the lifecycle of an HTTP request, ensuring that relevant data is available without needing to pass it explicitly through the call stack.

How It Works

Static Files Plugin ​

What It Is
The Static Files Plugin extends the functionality of blendsdk/webafx by allowing static file serving from specified directories. It is capable of supporting Single Page Applications (SPAs) with fallback handling for client-side routing.

How It Works
By registering the static files plugin with a configured root directory, the application can serve files directly over HTTP. It can return a default index.html for unmatched routes, ensuring SPAs function correctly. Caching headers and directory browsing can also be configured.

Complete Example

Composition of Controllers with Dependency Injection ​

When to Use
This pattern is beneficial when you have multiple controllers that need to share services, allowing you to achieve modularity and maintainability in your codebase.

Complete Example

typescript
import { WebApplication, BaseController, ServiceContainer } from 'blendsdk/webafx';
import { Request, Response } from 'express';

class LoggingService {
  log(message: string) {
    console.log(message);
  }
}

class UserController extends BaseController {
  constructor(settings: ApplicationSettings, services: ServiceContainer) {
    super(settings, services);
  }

  routes() {
    return [
      this.route()
        .get('/users')
        .handle(this.getUsers),
    ];
  }

  async getUsers(req: Request, res: Response) {
    const users = [{ id: 1, name: 'John Doe' }];
    this.ok(res, users);
  }
}

class LoggingController extends BaseController {
  constructor(settings: ApplicationSettings, services: ServiceContainer) {
    super(settings, services);
  }

  routes() {
    return [
      this.route()
        .get('/log')
        .handle(this.logMessage),
    ];
  }

  async logMessage(req: Request, res: Response) {
    const loggingService = await this.services.get<LoggingService>('loggingService');
    loggingService.log('Log request received');
    this.ok(res, { success: true });
  }
}

const app = new WebApplication();
app.registerService({
  name: 'loggingService',
  type: 'singleton',
  factory: () => new LoggingService(),
});
app.registerController('/api/users', UserController);
app.registerController('/api/log', LoggingController);

const shutdown = await app.start();
// Server is running...

// Graceful shutdown on SIGTERM/SIGINT
// await shutdown();

Why This Pattern Is Valuable
By leveraging service containers and a clear separation of concerns, this pattern promotes testability and prevents duplication of logic across controllers.

Caveats

  • Ensure that services in the container are registered before they are accessed to avoid runtime errors.
  • Managing many services might lead to complexity; ensure a consistent naming strategy is employed.

webafx Best Practices ​

Do / Don't Pairs ​

1. Use Full Import Statements ​

❌ Wrong✅ Correct
typescript<br>import { ApplicationSettings } from 'application-settings'; // wrong!typescript<br>import { ApplicationSettings } from 'blendsdk/webafx'; // correct

Why: The first example omits the necessary scope, which can lead to confusion and conflicts with similarly named modules in other packages.

2. Handle Errors Gracefully ​

❌ Wrong✅ Correct
typescript<br>await settings.loadFromFile('config.js');typescript<br>try {<br> await settings.loadFromFile('config.js');<br>} catch (error) {<br> console.error(error);<br>} // correct

Why: Not handling errors may cause unexpected application failure; the second example provides a way to log errors and maintain application stability.

3. Use Asynchronous Handlers Properly ​

❌ Wrong✅ Correct
typescript<br>handle((req, res) => { // some logic });typescript<br>handle(async (req, res) => {<br> await someAsyncFunction();<br>});

Why: The first example does not support asynchronous operations properly, potentially leading to unresolved promises and application hang-ups. The second ensures all async operations are correctly awaited.

4. Ensure Middleware Order ​

❌ Wrong✅ Correct
typescript<br>this.route().get('/example').handle(this.example);typescript<br>this.route().get('/example').middleware(middleware).handle(this.example);

Why: Middleware needs to be applied in the order they should run, affecting authentication, validation, and logging functions.

Anti-Patterns ​

1. Not Validating Input ​

  • Problem: This leads to security issues, crashes, and unexpected behavior.
  • Solution: Always use Zod for validation, including edge cases. Use the .validate() method with RouteBuilder.

2. Overusing Global State ​

  • Problem: Over reliance on global states increases the complexity of state management and invokes bugs.
  • Solution: Make use of the Service Container to manage and pass dependencies, ensuring that components do not maintain global state.

3. Ignoring Error Responses ​

  • Problem: Failing to return proper error messages results in poor client experience or hard to debug issues.
  • Solution: Utilize the error handling middleware to send consistent error responses and set up logging in production environments.

Performance Tips ​

1. Cache Responses ​

Leverage HTTP caching by utilizing headers like Cache-Control to reduce server load and improve response times. Implement static files with appropriate caching strategies.

2. Optimize Middleware ​

  • Implement essential middleware only where needed to avoid unnecessary overhead.
  • Use rate limiting on public endpoints to prevent abuse while maintaining a high performance.

3. Avoid Blocking Calls ​

  • Never perform blocking operations on the main thread. Use asynchronous functions and leverage async/await for such tasks.

4. Limit Payload Sizes ​

When registering routes, define strict limits using BODY_LIMIT settings to ensure users cannot overload your application with large requests.

Security Considerations ​

1. Use Helmet ​

Ensure you are using Helmet to automatically set secure HTTP headers for better security and to protect from common vulnerabilities.

2. Rate Limiting ​

Apply a rate limiting middleware to your routes, especially on public APIs to mitigate the risk of DDoS attacks and abusive request patterns.

3. Validate All Inputs ​

Never trust user inputs; always validate incoming requests with Zod schemas to ensure that your API is only processing valid data.

4. Logging Sensitive Data ​

Avoid logging sensitive information, including personal identifiers such as user tokens or passwords. Use context-aware logging where necessary.

webafx Troubleshooting ​

Common Errors ​

Configuration Validation Errors ​

  1. Error Message / Symptom
    Configuration validation failed: - PORT: Invalid value; must be an integer between 0 and 65535.

    Cause
    This happens when the PORT specified in your configuration is outside the valid range (0-65535) or is not an integer.

    Fix
    Check your configuration and ensure the PORT value is a valid integer in the allowed range.

    typescript
    const settings = new ApplicationSettings({ PORT: 3000 });  // Valid PORT

Dynamic Import Failures ​

  1. Error Message / Symptom
    Configuration file error: ./path/to/config.js

    Cause
    If the JavaScript configuration file does not exist or is not properly exported, the dynamic import will fail.

    Fix
    Ensure the file exists at the specified path and that it exports either a default object or a config object.

    typescript
    // Example content of config.js
module.exports = { PORT: 4000 }; // Ensure this format

Missing Middleware in Route Definitions ​

  1. Error Message / Symptom
    Route method must be set before calling handle()

    Cause
    This occurs when you define a route using the route builder but don't specify an HTTP method before trying to handle it.

    Fix
    Ensure that you properly set the HTTP method using get(), post(), etc., before calling handle().

    typescript
    const route = new RouteBuilder()
  .get('/api/some-path') // Ensure method is set
  .handle(async (req, res) => {
    res.json({ message: 'Success' });
  });

Unauthorized Access on Secure Routes ​

  1. Error Message / Symptom
    Unauthorized: Authentication required

    Cause
    This happens when an authenticated request is attempted on a secure route without valid credentials.

    Fix
    Ensure that the request includes valid authentication tokens or necessary credentials in the headers.

    typescript
    const response = await supertest(app.express)
  .get('/api/protected')
  .set('Authorization', 'Bearer valid-token')
  .expect(200);

Debugging Strategies ​

  1. Enable Detailed Error Logging
    Set the logging level to DEBUG or use the errorHandlerMiddleware with includeStack set to true to capture stack traces and detailed error information.

    typescript
    app.use(errorHandlerMiddleware(async (req, err) => {
  console.error(err);  // Log the error for review
}, true));

  2. Use Correct TypeScript Configurations
    Validate that the TypeScript compiler options are set as expected, especially for strict settings.

    json
    {
  "compilerOptions": {
    "strict": true,
    "module": "NodeNext",
    "target": "ES2020",
    // other configurations...
  }
}

  3. Test Individual Components in Isolation
    Make sure to unit test your components, such as services and controllers, using Vitest to catch issues early in development.

    typescript
    describe('MyService', () => {
  it('should perform expected operation', () => {
    // Expectation and assertions for the service.
  });
});

  4. Monitor External Dependencies
    Keep an eye on external APIs or databases that your application relies on and handle errors gracefully if they become unavailable.

Known Pitfalls ​

  • Incorrect Route Handling: Always ensure that routes are properly defined with their corresponding middleware and handlers to avoid runtime errors. Use the fluent API correctly to ensure stability.

  • Async Context Usage: When using AsyncLocalStorage, remember that context data is only available within the scope of asynchronous operations.

  • CORS Misconfiguration: Double-check your CORS settings, ensuring you specify origins correctly; failure to do so can lead to blocked frontend requests.

  • Service Dependencies Not Resolved: Ensure that services are properly registered and that dependencies are resolved within the request context, particularly for per-request services.

  • Validation Error Handling: Make sure all validation errors are properly captured and transformed into responses, making client debugging easier.

By following these troubleshooting guidelines, you will address common errors experienced when working with the blendsdk/webafx package, ensuring a smoother development experience.
